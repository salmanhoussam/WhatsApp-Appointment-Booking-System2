# Lia — إدخال بيانات المالك عبر واتساب

> **دراسة معمارية فقط.** لا كود · لا ميتا · لا migration · لا schema · لا كتابة إنتاج · لا push.
> **محطّة توقّف في §21 بانتظار اعتماد المعمارية والشريحة الأولى.**
>
> **النطاق:** رسائل **المالك** لإدخال بيانات. **خارجه:** فلو الحجز · Item Order · هوية/مصادقة
> الأدمن · قوالب ميتا.

**التاريخ:** ٢٠٢٦-٠٩-١٣ · `bd9324e` · الشجرة نظيفة عدا وثائق
**كل رقم أدناه مقروء من الكود أو الـDB هذه الجلسة، لا من الذاكرة.**

# ١ — الخلاصة التنفيذية

**ثلاث حقائق تقلب ترتيب المراحل الذي اقترحتَه، وكلها مقيسة:**

```
١  القناة لا تعرف الوسائط إطلاقاً       ← _extract_message تعالج ٤ أشكال، والباقي "unknown"
٢  لا تنزيل وسائط في المستودع كلّه       ← grep media|download على whatsapp_service = صفر
٣  المورّد المُركَّب يرى الصور ولا يسمع    ← Claude يقبل صوراً، ولا يقبل صوتاً
```

**والنتيجة المعمارية:** **الصورة أرخص من الصوت، لا أغلى.** الصورة تحتاج **تنزيلاً** (جديد، صغير)
+ **رؤية** (المورّد القائم، استعمال جديد). الصوت يحتاج **نفس التنزيل** + **مورّد ثانياً بالكامل**
(حساب · مفتاح · كلفة · نمط فشل) لأنّ Anthropic **لا تقدّم تحويل كلام إلى نصّ**.

**فأوصي:** `TEXT` → `IMAGE+CAPTION` → `VOICE` — لا `TEXT+VOICE` أوّلاً.

**والخبر الجيد:** الشريحة الأولى (نصّ) **تُبنى بالكامل من قطع قائمة** — `onboarding.py` سابقة
حرفية لـ«AI → JSON → Pydantic»، و`stateData` موجودة للمسوّدة، والأزرار التفاعلية موجودة للتأكيد،
ومسار الكتابة قائم ومُخوَّل. **صفر بنية تحتية جديدة.**

# ٢ — قدرات الوسائط الفعلية اليوم

## ٢أ — ما تعالجه القناة (`whatsapp_flow.py:239-279`)

| شكل ميتا | الحالة |
|---|---|
| `text` | ✅ |
| `interactive.button_reply` | ✅ |
| `interactive.list_reply` | ✅ |
| `button` (نقرة قالب) | ✅ |
| **`audio` / `voice`** | 🔴 → `("unknown", "", "")` |
| **`image`** | 🔴 → نفسه |
| **`document` · `video` · `sticker` · `location` · `contacts`** | 🔴 → نفسه |

## ٢ب — ومصير رسالة صوتية اليوم، خطوةً بخطوة

```
تصل  →  _extract_message = ("unknown","","")
      →  التينانت يُحَل (إن أمكن)
      →  _record_inbound(message_type="unknown", text=NULL)      ← معرّف الوسيط يُفقَد كلياً
      →  آلة الحالات: msg_type != "text" ⇒ «الرجاء اختيار...» أو لا شيء
```

**فالصفّ يُكتَب بلا أي أثر للوسيط.** لا `media_id` · لا `mime_type` · لا `caption` · لا حجم.

## ٢ج — ما لا وجود له، بالقياس لا بالانطباع

| | |
|---|---|
| تنزيل وسائط | 🔴 **صفر.** لا نداء لـ`GET /v18.0/{media-id}` في المستودع |
| `mime_type` أو فحص الحجم | 🔴 صفر |
| حفظ الـ`caption` | 🔴 صفر |
| تحويل كلام إلى نصّ | 🔴 صفر |
| تحليل صور | 🔴 صفر |
| أعمدة للوسائط في `whatsapp_messages` | 🔴 **لا شيء** — الموجود `messageType` · `text` · `templateName` · الترابط والتوقيتات |

**⇒ دعم الوسائط ليس «توسيعاً» — هو قدرة غير مبنيّة.**

## ٣أ — `onboarding.py` هو القالب المعماري، لا مجرّد سابقة

```python
class ClientExtract(BaseModel):          # ← عقد صريح
    slug: str
    business_name_ar: str
    service_type: str                     # قيم محصورة
    ...
extracted = await _extract_with_claude(raw_text)
content = content.strip().removeprefix("```json").removesuffix("```").strip()
return ClientExtract.model_validate_json(content)     # ← الـAI لا يُصدَّق، يُتحقَّق منه
```

**وهذا بالحرف مبدؤك:** الـAI يُنتج مسوّدة، و**Pydantic هو السلطة**. فـLia لا تخترع نمطاً، **ترث
واحداً يعمل بالإنتاج.**

## ٣ب — 🔴 القيد الذي يحكم كل ما يلي

> **Claude يقبل نصّاً وصوراً. لا يقبل صوتاً.**

فالصوت يحتاج **مورّداً ثانياً** (Whisper أو ما يعادله): حساب · مفتاح يُدوَّر · كلفة · نمط فشل ·
وجودة العربية اللبنانية **غير مقيسة عندنا**.

⚠️ **بند تحقّق قبل الالتزام، لا أثبته هنا:** قدرة مدخلات الصوت عند Anthropic **يجب التأكّد منها من
وثائقها وقت التنفيذ** — بنيت هذا على معرفتي، لا على قراءة وثيقة هذه الجلسة.

## ٤هـ — عقود البَذر: ما يُعاد استعماله وما لا

`scripts/data/{slug}/template.json` — مُرقَّم (`version: 3`)، فيه `_meta` وقرارات موثّقة، ويقرأه
`seed_from_rk_template.py` مباشرة.

| الجزء | الحكم |
|---|---|
| أشكال حقول الخدمة/الحلاق | ✅ **تُعاد استعمالها كعقد بيانات** |
| `_meta` · `decisions_applied` · `source_tenant` | 🔴 **تزويد فقط** — لا معنى لها في رسالة مالك |
| محتوى الصفحة | 🔴 تزويد فقط |

> **و`Lia` لا تشغّل سكربتات بَذر — أبداً.** السبب ليس ذوقاً: السكربتات أدوات مشغّل تكتب إعداداً
> **متجاوزةً** تحقّق الـAPI وتخويله وأثره التدقيقي. تشغيلها من رسالة واتساب يعني **مسار كتابة ثانياً
> بلا تخويل**.

# ٥ — معمارية الصوت المقترحة

```
رسالة audio  →  media_id  →  GET /v18.0/{media_id}  →  url (ينتهي سريعاً)
             →  تنزيل مُصدَّق بنفس التوكن  →  فحص mime + حجم
             →  تحويل إلى نصّ (مورّد ثانٍ)  →  transcript + ثقة
             →  Lia تستخرج القصد  →  مسوّدة  →  تحقّق  →  معاينة  →  تأكيد  →  الـAPI القائم
```

| السؤال | الجواب |
|---|---|
| **أين يحدث التحويل؟** | خدمة جديدة `app/services/transcription_service.py` — **خارج** `whatsapp_service` (نقل صرف) و**خارج** الـflow |
| **أي مورّد؟** | **يحتاج قراراً**: Whisper (OpenAI) · Google STT · Azure. **وجودة اللبناني غير مقيسة عندنا** — أوصي بفحص عشر ملاحظات صوتية حقيقية **قبل** الاختيار |
| **نفس المورّد أم ثانٍ؟** | 🔴 **ثانٍ إلزاماً** — Anthropic لا تقدّم STT (§3ب) |
| **إذا فشل التحويل؟** | لا مسوّدة. ردّ: «ما قدرت أسمع الرسالة منيح، ابعتها نصّ أو أعد تسجيلها». **ولا تخمين** |
| **إذا كان الكلام غير واضح؟** | الثقة المنخفضة تُعامل كفشل جزئي: **تُقتبَس القراءة ويُطلب تأكيدها حرفياً** قبل أي استخراج |
| **هل تُقتبَس البيانات؟** | 🔴 **إلزامي** — المالك يرى **ما فهمناه** لا «تمّ». وهذا أرخص حرس ضد الهلوسة |

## ٥أ — عمليات متعدّدة في صوت واحد

> *«ضيف كيراتين ٢٥ دولار، وعدّل سعر البروتين لـ٣٠، وشيل خدمة القص»*

**توصيتي للمرحلة الأولى: عملية واحدة لكل دور محادثة.**

والسبب مقيس لا حذر عام: `create` و`update` و`delete` **ثلاثة عقود مختلفة** بثلاث قواعد تحقّق وثلاث
عمليات حلّ كيان — وخطأ في الثالثة (`شيل`) **غير قابل للتراجع** بلا حذف ناعم، **ولا حذف ناعم على
`CatalogService`** (فيه `isActive` فقط، وهو شيء آخر).

**فالسلوك:** تُستخرَج العملية **الأولى** ويُقال صراحةً: «فهمت الأولى، وبعد ما نخلّصها ابعتلي التانية».
والمعالجة الدفعية بند مرحلة لاحقة **بعد** إثبات الواحدة.

# ٦ — تصنيف دور الوسيط (Media Purpose Classification)

> **إضافة سلمان، ٢٠٢٦-٠٩-١٣، ومُعتمَدة.** وهي تمنع خطأً معمارياً كبيراً: اعتبار كل صورة يبعتها
> المالك «صورة لازم نخزنها».

**السؤال الأول عن أي وسيط ليس «هل في صورة؟» بل «ما دورها في هذا الطلب؟»**

```
Media
  ↓
Purpose Classification
  ├── DATA_SOURCE     الصورة مصدر معلومات — وتُرمى بعد الاستخراج
  ├── ENTITY_ASSET    الصورة جزء من الكيان — وتُخزَّن دائماً
  └── UNRESOLVED      لا تُخمَّن. يُسأل.
```

## ٦أ — أنبوبان متباعدان بعد التصنيف، لا أنبوب واحد

```
DATA_SOURCE                          ENTITY_ASSET
  استخراج (رؤية)                       مرجع في المسوّدة (media_id فقط)
  ↓                                    ↓
  مسوّدة مُهيكَلة                        معاينة تذكر «صورة مرفقة»
  ↓                                    ↓
  تحقّق                                 تأكيد
  ↓                                    ↓
  معاينة صفّاً صفّاً                      إنشاء الكيان عبر الـAPI
  ↓                                    ↓
  تأكيد                                رفع الصورة بالمعرّف الجديد
  ↓                                    ↓
  الـAPI القائم                         Entity.image_url
  ↓                                    ↓
🔴 الوسيط يُرمى حسب سياسة الاحتفاظ      🟢 تخزين دائم — وهو المقصود
```

**وما يمتنع في `DATA_SOURCE` صراحةً**، بكلماتك: لا تخزين دائم · لا `image_url` داخل الكيان · لا
base64 في الـDB · **ولا ربط الصورة بالحجز.**

## ٦ب — كيف يُحدَّد التصنيف — ومن أين يأتي

| المصدر | الوزن |
|---|---|
| **الـcaption / الرسالة المصاحبة** | 🟢 **المصدر الأساسي والوحيد الموثوق** — «دخّل هول» ⇒ DATA_SOURCE · «ضيف هيدا المنتج» ⇒ ENTITY_ASSET |
| نوع القصد المُستخرَج | 🟡 مؤشّر مساند: `create_product`/`set_barber_image` تميل لـASSET؛ `create_*_entries` لـDATA_SOURCE |
| **محتوى الصورة نفسه** | 🔴 **لا يُستعمل للتصنيف إطلاقاً** — صورة قائمة أسعار وصورة منتج تبدوان للنموذج قابلتين للتأويل، والخطأ هنا يُنتج ملفاً دائماً لا يُطلَب أو بيانات مفقودة |
| لا caption | ⇒ **`UNRESOLVED`** |

**وسلوك `UNRESOLVED` محدَّد:** **لا استخراج · لا تنزيل · لا مسوّدة** — سؤال واحد فقط:

```
وصلتني الصورة 📷 — شو بدك أعمل فيها؟
[ 📋 استخرج البيانات ]   [ 🖼 استعملها صورة للعنصر ]
```

**والتنزيل لا يبدأ قبل معرفة الدور** — وهذا حرس خصوصية لا تحسين أداء (§14-٦): صورة قد تحمل ما لا
علاقة له بالعمل، فلا تُقرأ بلا قصد معلوم.

## ٦ج — سلامة الجدول في `DATA_SOURCE` (نقطتك عن الترتيب)

إذا كانت الصورة جدولاً، **فترتيب الصفوف وعلاقات الأعمدة بيانات، لا شكل**. فيُحفَظ:

```
حدود الصفوف · علاقة الاسم بالمبلغ · الترتيب · القيم · العملة · التواريخ
```

**والقاعدة الحاكمة، بصياغتك:** لو لم تكن الرؤية واثقة أنّ `$25` تخصّ محمد لا علياً — **لا تخمّن.**

```
في الصورة تلاتة أسماء وتلاتة مبالغ، بس المحاذاة مش واضحة.
هيك فهمتها:  محمد $25  ·  علي $15
صح؟   [ ✅ صح ]   [ ✏️ لأ، صحّحلي ]
```

**وكل صفّ يُقتبَس بقيمته قبل الكتابة.** وعدم تطابق عدد الأسماء مع عدد المبالغ **رفضٌ لا ترميم.**

# ٦هـ — 🔴 مثال الكالندر: العقد الذي تتخيّله **غير موجود**

**وهذا بالضبط ما طلبت أن أفحصه بدل أن أخترعه — والقياس أوقفه:**

| الفحص | النتيجة |
|---|---|
| حقل مبلغ/سعر/مدفوع على `Reservation` | 🔴 **غير موجود** — لا `amount` ولا `price` ولا `paid` ولا `total` |
| موديل دخل/معاملة/فاتورة/سجلّ/كالندر في الـschema | 🔴 **صفر** — لا `Income` ولا `Transaction` ولا `Payment` ولا `Invoice` ولا `Ledger` |
| حيث يوجد `totalPrice` فعلاً | `Booking` (عقارات — **خارج النطاق**) · `StoreOrder` · `StoreOrderItem` |
| فورم إنشاء الحجز (`ReservationCreateIn`) | `module_key` · `customer_name` · `customer_phone` · `customer_email?` · `reserved_at` · `duration_min?` · `notes?` · `metadata?` — **ولا مبلغ** |
| «الكالندر» في اللوحة | `ReservationsWeekCalendar.jsx` — **عرضٌ للحجوزات**، لا فورم إدخال بمبالغ |

> ## **⇒ «حسان $20 / محمد $25 / علي $15» لا مكان لمبالغها في النظام اليوم.**
> الأسماء تصير `customer_name`، **والمبالغ لا وجهة لها.**

**والثمن مقيس:** `CatalogService.price` موجود ومملوء (٠ خدمة بلا سعر من ١٣) — **فسعر الخدمة معروف
أصلاً**. لكن ما تصفه **مبلغٌ مقبوضٌ فعلاً يختلف عن اللائحة** (٢٠/٢٥/١٥ لثلاثة أشخاص)، وهذا
**مفهومٌ ثالث لا يملكه الـschema.**

|---|---|---|
| **١** | **يبقى خارج النطاق** حتى تُصمَّم قدرة «سجلّ/دخل» بقرارك | 🟢 **توصيتي.** وهي قدرة منتَجية كاملة (تقارير · عملات · مرتجعات · من قبض) لا حقل |
| **٢** | المبالغ في `Reservation.metadata` (Json) | 🔴 **أرفضه** — اختراع شكل داخل عمود بلا نوع، **لا يراه أي تقرير**، وهو بالحرف «الجداول الفاضية» بصيغة أسوأ: جداول مملوءة بما لا يُقرأ |
| **٣** | الأسماء تصير حجوزات **بلا مبالغ**، والسعر من الخدمة المختارة | 🟡 ممكن اليوم بلا schema — **لكنه لا يفعل ما طلبته**، فيُقال صراحةً لا يُقدَّم كأنه الحلّ |

### 🟢 وما **يعمل** اليوم بنفس أنبوب `DATA_SOURCE` بلا أي schema

**صورة قائمة خدمات مطبوعة → خدمات.** لأنّ الوجهة موجودة كاملةً: `name_ar` · `price` ·
`duration_min` · `currency` على `CatalogServiceCreate`.

> **فالأنبوب واحد، والفرق في الوجهة:** `DATA_SOURCE` **جاهز للخدمات**، **ومحجوب للمبالغ** —
> لا لعيب في التصنيف بل لغياب المكان الذي تُكتب فيه.

# ٧ — معمارية الصورة المقترحة

**والفرق الحاكم:** الرؤية **موجودة في المورّد المُركَّب**. فالصورة تحتاج **التنزيل وحده** جديداً.

```
رسالة image  →  media_id + caption + mime  →  تنزيل (نفس مسار الصوت)
             →  base64  →  Claude vision  →  حقول مرشَّحة
             →  مسوّدة  →  تحقّق  →  معاينة  →  تأكيد  →  الـAPI  →  ثمّ الرفع (§13)
```

## ٦أ — التمييز الذي لا تستطيع الصورة قوله عن نفسها

> **«صورة تحمل بيانات» ≠ «صورة هي صورة الكيان».**

ولا يُستنتَج من الصورة نفسها. **فالمصدر الوحيد الموثوق هو الـcaption أو سؤال صريح** — §6ب.

## ٦ب — الحالات الستّ

| | الحالة | Lia تستنتج | **لا** تستنتج | يُسأل |
|---|---|---|---|---|
| **A** | صورة قائمة خدمات مطبوعة | أسماء · أسعار · مدد (مرشَّحة) | **أيّها يُضاف** · الفئة · هل هي جديدة أم موجودة | «كلهن أم واحدة؟» + تأكيد كل صفّ |
| **B** | صورة منتج + «ضيف هيدا المنتج» | أنّ الصورة **أصل** الكيان | الاسم · السعر (لا نصّ فيها) | الاسم والسعر إلزاماً |
| **C** | صورة فيها منتج **ونصّ** سعر/اسم | حقول مرشَّحة **و** أنّ الصورة أصل | أيّ النصّين الاسم لو تعدّد | تأكيد الحقول |
| **D** | عدّة خدمات/منتجات في صورة | قائمة مرشَّحة | **أيّها مطلوب** | **عملية واحدة لكل مرّة** (§12) |
| **E** | صورة بلا caption | **لا شيء** 🔴 | **القصد نفسه** | «شو بدك أعمل بهالصورة؟» — ولا مسوّدة قبل الجواب |
| **F** | صورة قد تحمل معلومات حسّاسة | — | — | **لا تحليل تلقائي بلا قصد معلوم** (وهذا سبب إضافي لقاعدة E) |

## ٦ج — الـOCR مقابل الرؤية

**لا حاجة لـOCR منفصل في المرحلة الأولى.** الرؤية متعدّدة الوسائط تقرأ النصّ المطبوع **وتفهم
بنيته** (اسم/سعر/مدة في صفٍّ واحد) — وOCR يعطي نصّاً خاماً بلا بنية، فيحتاج تحليلاً بعده.

> **قاعدة:** OCR مستقلّ **لا يُضاف** إلا إذا أثبت فحص حقيقي أنّ الرؤية تفشل على قوائم عربية مطبوعة.
> **دليل قبل أداة.**

# ٨ — الاستخراج ليس سلطة

**مبدؤك، مُعاد بصيغة قابلة للتنفيذ:**

```
نصّ · تحويل صوت · OCR · رؤية · تفسير AI
        ↓
   مسوّدة مرشَّحة   ← لا شيء منها بيانات موثوقة
        ↓
Pydantic + حلّ كيان على التينانت الحالي  ← السلطة
```

**و`ClientExtract` أثبتت النمط بالإنتاج.** ولـLia:

```json
{
  "intent": "create_service",
  "confidence": "high | medium | low",
  "data": { "name_ar": "كيراتين للشعر", "price": 25, "duration_min": 60,
            "currency": "USD", "description_ar": null, "name_en": null },
  "unresolved": ["category"],
  "source": { "voice": true, "transcript_confidence": 0.82 }
}
```

## ٨أ — 🔴 المعرّفات لا تأتي من الـAI أبداً

| المعرّف | من يحلّه |
|---|---|
| `service_id` · `barber_id` · `product_id` · `category_id` | **الباكند، على `clientId` الحالي** |
| التينانت | **من سجلّ التاجر، لا من نصّ ولا من `phone_number_id`** — نفس قاعدة A2 |

**و`category_id` إلزامي في العقد (§4أ)** — فحلّ الفئة **جزء من الشريحة الأولى لا تأجيل**: تُحَل
بالاسم، وإن لم تُوجد **يُسأل** (لا تُنشأ بصمت).

# ١٠ — ربط الرسائل المتعدّدة

**أصغر ميكانيزم آمن للمرحلة الأولى — ويستعمل ما هو مبنيّ:**

```
whatsapp_sessions.stateData   ← موجود، Json، TTL ٣٠ دقيقة، مفتاحه (phoneNumberId, customerPhone)
```

| القاعدة | التفصيل |
|---|---|
| **مسوّدة واحدة نشطة لكل رقم** | تُخزَّن في `stateData` تحت `lia_draft` |
| **نافذة الربط** | **١٠ دقائق** من آخر رسالة تخصّ المسوّدة (أقصر من TTL الجلسة عن قصد) |
| **الوسيط ينضمّ للمسوّدة النشطة** | صورة/صوت داخل النافذة ⇒ يُضاف كمصدر، لا يبدأ مسوّدة جديدة |
| **مرجع صريح** (`هيدا`/`هول`/`هاي`) | يُقوّي الربط، **ولا يُنشئه وحده** |
| **رسالة غير ذات صلة** | **لا تُلغي المسوّدة**، لكن تُوقف الربط الضمني — فالوسيط بعدها يُسأل عن قصده |
| **إلغاء** | كلمة صريحة (`إلغاء`/`بلّش من جديد`) أو انتهاء النافذة |
| **بعد التأكيد** | المسوّدة تُمسح فوراً |

> **وما لا أبنيه:** ترتيب وسائط متعدّدة · ربط عبر جلسات · مسوّدات متوازية. **كلها مرحلة لاحقة**،
> ودليل الحاجة إليها لم يُجمَع بعد.

# ١١ — الثقة والتأكيد

| الحالة | السلوك |
|---|---|
| **A — معاينة مباشرة** | ثقة عالية **و** كل الحقول الإلزامية موجودة **و** كيان واحد مُحَل |
| **B — سؤال توضيحي واحد** | حقل إلزاميّ واحد ناقص |
| **C — أسئلة متتابعة** | أكثر من حقل ناقص — **واحداً واحداً**، لا استمارة |
| **D — رفض** | لا قصد مفهوم · أو عملية غير مدعومة بالمرحلة |
| **E — طلب إعادة الإرسال** | فشل تنزيل/تحويل/قراءة صورة |
| **F — امتناع صريح** | **غموض في هوية الكيان** — «اعمل متل هيدا» بلا مرجع · أو اسمان متشابهان |

**وقواعد أمان صريحة:**

```
🔴 سعر أو مدة «مُستنتَجان» بلا ذكر صريح  ⇒  يُسألان، ولا يُفترضان أبداً
🔴 خدمتان باسم متشابه                    ⇒  تُعرَض الاثنتان ويُختار، ولا تُخمَّن
🔴 صورة فيها ١٠ منتجات                    ⇒  عملية واحدة، ولا دفعة
🔴 «اعمل متل هيدا» بلا مرجع                ⇒  امتناع + سؤال
🔴 ثقة منخفضة                             ⇒  تُقتبَس القراءة أوّلاً، ثمّ الاستخراج
```

# ١٣ — الوسائط: التخزين والاحتفاظ والذرّية

## ١٣أ — 🟢 والتصميم القائم يحرس الذرّية بنفسه

**قياس حاسم:** `POST /api/v1/admin/upload` **يشترط معرّف الكيان** لكل سياق يخصّنا:

```
catalog_service  →  service_id مطلوب   (HTTP 400 بدونه)
barber           →  barber_id مطلوب
catalog_item     →  category_id + item_id مطلوبان
```

ويتحقّق من **ملكية التينانت** للمعرّف (إصلاح ٢٠٢٦-٠٨-٣٠).

> ## **⇒ لا يمكن فيزيائياً رفع صورة كيان قبل وجود الكيان.**
> فالسيناريو الذي تخشاه — صورة تصير دائمة ثمّ لا تأكيد — **مستحيل بالبناء** على مساراتنا، لأنّ
> لا معرّف يُوضع في المسار.

**فالترتيب الآمن مفروض لا مُختار:**

```
مسوّدة (صفر كتابة تخزين)  →  تأكيد  →  إنشاء الكيان عبر الـAPI  →  ثمّ الرفع بالمعرّف الجديد
```

**واتجاه الفشل هو الصحيح:** لو فشل الرفع، يبقى **كيان بلا صورة** — مرئيّ وقابل للإصلاح — لا **ملف
يتيم**.

⚠️ **واستثناء خارج نطاقنا:** سياقات `page_*` لا تشترط معرّفاً، **فهي وحدها قابلة للتيتيم**. لا
تلمسها Lia في المرحلة الأولى.

## ١٣ب — أين يُحفَظ الوسيط أثناء المسوّدة؟ **في أي مكان**

**أنظف جواب، وهو أيضاً الأقل بنية:** **لا يُحفَظ إطلاقاً.** يُخزَّن **`media_id` وحده** في
`stateData`، ويُعاد تنزيل الوسيط **لحظة التأكيد**.

```
❌ base64 في stateData          ← الجلسة صفّ DB؛ صورة تضخّمه بلا داعٍ
❌ ملف مؤقّت على القرص            ← Railway بلا قرص دائم، وعامِلان (gunicorn -w 2)
✅ media_id + إعادة التنزيل       ← صفر تخزين مؤقّت، وصفر تسريب
```

⚠️ **بند تحقّق:** مدّة احتفاظ ميتا بالوسيط وصلاحية رابطه **تُقرأ من وثيقة ميتا وقت التنفيذ** — لا
أثبتهما هنا. **ولو كانت المدّة أقصر من نافذة التأكيد**، البديل المُصرَّح: تنزيل فوري إلى **مسار
مؤقّت مُعزول** (`{slug}/_drafts/{draft_id}/`) + **حذف إلزاميّ** عند التأكيد أو الإلغاء أو انتهاء
النافذة. `delete_unit_image(public_url)` موجودة ويمكن إعادة استعمالها.

## ١٣ج — ما يُسجَّل

| | |
|---|---|
| على `whatsapp_messages` | `messageType` الحقيقي (`audio`/`image`) بدل `unknown` · و**الوسيط: `media_id` · `mime` · الحجم · `caption`** ⇒ **يحتاج أعمدة جديدة** ⇒ **قرار schema بموافقتك** |
| على `SecurityAuditLog` | كل مسوّدة تُنشأ · تُؤكَّد · تُرفض · تُلغى · تنتهي — **بالفاعل والتينانت** |
| ولا يُسجَّل | 🔴 **النصّ المحوَّل لا يُخزَّن دائماً بلا قرار** — قد يحمل كلاماً لا علاقة له بالعمل |

## ١٣د — احتفاظ

> **لا سياسة احتفاظ في النظام اليوم — لا للوسائط ولا للنصوص المحوَّلة.**
> **فهذه قرار تصميم يحتاج موافقتك**، ولا أخترعها. والأسئلة التي تحتاج جواباً: هل يُحتفَظ بالصوت بعد
> التحويل؟ بالنصّ المحوَّل؟ لكم؟ ومن يستطيع قراءته؟

| **١** | **نصّ** → `create_service` → مسوّدة → معاينة → تأكيد → الـAPI | 🟢 **صفر.** كل قطعة قائمة |
| **٢** | **صورة + caption** → `create_service` | 🟡 تنزيل وسائط (صغير) + **رؤية بالمورّد القائم** |
| **٣** | **صوت** → نفس الأنبوب | 🔴 **مورّد ثانٍ** + قرار جودة العربية |
| **٤** | صورة قائمة (عدّة صفوف) → مسوّدات متتابعة | بعد إثبات ٢ |
| **٥** | حلاق ومنتج | بعد إثبات الخدمة |
| **٦** | ترقية الوسيط لأصل + تعديل/حذف + عمليات متعدّدة | الأخيرة |

> **ولماذا الصوت بعد الصورة، لا معه:** الصورة تحتاج **قدرة واحدة جديدة** (التنزيل) ثمّ تستعمل
> مورّداً مُركَّباً يرى. الصوت يحتاج **نفس التنزيل + مورّداً كاملاً جديداً** لا نعرف جودته على
> اللبناني. **فالصورة تُثبت الأنبوب بنصف الخطر.**
>
> ⚠️ **ومقايضة أعلنها ولا أحسمها:** أصحاب المحلات يستعملون **الملاحظات الصوتية أكثر** من الصور.
> فقيمة الصوت المنتَجية أعلى، وكلفته الهندسية أعلى. **الترتيب قرارك** — وتوصيتي مبنيّة على المخاطر
> لا على التفضيل.

# ١٧ — الشريحة الأولى بالضبط

**نصّ فقط · `create_service` فقط · تينانت واحد للفحص.**

```
المالك:  "ضيف خدمة كيراتين، 25 دولار، ساعة"
Lia:     هيك فهمت 👇
         الخدمة: كيراتين | السعر: 25 USD | المدة: 60 دقيقة | الفئة: خدمات الشعر
         [ ✅ ضيفها ]  [ ❌ إلغاء ]
المالك:  [✅]
Lia:     ✅ تمّت إضافة *كيراتين* — ظاهرة للزبائن هلق.
```

**والفحص الحاسم:** الخدمة المُضافة **تظهر فوراً في قائمة خدمات فلو الحجز** — لأنّ الكتابة مرّت
بالمسار القائم، فلا شيء إضافيّ يلزم لتظهر.

**ما تشمله:** حلّ الفاعل (قائم) · التخويل (قائم) · استخراج القصد (جديد) · Pydantic (جديد) · حلّ
الفئة (جديد) · أسئلة النقص · معاينة · تأكيد بزرّ · الكتابة عبر `POST /admin/catalog-services` ·
أثر تدقيقي · استهلاك المسوّدة مرّة واحدة.

**ما لا تشمله:** صوت · صورة · تعديل · حذف · حلاق · منتج · عمليات متعدّدة · ترقية أصول · أي قالب ميتا.

# ١٨ — الملفات التي ستتغيّر في الشريحة الأولى

```
جديد    app/services/lia_owner_entry.py        القصد + المسوّدة + المعاينة + التأكيد
جديد    app/schemas/lia_drafts.py              عقود Pydantic — على نمط ClientExtract
تعديل   app/services/whatsapp_flow.py          تفويض رسالة مالك نصّية إلى Lia
                                                (قبل فلو الزبون، بعد merchant_actions)
تعديل   app/services/whatsapp_reservation_flow.py   STATES تُسجَّل حالات Lia — والحرس القائم يمسك النسيان
قراءة   app/api/v1/admin/catalog_services.py   مسار الكتابة — لا يُعدَّل
قراءة   app/core/permissions.py                is_authorized — لا يُعدَّل
```

**وصفر تعديل على:** schema · فلو الحجز · مسارات الكتابة · ميتا.

⚠️ **قرار معماري واحد يلزمني:** هل تنادي Lia **خدمة الكتابة داخلياً** أم **الـHTTP endpoint**؟
الداخلي أسرع ويتجاوز `require_permission` (فيلزم استدعاء `is_authorized` يدوياً)؛ الـHTTP يمرّ
بالبوابات كلها لكنه يحتاج توكناً. **أوصي بالداخلي مع استدعاء صريح لنفس المحكّم** — وهو ما يفعله
`whatsapp_merchant_actions` أصلاً ومُثبَت.

# ٢٠ — مخاطر وقرارات غير محسومة

| # | | الحالة |
|---|---|---|
| ١ | **سياسة احتفاظ الوسائط والنصوص المحوَّلة** | 🔴 **غير موجودة — قرار يحتاج موافقتك** |
| ٢ | **أعمدة الوسائط على `whatsapp_messages`** | 🔴 **schema — بموافقتك، وليست في الشريحة ١** |
| ٣ | **مورّد التحويل الصوتي وجودته على اللبناني** | 🔴 **غير مقيس** — فحص عشر ملاحظات حقيقية قبل الاختيار |
| ٤ | **قدرة Anthropic على مدخلات الصوت** | ⚠️ **تُقرأ من وثيقتها وقت التنفيذ** — لم أقرأها هذه الجلسة |
| ٥ | **احتفاظ ميتا بالوسيط وصلاحية رابطه** | ⚠️ نفس الشيء — يحكم §13ب |
| ٦ | **`price`/`duration_min` اختياريان في الـAPI** | 🔴 **إلزاميان في عقد Lia** — وإلا «الجداول الفاضية» تتكرّر |
| ٧ | **ثلاثة مسارات لكتابة خدمة** | 🔴 قائم **قبل** Lia — تُستهدَف `catalog_services.py` وحدها، والتوحيد بند مستقلّ |
| ٨ | **حدّ المعدّل داخل الذاكرة لا يصلح مع عامِلين** | 🟡 Lia تحتاج حدّاً حقيقياً |
| ٩ | **`working_hours` و`variants`** | 🔴 **لا من AI أبداً** — بنى متشعّبة وخطؤها يكسر الإتاحة |
| ١٠ | **كلفة الاستدعاءات** | 🟡 غير مُقدَّرة — الرؤية أغلى من النصّ بفرق معتبر |
