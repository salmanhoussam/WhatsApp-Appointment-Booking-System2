# ٠ — الحقيقة الواحدة التي تفسّر كل شيء

بحثت عن «لماذا لا يُستكمل الحجز على الواتساب» فوجدت أنّ السؤال نفسه مبنيّ على افتراض خاطئ:

```
┌─────────────┐                                    ┌──────────────────┐
│   الموقع    │ ── wa.me/{config.whatsapp_number} ─▶│ واتساب صاحب المحل │  ← لا webhook
└─────────────┘         رقم التينانت الشخصي          └──────────────────┘     لا bot
                                                                              لا session

┌─────────────┐                                    ┌──────────────────┐
│  البوت      │ ◀── phone_number_id (WABA) ────────│ الرقم المركزي     │  ← كل الذكاء هنا
└─────────────┘         WHATSAPP_CENTRAL_NUMBER     └──────────────────┘
```

> ## 🔴 الموقع والبوت يعملان على **رقمين مختلفين، ولم يُوصَلا قطّ.**

**الدليل المباشر:**

| | |
|---|---|
| الموقع يرسل إلى | [`useReservationBooking.js:299`](frontend/src/hooks/useReservationBooking.js#L299) — `config.whatsapp_number` |
| ومصدره | [`public_service.py:223`](app/services/public_service.py#L223) — `Client.whatsapp_number` |
| والقيم الحقيقية (مقيسة) | `rk` → `96176985477` · `mr-h` → `96171455767` · `barberlab-test` → `96178727986` |
| البوت يسمع على | `WHATSAPP_CENTRAL_NUMBER` ([`config.py:89`](app/core/config.py#L89)) |
| **والنتيجة** | **ولا واحد من الثلاثة هو الرقم المركزي** ⇒ رسالة الزبون **لا تصل الـwebhook إطلاقاً** |

**وهذا بالحرف ما وصفته:** *«رسالة الحجز وصلت لرقمي مباشرة من الزبون، مش من السنترال.»* — ليس عطلاً
في المعالجة، **بل الرسالة لم تدخل النظام أصلاً.**

**والآلية الصحيحة موجودة ومهجورة:** `build_central_booking_link()`
([`whatsapp_service.py:243`](app/services/whatsapp_service.py#L243)) تُنتج `حجز {slug}` بالضبط،
و`_resolve_client_from_deeplink()` مبنيّ لقراءتها، وendpoint `GET /reservations/whatsapp-link`
جاهز — **ومستدعيه الوحيد في كل الواجهة `DemoBuilderPage.jsx:68`.** صفحة حجز الـbarber لا تستعمله.

# ٣ — العطلان بالجذر الدقيق

## 🔴 BLOCKER 1 — هدف واتساب غير صالح

| | |
|---|---|
| **العَرَض** | `customerPhone = 'عبر واتساب'` في **١٧ صفّاً حقيقياً** |
| **الجذر المباشر** | [`useReservationBooking.js:76,282`](frontend/src/hooks/useReservationBooking.js#L76) يمرّر ثابتاً نصّياً |
| **الجذر الحقيقي** | **التصميم افترض أنّ الواتساب سيُكمل الهوية لاحقاً — والرابط الذي يُكملها لم يُبنَ.** فالحقل النصّي علامة «سنعرفه بعدين»، والبعدين لم يأتِ |
| **ولماذا لم يُكتشف** | `send_text` **لا ترفع استثناءً أبداً**، و`_report` تسجّل الفشل ولا تكسر شيئاً. فالحجز ينجح، والزبون لا يُشعَر، **ولا أحد يعرف** |
| **الـsource of truth الصحيح** | **رقم الواتساب الحقيقي للزبون، يُربَط لحظة الاستهلاك** — لا يُخترَع عند الإنشاء |
| **الحدّ الأدنى** | ثلاث حركات في §11، **بلا schema** |
| ⚠️ **قيد قائم** | `customerPhone String` **NOT NULL** ⇒ تخزين «لا رقم بعد» يحتاج **قرار معماري**، مصنَّف في §5 |
| 🔴 **ونفس العطل في Item Order** | `rk` فيه أوامر شراء بـ`phone = 'عبر واتساب'` — **النمط ليس خاصّاً بالـReservation** |

## 🔴 BLOCKER 2 — المرجع يصل ولا يُحَل

**والتشريح يقول إنّ العطل ليس معالجاً ناقصاً، بل ثلاث حلقات مقطوعة بالتسلسل:**

```
١  الرسالة لا تصل الـwebhook أصلاً        ← الموقع يرسل لرقم التينانت (§0)   🔴 الأخطر
٢  ولو وصلت: التينانت لا يُحَل            ← لا تبدأ بـ«حجز»، ولا slug فيها     🔴
٣  ولو حُلَّ:  المرجع لا يُقرأ              ← صفر معالج لـ«رقم الحجز»           🔴
```

**الدليل على ٢:** النصّ يبدأ بـ«مرحباً» فيسقط `startswith("حجز")`؛ ثم لا slug في الـtokens؛
فـ`_resolve_client` تُرجع `None` ⇒ [`whatsapp_flow.py:445`](app/services/whatsapp_flow.py#L445):
**`logger.warning` ثم `return`** — **إسقاط صامت بلا ردّ للزبون.**

**الدليل على ٣:** «رقم الحجز» يظهر في موضعين فقط، **كلاهما نصّ صادر**
(`whatsapp_reservation_flow.py:460` · `whatsapp_flow.py:803`). **ولا قارئ واحد.**

**ولماذا ظهر لك أنّ البوت «بدأ حجزاً جديداً» بدل الصمت:** لأنّ لديك **جلسة قديمة مربوطة**
بـ`barberlab-test`، فنجحت الخطوة ١ من `_resolve_client`. **فالسلوك يعتمد على حالة سابقة** — وهذه
هي المشكلة: زبون جديد **يُسقَط بصمت**، وزبون عائد **قد يُحَل لتينانت خاطئ**.

## ٤ب — 🔴 ثقب أمني قائم في حلّ التينانت

`_resolve_client_from_text()` ([`whatsapp_flow.py:927`](app/services/whatsapp_flow.py#L927)) هو
**آخر تراجُع**، ويعمل على `prisma_client.client.find_many()` — **كل التينانتات بلا نطاق**:

```python
tokens = set(re.findall(r"[a-zA-Z0-9؀-ۿ_-]+", message_text.lower()))
for c in clients:
    if c.slug and c.slug.lower() in tokens:
        return c
```

> **أي كلمة في أي رسالة تساوي slug تينانت ⇒ يُحَل ذلك التينانت.** والـslugs قصيرة (`rk`, `anas`,
> `smar`). فاسم حلاق أو خدمة أو كلمة عابرة قد تحوّل المحادثة لمحلّ آخر. `_resolve_client_from_deeplink`
> حُصِّن بـ`startswith("حجز")`، **وهذا المسار لم يُحصَّن.**
>
> **يُسجَّل كـSecurity Concern (§13)، ولا يُصلَح الآن — خارج أصغر شريحة.**

## ٤ج — النموذج المقترح (تصميم فقط)

```
الموقع ── ينشئ الحجز ──▶ Reservation(clientId, id)         ← التينانت مثبَّت هنا، ولا يُستنتج
   │                            │
   │                    ينشئ سجلّ مناولة:
   │                    hash(token) · clientId · reservationId · expiresAt · consumedAt
   │                            │
   └── CTA ──▶ wa.me/CENTRAL?text="حجز {slug} {token}"      ← البوت يسمع هنا
                              │
                    الرسالة الواردة:
                    ١ slug يحلّ التينانت       (آلية قائمة ✅)
                    ٢ token يحلّ الحجز         (جديد)
                    ٣ رقم المُرسِل يُربَط الآن     ← أوّل رقم حقيقي في السلسلة
                              │
                    ┌─────────┴─────────┐
                    ▼                   ▼
        Reservation.customerPhone   WhatsAppMessage.reservationId
        + customerId                (العمود موجود أصلاً ✅)
```

**ثلاثة مبادئ مثبَّتة، وهي قيودك نفسها:**

1. **التينانت من السجلّ المُطابَق، لا من النصّ ولا من `phone_number_id`.**
2. **التوكن الخام ليس المصدر** — يُخزَّن مُهَشَّماً، ويُستهلك مرّة واحدة.
3. **المرجع `id[:8]` يبقى تسمية بشرية بحتة** — للعرض والمطابقة اليدوية، **لا هوية ولا تخويل.**

> ⚠️ **قرار يلزمك:** هذا التصميم **هو D13 بعينه**، وقد أغلقتَ تنفيذه سابقاً. وPHASE 1 كما صغتَها
> **لا تُنفَّذ بدونه.** فالسؤال ليس تقنياً: **هل نفتح D13 تحت مسمّى PHASE 1، أم نؤجّل PHASE 1؟**
> لا أقرّره.

**وقرار سلمان: الزرّان معاً** — وهو الخيار الذي لا يُضحّي بشيء:

| | «احجز عبر واتساب» (جديد) | «تواصل مع المحل» (قائم) |
|---|---|---|
| يذهب إلى | **الرقم المركزي** | واتساب صاحب المحل شخصياً |
| البوت | **يحلّ التينانت ويستكمل** | لا يتدخّل |
| صاحب المحل | **تنبيه القالب + أزرار** | **رسالة الزبون الخام، كما اعتاد** |

> المباشرة** عبر الثاني. **والثمن الوحيد قرار تصميمي:** أي الزرّين هو الأساسي بصرياً — والتوصية
> **«احجز عبر واتساب»** أساسياً، **و«تواصل»** ثانوياً، لأنّ الأوّل وحده يُنتج حجزاً متتبَّعاً.

**ما لا تفعله الشريحة:** لا تستعيد سياق الحجز (يحتاج ١ب) · لا تُصلح الـ١٧ صفّاً القائمة (قرار
بيانات منفصل) · لا تلمس Item Order.

## ١٥د — والفرق الذي يحدّد الجواب الحقيقي

سؤالك: *«يحفظ المعلومات المفيدة من الـconversation ليستعملها السيستم بتيبل تاني»* — **والمعلومات
المفيدة صنفان، ولا يخدمهما نفس الحلّ:**

```

   المصدر: الكود نفسه             ⇒ تُكتَب في purpose/contextType/reservationId

```

**وأوضح مكسب حقيقي للـAI اليوم، وهو مقيس:** `_CONFIRM_INTENTS` تطابق **نصّاً حرفياً** —
`تأكيد`/`تاكيد`/`إلغاء`/`الغاء`. فمن يكتب **`ok`** أو **`تمام`** أو **`3ande maw3ad`** ⇒ **يفشل
صامتاً.** ونسبة الفرنكو-عربي في لبنان عالية. **فتطبيع القصد، لا الترجمة، هو أوّل قيمة.**

## ١٥هـ — الشكل المعماري، بلا التزام

```
whatsapp_messages.text  ──▶  AI (استخراج)  ──▶  مقترَح مُهيكَل  ──▶  تحقّق  ──▶  جدول الرؤى
       (نصّ خام)              claude-haiku        JSON + ثقة        Pydantic      (جديد)
                                                                        │
                                                     🔴 ولا كتابة مباشرة في الـdomain
```

**وثلاثة مبادئ تُثبَّت الآن لأنّ تجاهلها لاحقاً مكلف:**

1. **الـAI يكتب في جدول رؤى، لا في `Reservation` ولا `Customer`.** وأي كتابة domain تمرّ بالـService
   القائم — قاعدة «قدرة واحدة، مسار كتابة واحد» ([`architecture.md §9`](.claude/rules/backend/architecture.md)).
2. **كل رؤية تحمل ثقتها ومصدرها**، والمنخفضة **تُعرَض ولا تُطبَّق.**
3. **عدم توفّر الـAI لا يكسر شيئاً** — نفس تعاقد `send_text`: يتدهور، ولا يُسقِط حجزاً.

## ١٥و — 🛑 وثلاث عقبات تسبق أي سطر AI

| # | العقبة | الحالة |
|---|---|---|
| ١ | **الصادر لا يُسجَّل** (صفر `OUT`) | 🔴 **يُصلَح أوّلاً** — نموذج يرى نصف محادثة يخمّن الباقي |
| ٢ | **أعمدة الترابط فارغة** (٠/١٣ في الأربعة) | 🔴 **تُملأ بالكود لا بالـAI** — المعلومة موجودة |
| ٣ | **لا مجموعة نصوص** — ١٣ رسالة | 🟡 **لا شيء يُعدَّن بعد** |

> **الجواب المباشر على «تضبط معنا؟»: نعم، وهي إضافة صحيحة ومتّسقة مع المعمارية — ولكنها PHASE 6،
> لا الآن.** والسبب ليس تقنياً: **العقبتان ١ و٢ تجعلان الـAI يشتري ما نملكه.** وترتيباً: أسجّل
> الصادر، أملأ الأعمدة الأربعة، تتراكم محادثات حقيقية — **ثمّ الـAI يعمل على مادّة كاملة.**

# ١٦ — تصحيح: الجلسات الأجنبية ليست دليل الثقب

**سُجِّل سابقاً في هذه الخطة** أنّ ثلاث جلسات من أرقام أجنبية مربوطة بـ`alzabt-demo` هي «الدليل
الميداني الأول» على ثقب §4ب. **وهذا استنتاج لا تحمله البيانات، ويُصحَّح هنا:**

```
21650492272  بعت:  'حجز barberlab-test'   ← deep-link سليم، والتينانت حُلَّ صحيحاً
```

فالجلسة كانت عند `alzabt-demo` من **تواصل سابق**، وdeep-link إبراهيم **جاوزها كما هو مُصمَّم**
([`whatsapp_flow.py:466`](app/services/whatsapp_flow.py#L466)). وأرجح تفسير للثلاثة: **عملاء
محتملون ضغطوا رابط الديمو** — وهذا غرض `alzabt-demo` بالحرف.

**لكن الثقب نفسه مُبرهَن بدليل آخر كان في السجلّ:**

```
09:25   96178944316   →   'موعد rk'   ⇒   حُلَّ rk
```

**«موعد rk» لا تبدأ بـ«حجز»**، فسقط `_resolve_client_from_deeplink`، ومرّت على
`_resolve_client_from_text` **فطابقت الكلمة `rk`**. حميدة هنا لأنّ سلمان كتبها بنفسه —
**والمكانيزم مُثبَت عاملاً**، وهو ما يجعل §4ب حقيقياً لا نظرياً.

# ١٧ — 🔴 العطل الحيّ: A2 غير قابلة للوصول، والسبب هو الصادر غير المُسجَّل

**واقعة حقيقية، ٢٠٢٦-٠٩-١٢ ١٧:٥٩ — بالسجلّ لا بالاستنتاج:**

```
🔘 Template button tapped — text='تأكيد' payload='تأكيد' from=96178727986
   context_wamid=wamid.HBgLOTYxNzg3Mjc5ODYVAgARGBIyQ0FFMDIxRkJFNThBNThENzcA
🚫 Merchant action refused (unknown_context) from 96178727986
```

**كل حلقة عملت إلا الأخيرة:**

| | |
|---|---|
| قالب التنبيه أُرسِل | ✅ `accepted by Meta for 96178727986 (ref=70FA38A1)` |
| ووصل وقُرِئ | ✅ `status=delivered` ثمّ `status=read` |
| النقرة وصلت | ✅ `text='تأكيد' payload='تأكيد'` |
| النصّ طُوبِق | ✅ `_CONFIRM_INTENTS` — **الأزرار بلا payload، والمطابقة على النصّ صحيحة** |
| **المرساة** | 🔴 `find_message_by_wamid(context_wamid)` = `None` ⇒ **`unknown_context`** ⇒ رفض صامت |
| الحجز | `70FA38A1` **بقي `pending`** — والزبون لم يُشعَر |

## السبب الجذري، بقياس واحد

```
grep -rn '"OUT"' app/  →  صفر نتيجة
```

**لا يوجد في الكود سطر واحد يكتب رسالة صادرة.** فـ`whatsapp_messages` كله `IN` (١٩ صفّاً)،
و`find_message_by_wamid` تبحث عن صفّ **لم يُكتَب قطّ**:

```
القالب يُرسَل ✅ → ميتا تُرجع wamid ✅ → لا يُخزَّن 🔴
                              ↓
النقرة تصل ✅ → البحث بالـwamid = None → unknown_context → رفض صامت 🔴
```

> ## **A2 مكتملة وصحيحة، وغير قابلة للوصول بنيوياً.**
> بُنيت على مرساة A3 — صفّ الصادر — **والمرساة لم تُكتَب.** وهذا **ثالث ظهور لنفس نمطي**: أبني
> جهة الاستقبال وأعلنها منتهية بلا التحقّق أنّ جهة الإرسال تسجّل ما تقرأه الأخرى. أوّله «الزرّ
> الميت» (`send_template` بصفر مستدعٍ)، وثانيه اللغة `ar`، وهذا ثالثه.

## والإصلاح واحد يحلّ أربعة أشياء معاً

**تسجيل الرسالة الصادرة بـ`wamid` و`reservationId` و`purpose` و`templateName` لحظة الإرسال:**

| يُصلِح | كيف |
|---|---|
| 🔴 **A2 تعمل فعلاً** | المرساة تُوجد فتُحَل النقرة |
| 🔴 سجلّ القناة نصف الأعمى | يصير فيه الجهتان |
| 🔴 الأعمدة الأربعة الفارغة (٠/١٩) | تُملأ **بالكود، لا بالـAI** (§15د) |
| 🟡 «الإرسال ليس تسليماً» | `sentAt`/`deliveredAt`/`readAt` لها أعمدة **موجودة وفارغة**، والـwebhook يستلم الحالات فعلاً |

**فيصير بند PHASE 1أ الأول، قبل كل شيء آخر** — لأنه يجعل ميزةً **مبنيّة ومدفوعة** تعمل، ولا يحتاج
schema (الأعمدة كلها موجودة) ولا قالباً ولا ميتا ولا D13.
