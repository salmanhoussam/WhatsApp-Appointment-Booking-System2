## Context

في ١١-٠٩-٢٠٢٦ أُضيف `whatsapp_outbound` لحلّ مشكلة واحدة: ضغطة زرّ القالب لا تحمل مرجع الحجز،
و`context.id` هو الرابط الوحيد. أوقف سلمان الترقيع وسمّى السبب:

> **ما نبنيه لم يعد ميزة — صار Channel كاملاً، ويحتاج نموذج بيانات واضح قبل أي جدول إضافي.**

مرّت البوابة بمراجعتين. الأولى رجعت `APPROVE WITH CORRECTIONS` بثماني نقاط؛ هذه النسخة تطبّقها،
وثلاث منها كانت تصحيحاً لخطأ حقيقي في المسودّة لا إعادة صياغة:

# §1 — CURRENT ERD (الحالة عند المصادقة، بالدليل)

```
Client ──┬── Reservation ── Customer      (customerId NULL · SetNull + لقطة اسم/هاتف مجمّدة)
         ├── Barber ── User (barberId, 1-1)
         └── Booking ── Customer          (customerId NOT NULL · Cascade · وفيه source ✅)

whatsapp_sessions      (phone_number_id, customer_phone) UNIQUE
   client_id NULL · بلا FK · ٣٠ دقيقة · حذف صلب عند النجاح (٦ مواضع) · ٤ صفوف

whatsapp_outbound      wamid UNIQUE · client_id FK Cascade · reservation_id بلا FK
   ٠ صفوف · يُكتَب ولا يُقرأ (find_by_wamid بلا مُستدعٍ)
```

### قيود إنتاج غير ممثَّلة في Prisma — تُصان ولا تُسقَط

- **`reservations_active_barber_slot_uidx`** — فهرس **جزئي** فريد على
  `(client_id, barber_id, reserved_at) WHERE status IN ('pending','confirmed','arrived') AND barber_id IS NOT NULL`.
  **موجود فعلاً، مؤكَّد بالاستعلام.** غير قابل للتعبير في Prisma DSL، وغير مرئي لـ`migrate diff`
  — فهو لا يُسقَط تلقائياً، لكنه أيضاً غير محمي. **يُرسم على كل ERD ويُذكر في كل خطة تمسّ
  `reservations`.**
- **`whatsapp_sessions_expires_at_idx`** — **لا يُفترض وجوده.** ذُكر في تحقيق سابق استنتاجاً من
  ملف `.sql`، والفحص المباشر على قاعدة الإنتاج **كذّبه**. أي عمل مستقبلي يتعامل معه على أنه
  غير موجود ما لم يُعَد فحصه.

> **قاعدة عامة مستخلصة:** أي فهرس إنتاج غير ممثَّل في Prisma لا يُسقَط ولا يُفترض. يُفحص مباشرةً
> قبل أي تغيير مخطّط.

### ما يُرمى اليوم — مقيس لا مفترض

| # | المُرمى | الدليل |
|---|---|---|
| ١ | حمولة ميتا الخام | لا عمود خام؛ الوحيد في المخطّط هو `SamsaraEvent.rawPayload` |
| ٢ | **`messages[].id` الوارد** | غير مقروء ⇒ **لا مفتاح تكرار** — §6 |
| ٣ | نصّ كل رسالة واردة وصادرة | لا جدول يحفظه |
| ٤ | `contacts[].profile.name` | اسم الزبون يصل مجاناً والبوت يطلب كتابته |
| ٥ | كل `statuses[]` بما فيه `pricing.*` | `webhook.py:113-146` log-only (G6) |
| ٦ | `context.id` | يُستخرج ويُسجّل ويُرمى — `whatsapp_flow.py:348-352` |
| ٧ | نتيجة ~٣٠ إرسالاً محادثياً | `SendResult` لا يُفحص: مرفوض ≡ مُسلَّم |
| ٨ | قناة الحجز | `Reservation` **بلا `source`** بينما `Booking` لديه |
| ٩ | **أنّ المحادثة حدثت** | الجلسة تُحذف عند النجاح ⇒ القمع المهجور غير مرئي |

**القياس الحيّ الذي يثبت ٩:** أربع جلسات في الإنتاج، كلها منتهية، **كلها واقفة عند
`RES_AWAITING_SERVICE`**، أقدمها ٦ أيام، ولا شيء يكنسها. أربعة أشخاص فتحوا البوت ولم يختاروا
خدمة. هل السبب خلل في القائمة أم زبائن غير جادّين؟ **لا يمكن معرفته — وهذا هو المبرّر.**

# §2 — الحجر الأساس

D-B في `whatsapp-customer-experience-architecture.md` يقول:
*"The shared number is the anomaly, not the key."*
**أُلغي D-B في ١١-٠٩-٢٠٢٦** لسبب تقني قاطع — رقم يدخل الـCloud API يخرج من تطبيق واتساب، فيخسر
صاحب المحل رسائله على هاتفه. فالرقم المشترك صار **دائماً**.

```
✅ phone_number_id  →  whatsapp_account      هوية القناة — يبقى، ويُخزَّن على كل رسالة
❌ phone_number_id  →  client_id             هوية المستأجر — مستحيلة: معرّف واحد لكل المستأجرين
```

> **`phone_number_id` لا يفقد قيمته — يفقد مسؤولية لا يستطيع حملها.**

هو يجيب على «على أي قناة وصلت هذه الرسالة؟»، ويبقى ضرورياً لحظة وجود رقم ثانٍ (فئة أو توصيل).

تحليل المستأجر يصير:

```
رسالة واردة
   ├── ١  سياق صريح: handoff / deep-link          ← الأقوى
   ├── ٢  محادثة قائمة (conversation.clientId)    ← مصدر الحقيقة
   └── ٣  احتياطي: مطابقة سلوغ في النصّ
```

`display_phone_number → Client.phone` (`whatsapp_flow.py:806-813`) **يُتقاعد**: اليوم يُطابق
`alzabt-demo` وحده، فيُرجع المستأجر الخطأ بصمت لأي رسالة بلا نصّ — ضغطة زرّ قالب مثلاً.

# §4 — قرارات لكل جدول

| الجدول | القرار | السبب |
|---|---|---|
| `WhatsAppAccount` | ✅ **بلا `clientId`** | صفّ واحد = الرقم المركزي. يُخرج `wabaId`/`phoneNumberId` من متغيّرات البيئة. عمود `scope` واحد يستوعب «رقم لفئة» و«رقم توصيل» لاحقاً **بلا جدول جديد** — قرار سلمان: مركزي لكل الفئات الآن، مع بقاء الباب مفتوحاً |
| `WhatsAppConversation` | ✅ | المكان الوحيد الثابت لـ`clientId` — §5 |
| `WhatsAppMessage` | ✅ · **يبتلع `WhatsAppOutbound` بسياقه كاملاً** | §4ب |
| `WhatsAppSession` | ✅ يبقى ككيان · يصير ابن المحادثة | §5د |
| `WhatsAppMessageEvent` | ⏸️ **مؤجَّل** بمُحفِّزات معلنة | §4ج |
| `WhatsAppHandoff` | ⏸️ **موقوف على D13** | §8 |
| `whatsapp_templates` | ⏸️ مؤجَّل | قالب واحد. `templateName`+`templateLanguage` على الرسالة تكفي. **المُحفِّز:** أول إصدار ثانٍ من قالب |
| `whatsapp_outbound` | 🔻 **يُتقاعد** | **٠ صفوف ⇒ الدمج مجاني، بلا ترحيل بيانات** |
| `Customer` | ✅ يُعاد استعماله | لا كيان جديد |
| `Reservation.source` | ✅ قرار تصميمي **مستقل** | §4د |

### §4ب — الدمج لا يُسقط السياق

الرسالة تجيب على سؤالين منفصلين، وإسقاط الثاني يُعيد المشكلة التي بدأنا منها من باب آخر:

```
ما الذي أُرسل؟   direction · messageType · text · templateName · wamid
لماذا أُرسل؟     purpose · contextType · contextId · reservationId
```

```
تنبيه تاجر ──▶ wamid ──▶ ضغطة زرّ ──▶ context.id ──▶ صفّ الرسالة ──▶ reservationId
```

`purpose` (مثلاً `new_reservation_alert`) يوجّه الردّ **بالنيّة**، لا بتخمين نصّ الزرّ — والنصّ
عربي وقابل للترجمة. `contextType`/`contextId` يُبقيان الباب مفتوحاً لسياق غير الحجز (طلب متجر)
بلا عمود جديد لكل نوع.

### §4ب-٢ — ✅ A3 · مِلكية الرابط بين الرسالة والحجز

> **حُسم في ١١-٠٩-٢٠٢٦ بقرار سلمان، قبل فتح Implementation Gate 1.**
> السبب: المسودّة كانت تحمل **رابطين لنفس العلاقة بلا مِلكية واضحة** — وهو شكل
> **Duplicate Architecture** بتصنيف `TENANT_OS.md`، ونفس الخطأ الذي صُحّح في `Message.clientId`.

```
contextType + contextId   ──▶  المرجع المِعياري لسياق الأعمال (canonical business context)
reservationId             ──▶  مرجع مُيسَّر مُصنَّف (typed convenience reference)
                                لسياقات الحجز، يُصان ذرّياً مع السياق المِعياري
```

**سبعة ثوابت — لا يُفتح Gate 1 بدونها:**

1. `contextType`/`contextId` هو **المرجع المِعياري** للسياق.
2. حين يكون `contextType = "reservation"`، يجب أن يشير `reservationId` إلى **الحجز نفسه**.
3. **لا يُسمح** بـ`reservationId` يشير إلى حجز مختلف عن السياق.
4. **الكاتب الواحد يحدّد الاثنين في العملية/المعاملة نفسها.**
5. القراءة السريعة للحجز يجوز أن تستعمل `reservationId` مباشرةً — وهذا **تحسين ومرجع مختصر**،
   لا مصدر حقيقة مستقلّاً.
6. رسالة لا ترتبط بحجز ⇒ `reservationId = NULL`، ويبقى السياق العامّ صالحاً.
7. **لا يوجد مسار يسمح للاثنين بأن يتطوّر كلٌّ منهما بمعزل عن الآخر.**

> **تمييز لفظي مقصود** (تصحيح سلمان): `reservationId` **ليس «مُزال التطبيع» فحسب** — هو مرجع/FK
> حقيقي، لا نسخة محسوبة. وهذا يفرّقه عن `Message.clientId` في §5ج، الذي هو فعلاً نسخة مشتقّة من
> `Conversation.clientId`. حقلان، وعلاقتان مختلفتان بمصدر الحقيقة، ولا يوصفان بالكلمة نفسها.

**الفائدة التي يحفظها هذا الشكل:** الاستعلام والتخويل يبقيان مباشرَين على `reservationId`
(§7 يعتمد عليه للوصول من ضغطة زرّ إلى `reservation.clientId`) — **بلا خلق مصدر حقيقة ثانٍ.**

### §4ج — تأجيل الأحداث، بمُحفِّز قابل للفحص

| | يكفي | لا يكفي |
|---|---|---|
| أعمدة `sentAt/deliveredAt/readAt/failedAt` + `errorCode` | «ما آخر حالة وصلت إليها الرسالة؟» | «أعطني كل انتقالات الحالة» |

**مُحفِّزات الترقية — أيٌّ منها يكفي وحده:**
1. الحاجة إلى تاريخ أحداث متعدّد لرسالة واحدة
2. `pricing.*` / `conversation.*` من ميتا لحساب كلفة القناة **لكل مستأجر**
3. **أي حاجة إلى audit trail زمني للرسالة**

> **المُحفِّز ٢ صار تجارياً لا نظرياً:** فُعِّلت WhatsApp Insights في ١١-٠٩-٢٠٢٦. تقاريرها
> **مجمّعة على مستوى الـWABA**، وعندنا رقم واحد لكل المستأجرين ⇒ **لا تستطيع الفرز بين
> المستأجرين أبداً**. ونفس السبب: الرقم المشترك الذي منع WABA لكل مستأجر هو الذي يُعميها عنهم.
> وبيانات الكلفة نفسها **تصل إلينا في الـwebhook** (`statuses[].pricing.*`) **ونرميها** —
> فالتقاطها يعطي الرقم نفسه منسوباً لكل مستأجر، وهو ما لا تستطيعه Insights.

### §4د — `Reservation.source`

`source = "whatsapp" | "website" | "admin"` بدل بادئة نصّ حرّ في `notes` (قابلة للتعديل وتضيع).

**نوع `String` مع قيم موثَّقة، لا `enum` في قاعدة البيانات** — مطابقةً لـ`Booking.source` القائم،
ولعُرف المشروع المعلن في `SecurityAuditLog.eventType`: *"extensible, not an enum by design"*.

**قرار مستقل:** لا يتبع أي جدول من جداول القناة، ولا يوقفه مانع منها.

# §5 — تعريف المحادثة

### §5أ — ما هي المحادثة

> **الارتباط طويل العمر بين هوية زبون، وقناة واتساب، وسياق مستأجر معيّن.**

الهوية المنطقية: `(accountId, customerPhone, clientId)` — و`clientId` **قابل للفراغ**.

**لا يجوز أن يكون `(phoneNumberId, customerPhone)` مفتاحاً فريداً للمحادثة** بعد قرار الرقم
المركزي: الزوج نفسه يخدم كل المستأجرين، فهو يدمج محادثتَي محلَّين مختلفَين في صفّ واحد.

**حالتان مختلفتان يجب أن يستوعبهما التعريف:**

```
محادثة زبون                      محادثة تهيئة مستأجر
رقم واتساب                        رقم واتساب
   ↓                                 ↓
Conversation                      Conversation
   ↓                                 ↓
clientId = rk                     clientId = NULL
                                     ↓  عند التوفير
                                  clientId = X
```

محادثة التهيئة **تحدث قبل وجود المستأجر** — ولهذا `clientId` قابل للفراغ. مطلب حقيقي، لا احتياط.

### §5ب — دورة الحياة، والقيد الذي تفرضه

المحادثة تُفتح وتُغلق وتُفتح من جديد (`status`, `closedAt`). لذلك الفريدة **ليست** على الثلاثي
مطلقاً، بل:

> **محادثة نشطة واحدة على الأكثر لكل `(accountId, customerPhone, clientId)`.**

وهذا **فهرس فريد جزئي**. وللمشروع سابقة حيّة بنفس الشكل بالضبط —
`reservations_active_barber_slot_uidx` — مع درسها المدفوع:

- Prisma **لا تستطيع التعبير عنه** ⇒ يُطبَّق بـSQL صريح ويُوثَّق في المخطّط كتعليق
- `migrate diff` **لا يراه** ⇒ لا يُسقطه، لكنه أيضاً لا يحميه

### §5ج — المحادثة مصدر الحقيقة، لا الرسالة

```
Conversation.clientId          ★ مصدر الحقيقة
        └── Message.clientId   مشتقّ · للفهرسة والاستعلام فقط
```

`message.clientId` يبقى لأن قاعدة المنصّة قاطعة: *«كل DB query فيها clientId — لا استثناء»*،
والانضمام للمحادثة في كل استعلام كلفة بلا مقابل.

**الثابت الواجب، والخطر الذي يمنعه:**

```
❌ conversation.clientId = rk   و   message.clientId = footlab     ← يجب أن يكون مستحيلاً
```

**آلية الإنفاذ: كاتب واحد فقط.** `message.clientId` يُكتب **حصراً** من `conversation.clientId`
داخل مستودع الرسائل، ولا يُقبل كوسيط من أي مُستدعٍ. تطبيق مباشر لمبدأ
`rules/backend/architecture.md §9` — *«قدرة واحدة، مسار كتابة واحد»*: الثابت يُحرَس بعدم وجود
مسار ثانٍ، لا بقيد في قاعدة البيانات.

**وعندما تُربَط محادثة تهيئة بمستأجر جديد** (`NULL → X`)، تُحدَّث رسائلها معه في نفس المعاملة.

**وحالة `clientId = NULL` مع القيد الجزئي:** Postgres يعتبر كل `NULL` مميّزاً، فالقيد لا يمنع
محادثتَي تهيئة لنفس الرقم. **صحيح ومقصود — ومكتوب هنا صراحةً بدل أن يُكتشف لاحقاً.**

### §5د — المحادثة ≠ الجلسة

| | المحادثة | الجلسة |
|---|---|---|
| تجيب على | تاريخ القناة والسياق | أين نحن في الحوار الآن |
| العمر | أيام/أسابيع | ٣٠ دقيقة |
| عند النجاح | **تبقى** | تُحذف |

```
Conversation
  ├── Message 1  "مرحبا"
  ├── Message 2  اختيار خدمة
  ├── Message 3  اختيار حلاق
  ├── Session    RES_AWAITING_SLOT      ← تُحذف عند النجاح
  └── Message 4  ...                     ← يبقى
```

> **الجلسة مؤقتة ولا تحمل تاريخ المحادثة معها. حذفها يجب ألّا يعني اختفاء المحادثة.**

وهذا حرفياً عيبُ اليوم: أربع جلسات موجودة، ولا تاريخ يثبت ماذا حدث.

# §6 — تكرار الوارد: متطلّب صحّة

**ليس تحسيناً — هو حدّ صحّة وأمان، وخلل قائم اليوم.**

```
اليوم:   ميتا ──▶ رسالة ──▶ آلة الحالة ──▶ create_reservation()
         إعادة محاولة بنفس الـwamid ──▶ آلة الحالة تعمل ثانيةً ──▶ حجز مكرّر ممكن
```

المطلوب:

```
wamid وارد ──▶ مُعالَج سابقاً؟ ──┬── نعم ──▶ تجاهُل
                                └── لا  ──▶ معالجة
```

**تفصيلان يحسمان صحّته:**

1. **`wamid UNIQUE` في `WhatsAppMessage`، وقابل للفراغ.** الاتجاهان يتشاركان العمود — معرّفات ميتا
   فريدة عالمياً. والفراغ ضروري: **إرسال فاشل بلا `wamid`**، وPostgres يسمح بـ`NULL` متعدّدة في
   فهرس فريد — وهو السلوك المطلوب تماماً.
2. **«افحص ثم عالِج» متسابقة. «أدخِل ثم عالِج» ذرّية.** الإدخال نفسه — ونجاحه أو ارتطامه بالقيد
   الفريد — هو المطالبة. ومع `gunicorn -w 2` (وهو ما سبّب عطل الجلسات في الذاكرة أصلاً) هذا فارق
   حقيقي لا نظري.

**الموضع:** قبل آلة الحالة وقبل أي تعديل أعمال.

# §7 — صلاحيات فعل التاجر

```
❌ button payload = "تأكيد"  ──▶  أكّد الحجز
```

```
✅ رقم المُرسِل
      ↓ ربط بهوية تاجر (User.phone / Barber.phone / Client.whatsapp_number|phone)
   هوية تاجر
      ↓
   الحجز يأتي من سياق الرسالة (context.id → صفّ الرسالة → reservationId) — لا من النصّ
      ↓
   هل المُرسِل مخوَّل على reservation.clientId تحديداً؟
      ↓ نعم فقط
   الفعل  +  log_security_event على كل محاولة، ناجحة أو مرفوضة
```

**ثلاث نقاط تجعل هذا غير تافه:**

1. **الرقم المركزي مشترك** ⇒ لا شيء في الغلاف يقول لأي مستأجر تنتمي الضغطة.
   `reservation.clientId` هو المرساة الوحيدة.
2. **المُرسِل قد يخدم أكثر من مستأجر.** صاحب واحد قد يملك محلَّين (وهو سؤال
   `clients.phone UNIQUE` المفتوح أصلاً). فالربط مُرسِل→مستأجر **ليس ١:١**، والتخويل يُفحص
   **لهذا المستأجر تحديداً**.
3. **الحجز لا يُؤخذ من الحمولة أبداً.** زرّ محرَّر في WhatsApp Manager بلا حقل payload تصل حمولته
   مساويةً لنصّه — فحجزان في الساعة نفسها يُنتجان ضغطتين متطابقتين.

# §10 — التحقق

بوابة تصميم، فالتحقق **وثائقي لا تنفيذي**:

1. كل ادّعاء حالة راهنة يستشهد بملف:سطر أو باستعلام مُنفَّذ فعلاً — وقد صُحّح ادّعاء واحد
   (`whatsapp_sessions_expires_at_idx`) لأنه استُنتج من ملف لا من قاعدة البيانات.
2. الـERD المقترح يُقارَن عمود-بعمود مع `prisma/schema.prisma`: كل عمود قائم إمّا بقي أو له وريث
   مسمّى — **خصوصاً `reservations_active_barber_slot_uidx` الذي لا تراه Prisma**.
3. كل تأجيل يحمل **مُحفِّزاً قابلاً للفحص**، لا «لاحقاً».
4. كل خطوة في §9 تُعلن مانعها أو غيابه صراحةً.

**عند التنفيذ لاحقاً — قاعدة غير قابلة للتفاوض:** كل تغيير يمرّ بـ`prisma migrate diff` **قبل**
التطبيق، ويُطبَّق بـSQL صريح داخل معاملة. **لا `prisma db push`.** ليس تفضيلاً: `db push` في
١١-٠٩-٢٠٢٦ كان سيحذف `store_orders_client_id_customer_id_idx`، وهو فهرس إنتاج حقيقي أنشأه شغل
هوية الزبون، ولم يصل يوماً إلى ملف المخطّط.
