# Lia — Live Domain Verification  ·  مسارُ تحقّقٍ مستقلّ

## Context

الحزمُ المحليّةُ ٥٨٦ فحصاً خضراء، **ولا واحدٌ منها أثبت أنّ المالكَ الحقيقيَّ يستطيع استعمالَ
البوت.** اختبارُ ١٧ أيلول الحيُّ فشل بينما كانت الحزمُ خضراء — لأنّ ما فشل كان في الطريقِ بين
هاتفِ سلمان وقاعدةِ البيانات، لا في المنطق.

فهذا المسارُ يختبر **البوتَ الذي سيستعمله المالك**: هاتف → Meta → webhook → النسخةُ المنشورة →
قاعدةُ الإنتاج. وهو **منفصلٌ عن Phase B وعن قرارِ الإيداعِ القديم** كما نصَّ سلمان.

### 🔴 حقيقتان مقيستان تحكمان الخطّة

```
١  المنشورُ = b5f5dd0            (railway: environments=['production'] واحدة، branch=main)
   ولا يحمل S7 · ولا إصلاحَي F-C1/F-C2 · ولا T4.
   ⇒ اختبارٌ حيٌّ قبل النشر يختبر بوتاً بلا فحصِ تكرارٍ وبلا فرانكو وبلا مواعيد.
   ⇒ **النشرُ شرطٌ للاختبار، لا خطوةٌ تليه.** (قرارُ سلمان: ننشر أوّلاً)

٢  «تسجيلُ Customer عن طريق Lia» ليست قدرةً قائمة.
   العملياتُ المسجَّلةُ خمس: create_service · create_product · update_product
   · create_catalog_item · create_reservation — **ولا واحدةَ تُنشئ زبوناً.**
   صفُّ الزبونِ يُولَد أثراً جانبيّاً لـcreate_reservation (find-or-create بالرقم،
   reservation_service.py «Resolve [Customer]»).
   ⇒ القسمُ G يُختبَر **عبر** H/I لا كمسارٍ مستقلّ · و«تعديلُ بيانات زبون» غيرُ موجودٍ إطلاقاً.
```

**وتصحيحٌ صغيرٌ في التأطير:** Lia لا تملك دوماً. رقمُ واتسابٍ مركزيٌّ واحد، والتينانتُ يُحَلّ من
**رقمِ المُرسِل** (`whatsapp_flow.py:474` تنادي `try_handle` قبل حلِّ التينانت). فـ«الدومين» هنا =
النسخةُ المنشورةُ على Railway + قاعدةُ الإنتاج. والهدفُ `barberlab-test` وحدَه — **لا rk**.

## التسلسل — وكلُّ بوّابةٍ تحتاج كلمتَك

```
G0  النصوصُ الـ١٧ لـT4 **مُقَرَّةٌ** ⇒ خطُّ أساسِ التنفيذ — لا يُعاد فتحُها
G1  إيداعُ T4 (٦ ملفّات + حزمةُ اختبار)
G2  push → deploy                        ← ينشر على barberlab-test و rk و mr-h معاً
G3  إثباتُ أنّ المنشورَ صار الجديد          ← **طبقتان، لا واحدة** (أدناه)
G4  التشغيلُ الحيُّ ٢٨ سيناريو             ← كتابةُ إنتاجٍ على barberlab-test ورقمِك
G5  قراءةُ الدليلِ من DB بعد كلِّ دفعة        ← سكربتٌ read-only
```

### G3 — لماذا `commitHash` وحدَه لا يكفي  (تعديلُ سلمان ١)

```
الطبقةُ الأولى  railway commitHash == HEAD المدفوع        ⇒ يُثبت أنّ **النشرَ** حصل
الطبقةُ الثانية  ربطُ الطلبِ بالنسخة: لكلِّ سيناريو نلتقط من اللوج السطرَ الذي عالج
                **هذه الرسالةَ بعينِها** (wamid / sender / الوقت) ونتحقّق أنّه من النشرِ الجاري
```

**والسببُ ملموس:** الخادمُ يعمل بـ`gunicorn -w 2` — عاملانِ اثنان. فـ«النشرُ تمّ» لا يساوي «هذا
الطلبُ عولج بالكودِ الجديد»، ونافذةُ التبديلِ وحدَها تكفي لتفسيرِ فشلٍ نُسمّيه عطباً.
⇒ **أيُّ سيناريو لا نجد له سطرَ لوجٍ مرتبطاً يُسجَّل Unknown، لا PASS.**
(«railway commit + logs فقط» كما هي القاعدةُ القائمة — ولا `railway variables` إطلاقاً.)

## ما يُبنى

### ١ · `scripts/lia_live_evidence.py` — الدليلُ من قاعدةِ البيانات، لا من واتساب

يُعيد استعمالَ حارسِ Gate ① المُثبَت (`.claudedocs/work/lia-s7-preflight/2026-09-18/
preflight_read_only.py`): سدُّ **٢٧٥** دالّةَ كتابةٍ على مستوى صفوفِ `prisma.actions.*Actions`
+ `execute_raw` + `batch_`، والسدُّ يُثبَت بمحاولةٍ حقيقيّةٍ قبل أيِّ قراءة.

يأخذ ختماً زمنيّاً ويطبع لـ`barberlab-test` وحدَه:

```
CatalogItem / CatalogService الجديدة   id · الاسم · السعر · القسم · clientId
Reservation الجديدة                    id · reservedAt الخام · status · source · barberId
                                       · serviceId · customerId · clientId
Customer الجديدة                       id · phone · name          ← ومنها أثرُ WALK_IN
SecurityAuditLog                       lia_* لكلِّ محاولة، ناجحةً كانت أو مرفوضة
فحصُ تكرارٍ بعد كلِّ دفعة                 أسماءٌ مطويّةٌ ×2 (هل عاد «مشط خشب»؟)
🔴 وفحصُ تسرُّبٍ عبرَ التينانتات           صفرُ صفٍّ جديدٍ على rk أو mr-h في نافذةِ الاختبار
```

السطرُ الأخيرُ هو ما يجعل القسمَ L حقيقيّاً: النشرُ يشمل `rk`، فغيابُ الكتابةِ عنده يجب أن
**يُقاس** لا أن يُفترَض.

### 🔴 وغيابُ الصفِّ ليس إثباتاً للعزل  (تعديلُ سلمان ٢)

```
«لا صفَّ على rk» دليلٌ سلبيٌّ قويّ — ويتّفق مع عطبٍ ومع رفضٍ آمنٍ على حدٍّ سواء.
فالعزلُ يُثبَت بشِقَّين معاً:
   ① العمليةُ نفسُها **رفضت** — صمتٌ أو رسالةُ رفضٍ + صفُّ `lia_entry_refused` /
     `lia_write_refused` في SecurityAuditLog يحمل السببَ والعمليةَ والمُرسِل
   ② وصفرُ كتابةٍ في التينانتِ **الصحيحِ والخاطئِ معاً**
⇒ شقٌّ بلا الآخرِ يُسجَّل Unknown. ومحاولةٌ لم تترك أثراً في سجلِّ التدقيقِ = لم نُثبت أنّها وصلت أصلاً.
```

### ٢ · Artifact — «Lia Live Test Console»

أفضلُ من السابق بأربعةِ فروقٍ حقيقيّة، لا بالشكل:

```
١  كلُّ سيناريو يحمل **النصَّ العربيَّ الحرفيَّ** المطلوبَ إرساله + زرَّ نسخ
٢  حقولٌ تُملأ وتبقى: الردُّ الفعليّ · الحالةُ قبل/بعد · DB نعم/لا · Record ID · PASS/FAIL
٣  زرُّ «ولّد التقرير» ⇒ نصٌّ واحدٌ تنسخه لي، ففي تقريرِك كلُّ حقولِ القسم M
٤  لافتةٌ حمراءُ أعلى الصفحة تحمل **commit المنشور**، فلا يبدأ أحدٌ على نسخةٍ قديمة
```

يُبنى بقدرةِ `artifact` (تبقى النتائجُ محفوظةً وتصلني) — تُحمَّل مهارةُ
`artifact-capabilities` قبل كتابةِ أيِّ كودِ runtime.

🔴 **وليس مصدرَ الحقيقة**  (تعديلُ سلمان ٥)

```
مصدرُ الحقيقة:   واتساب (ما وصل فعلاً)  ·  لوجُ Railway  ·  قاعدةُ الإنتاج
والـArtifact:    واجهةُ تسجيلٍ وتجميعِ تقريرٍ — لا أكثر
```
فحقلٌ مكتوبٌ فيه «PASS» ليس دليلاً؛ الدليلُ هو الصفُّ والسطرُ واللقطة. ولا يُغلَق سيناريو من
الـconsole وحدَها، ولا يُشتَقّ منه رقمٌ نهائيٌّ بلا قراءةِ DB تسنده.

كُتِب — وهذا نصُّ اعتراضِك في القسم M.

### L-24 · ثلاثُ طبقاتٍ لا تُخلَط  (تعديلُ سلمان ٣)

```
١  نداءٌ داخليّ      هل نُودي `_notify_merchant_new_reservation`؟   ← لوج · أضعفُ الثلاث
٢  قبولُ ميتا       هل ردَّت Cloud API بـ200 و`wamid`؟              ← لوجُ الإرسال
٣  وصولٌ حقيقيّ      هل ظهرت الرسالةُ على هاتفِك؟                    ← لقطةُ شاشة · **الأقوى**
```

🔴 **والطبقةُ الثالثةُ لا تأتي من قاعدةِ البيانات، ومقيسٌ لماذا:** `webhook.py:126` يقرأ
`statuses[]` و**يسجّله فقط** — لا شيءَ يكتب `deliveredAt`. فحالةُ التسليمِ غيرُ مرئيّةٍ بالتصميم،
و«صفرُ تسليماتٍ مسجَّلة» ليس دليلاً على أنّ شيئاً لم يصل. ⇒ الشاشةُ هي الدليل.

ومصادفةٌ مفيدة: إشعارُ التاجرِ لـ`barberlab-test` يذهب إلى **رقمِك أنت**، فالطبقاتُ الثلاثُ
قابلةٌ للقياسِ في اختبارٍ واحد. وفي L-21 المطلوبُ **العكسُ تماماً**: الطبقةُ ① لا تُنادى أصلاً —
وغيابُ رسالةٍ على هاتفِك هناك هو النجاح.

## التحقّق — كيف نعرف أنّ هذا المسارَ نفسَه نجح

```
١  G3 مُثبَتٌ قبل أيِّ سيناريو:  railway commitHash == HEAD المدفوع
٢  ٢٨ سيناريو لكلٍّ منها الحقولُ العشرةُ من القسم M، ولا واحدٌ منها «جرّبنا واشتغل»
٣  كلُّ كتابةٍ مؤكَّدةٌ من DB — id حقيقيّ · التينانتُ الصحيح · بلا تكرار · بلا حقلٍ تغيّر سهواً
٤  صفرُ صفٍّ جديدٍ على rk أو mr-h طوالَ النافذة — **مقيسٌ لا مفترَض**
٥  الحزمُ المحليّةُ ٥٨٦+ تبقى خضراء بعد أيِّ إصلاحٍ يخرج من هذا المسار
٦  والنتيجةُ الصادقة: قائمةُ Confirmed / Side Findings / Unknowns — ولو فشل نصفُها،
   فذلك نجاحُ الاختبارِ لا فشلُه
```

### 🔴 ومفرداتُ النتيجةِ ليست PASS/FAIL وحدَها  (تعديلُ سلمان ٤)

```
PASS                              تصرّف كما وُصف، والدليلُ يسنده
FAIL                              خالف ما وُصف
Confirmed behavior / Product risk  فعل **ما بُني له بالضبط**، والأثرُ نفسُه يحتاج قرارَ منتج
Unknown                           لم نستطع الإثبات، ويُقال السببُ
```

**و L-22 من الصنفِ الثالثِ بالتعريف:** اندماجُ كلِّ «الطيّارين» في صفِّ زبونٍ واحدٍ هو نتيجةُ
قرارِك (٢٠٢٦-٠٩-١٨) وعملُ الكودِ الصحيح — فوضعُ PASS بجانبِه يقول إنّ هذا **مطلوب**، وهو ليس
كذلك بالضرورة. يُسجَّل بأثرِه المقيس: كم صفَّ زبونٍ ظهر، وبأيِّ اسم، وكم حجزاً يشير إليه.
