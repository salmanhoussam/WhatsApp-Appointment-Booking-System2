## A real gap found and fixed before verification (not silently shipped)

Investigating what A3.2/A4.2 needed to check surfaced a real, unverified assumption: A4.1 added a
new barber-selector chip row to Week, but never gated it behind `hideBarberPicker` the way Day's own
picker already was (Staff Scoped Access Phase D, 2026-08-09). Confirmed by reading
`app/api/v1/admin/reservations.py`'s `list_reservations` route directly:
`effective_barber_id = staff_barber_id if staff_barber_id is not None else barber_id` — a STAFF
caller's results are ALWAYS server-scoped to their own barberId, regardless of any client-supplied
selection. So a STAFF user selecting a different barber's chip in the new Week row would not leak
that barber's data (backend already prevents that), but it WOULD silently show an empty week
instead of any real data — the exact class of misleading UI Day's own picker was hidden to prevent.

**Fixed, same file A4.1 touched, before any verification claim was made**: added `hideBarberPicker`
prop to `ReservationsWeekCalendar.jsx`, gated the new chip row on `!hideBarberPicker`, and seeded
`weekVisibleBarberId`'s initial state in `ReservationsTab.jsx` to `myBarberId ?? null` (mirrors
Day's own `visibleBarberIds` seed) so Week still opens correctly narrowed to a STAFF user's own real
hours even with the picker hidden, instead of falling back to the pooled tenant-wide range.
