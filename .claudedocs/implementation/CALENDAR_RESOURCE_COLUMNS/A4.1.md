# Track A (Calendar) — Phase A4.1: Week View Planning Selector — Evidence (2026-08-22)

Implements Week's own recommendation from the reviewed and approved UX study
(`.claudedocs/work/calendar-uxui-study/2026-08-22/summary.md`, direction **W1**) — resolves A2.2's
own registered gap ("Week view still uses tenant-wide hours, not barber-specific") directly, not a
workaround. Scope, per Salman's explicit instruction: same design language as A3.1 (Day), Week
stays a planning view (density/day-columns), no drag-and-drop change, no new redesign.

## Change

One file's own logic + a small shared state addition, no backend, no schema, no DB change:

- **`ReservationsTab.jsx`** — new `weekVisibleBarberId` state (`null` = pooled/"الكل", the
  unchanged default; or one barber id). Single value, not a set like Day's `visibleBarberIds` —
  Week only ever narrows to one barber at a time, per the study's own W1 direction. Passed to
  `ReservationsWeekCalendar` as `weekVisibleBarberId`/`onWeekBarberChange`.
- **`ReservationsWeekCalendar.jsx`**:
  - New single-select chip row ("الكل (مجمّع)" + one chip per barber), same visual language as
    Day's own multi-select chips — one shared design vocabulary, different click semantics (single-
    select here, matching "Week narrows to one barber, Day shows several columns").
  - `startHour`/`endHour`: when one barber is selected, narrows to THEIR real hours (`barber.
    working_hours`, the exact same resolution A2.2 already proved correct) instead of the
    tenant-wide `hourRange` — this IS the direct fix for A2.2's registered gap, not a new
    mechanism: A2.2 could not do this because Week pooled every barber with no single one to
    resolve hours from; A4.1 removes that reason by giving Week a real single-barber selection.
    Pooled mode (`weekVisibleBarberId === null`) is unchanged — still the tenant-wide range, a
    real, accepted, named limitation of pooled mode specifically (nothing to narrow to when
    several barbers are shown at once), not a regression.
  - `byDay` now filters to the selected barber's own reservations when one is chosen; pooled mode
    unchanged (every barber, as before).
  - Quick Create (both the header button and empty-slot click) now pre-fills the selected barber
    when one is chosen — `barberId: weekVisibleBarberId ?? undefined`, same pattern Day's own click
    handler already established.
  - No change to drag-and-drop, the popover, or day navigation — Week's `over.id`-based day-column
    reassignment is untouched; a dragged card still only changes its day/time, never its barber
    (unaffected by this phase).

- **Quick Create pre-fill, narrowed mode**: clicking an empty cell while جعفر was selected opened a

### Side finding — pre-existing, NOT introduced by A4.1

In pooled ("الكل") mode, Quick Create's barber field was observed pre-filled with "حسين" rather
than left unset. Investigated immediately: this is `CreatePopover`'s own pre-existing internal
fallback (`reservationInteractions.jsx`: `useState(defaultBarberId || barbers[0]?.id || '')`) —
A4.1 correctly passes `barberId: undefined` in pooled mode (confirmed by reading the diff), and
this exact same `barbers[0]` fallback already fired before A4.1 existed (Week's header button never
passed a `defaultBarberId` prop at all until this phase). Not a regression, not touched — changing
`CreatePopover`'s own internal default is a separate, real, small UX decision (should pooled-mode
Create truly leave barber unset, forcing an explicit choice?) named here, not silently fixed
alongside an unrelated phase.
