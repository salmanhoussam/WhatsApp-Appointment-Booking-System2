## §١ — نتائجُ تحقيق P1

### P1-F1 · بوّابةُ ① لها **ثلاثةُ** مواضعِ نداءٍ فقط — نقطةُ اختناقٍ واحدة

| الموضع | السطر | السياق |

الثلاثةُ تنادي `_tenant_has_lia(client_id)`. ⇒ **الـvertical يسكن هنا، لا في مكانٍ رابع.**

### P1-F2 · `_resolve_actor` يعطي `client_id` ولا يعطي الـvertical

`_tenant_has_lia` يقرأ `clientservice` وحدَه. قراءةُ الـvertical تعني قراءةَ صفِّ `Client`.
تكلفةٌ إضافيّة: **استعلامٌ واحد لكلّ رسالة**، وهو مقبولٌ في مسارٍ يقرأ صفوفاً أكثرَ من ذلك بكثير.

### P1-F3 · النصفان يحتاجان **نصّين مختلفين** — والدالّةُ الحاليّة لا تستطيع التمييز

نصُّ ① اليوم: «خدمة الحجوزات مش مفعّلة على هالمحل.» — وهو **خطأٌ لرفضٍ سببُه الـvertical**:
عيادةٌ قد تحمل `reservations` فعّالةً تماماً. هذه حالةُ `text-context-rule` بحذافيرها.

⇒ الدالّةُ يجب أن تعيد **أيُّ نصفٍ سقط**، بنفس نمط `_authorise_operation` في الملفّ نفسِه
(*«Both are returned by name so the caller says which one fell rather than 'refused'»*).

### P1-F4 · 🔴 الفهرسُ وحدَه **يصنع** عطلاً يواجه الزبون

```python
# reservation_service.py — الحالي
except UniqueViolationError:
    raise ValueError("This barber is already booked for that time. Please choose a different time.")
```
```python

    raise HTTPException(status_code=409, detail=str(exc))   # ← مسارٌ عامّ
```

⇒ لحظةَ وجودِ فهرسٍ للمورد، **مريضُ عيادةٍ يُقال له إنّ حلّاقاً مشغول**، بنصٍّ يصل شاشتَه عبر
409 على نقطةٍ عامّة. **العطلُ يولد من التغيير نفسِه**، فيُصلَح في المرحلة نفسِها أو لا يُنفَّذ
التغيير.

### P1-F5 · ⚠️ الفهرسُ يُنشأ بأمان، **ولا يمكن إثباتُه حيّاً اليوم**

| الحقيقة | المصدر |

⇒ إثباتُ فهرسِ المورد حيّاً يحتاج حجزَ عيادةٍ حقيقيّاً ⇒ تينانتَ اختبار ⇒ **موافقةً منفصلة**.
**فـP1 تُغلق بإثباتٍ بنيويٍّ فقط** (الفهرسُ موجودٌ بالشرط الصحيح، مقروءاً من `pg_indexes`)،

> ولا يستطيع أن يُختبَر (صفرُ صفوفٍ تمرّ به).

## §٢ — التغيير الأوّل: Lia vertical allow-list

### ٢٫١ الشكل — **Option B، مُعتمَدٌ ٢٠٢٦-٠٩-٢٥**

> **`_tenant_has_lia` لا تُلمَس إطلاقاً.** لا إعادةَ تسمية، ولا فتحَ لجسر `lia OR reservations`.

```python
# app/services/lia_owner_entry.py

# ALLOW-LIST — لا deny-list. vertical غيرُ مذكورٍ هنا لا يصل Lia، ولا يسقط إلى الحلاقة.
# تُعدَّل بتغييرِ كودٍ مع سببٍ مُعلَن في رسالة الإيداع (repository-hygiene · Persona & Prompt Drift).
_LIA_VERTICALS = frozenset({"barber"})

async def _vertical_allows_lia(client_id: str) -> bool:
    """هل vertical هذا التينانت في قائمة السماح؟ دالّةٌ جديدةٌ مستقلّة تماماً.

    لا تقرأ `client_services` ولا تعرف شيئاً عن القدرات — وهذا هو المقصود: الفصلُ التامّ
    هو ما يضمن أنّ جسر `lia OR reservations` لا يُمَسّ."""
```

**ولماذا Option B بدل التوحيد** — والسببُ من القياس لا من الذوق: استعلامُ ٢٠٢٦-٠٩-٢٥ أثبت أنّ
`mr-h` و`alzabt-demo` يحملان `reservations` **بلا** `lia`. أي أنّ جسر `lia OR reservations`
**سلوكٌ حيٌّ لتينانتين حقيقيّين**. وأنظفُ ضمانةٍ لعدم كسره هي **ألّا تُفتَح الدالّةُ أصلاً** —
فتصير «الجسرُ سليم» خاصّيّةً بنيويّةً لا وعداً بمراجعة.

**والثمنُ المعلَن:** موضعُ نداءٍ رابعٌ مستقبليٌّ قد ينادي واحدةً وينسى الأخرى. يُغلَق بـ**FG-6**
(فحصُ AST يعدّ المواضع الثلاثة ويؤكّد النداءين والترتيب)، لا بالثقة.

### ٢٫٢ الترتيب: الـvertical **أوّلاً**، ثمّ `_tenant_has_lia`

```
في كلٍّ من المواضع الثلاثة، بهذا الترتيب حصراً:
    ①-a   _vertical_allows_lia(client_id)     ← الجديدة
    ①-b   _tenant_has_lia(client_id)          ← القائمة، بلا أيّ تغيير
```

كلاهما حقيقةٌ عن المحلّ لا عن الشخص، فلا ينطبق ترتيبُ «الأرخص أوّلاً». **الـvertical أوّلاً**
لأنّه الرفضُ الأصلب: vertical خارج القائمة **لا يمرّ أبداً**، بينما قدرةٌ غيرُ مفعّلةٍ قد تُفعَّل
غداً. وهذا يحلّ **F3** بلا فتحِ الجسر: `vertical_not_allowed` سببٌ مستقلٌّ يصدر من الدالّة
الجديدة، بينما فشلُ القدرة يبقى كما هو حرفيّاً بنصّه القائم.

### ٢٫٣ ماذا يصل المستخدم — لكلّ موضع

| الموضع | `lia_access_inactive` | `vertical_not_allowed` |
|---|---|---|
| **الترحيب** `:4619` | يسقط إلى مسار الزبون · **بلا نصّ** (سلوكٌ قائم) | **المعاملةُ نفسُها** — ولا تُخترَع صياغةٌ جديدة، تماماً كما ينصّ تعليقُ الموضع نفسِه |
| **إدخال البيانات** `:4698` | «خدمة الحجوزات مش مفعّلة على هالمحل.» (قائم) | 🆕 **نصٌّ جديد، يحتاج إقرارَك حرفيّاً** (٢٫٤) |
| **`_still_authorised`** `:2819` | `(False, "lia_access_inactive")` — قائم، بلا تغيير | `(False, "vertical_not_allowed")` — فرعٌ **جديدٌ يُضاف قبله**، والمنادي يصوغ |

**التدقيق:** حدثٌ جديد `lia_vertical_not_allowed` في `SecurityAuditLog` على مسار الإدخال، بنفس
شكل `lia_entry_refused` القائم. الترحيبُ لا يُدقَّق (لا شيءَ رُفض، سقوطٌ إلى مسارٍ آخر).

### ٢٫٤ 🔴 النصُّ الوحيدُ الذي يحتاج إقرارك حرفيّاً

يُضاف إلى `app/prompts/lia.md`، وإلى `_REQUIRED_REPLIES` (فيفشل الإقلاعُ إن نقص):

```
[[lia_vertical_unavailable]]
الإدخال عبر واتساب لسّا مش متاح لهالمحل. بتقدر تضيف من لوحة التحكّم.
```

**لماذا هذه الصياغة:** صادقةٌ (ليست «مش مفعّلة» وهي قد تكون مفعّلة) · لا تسرّب خارطةَ طريق
(لا تذكر «عيادة» ولا «حلاقة» ولا vertical) · تعطي مخرجاً حقيقيّاً · **بلا emoji** (قاعدةٌ ثابتة).

**بديلٌ إن لم تعجبك:** «لسّا ما فيّي ساعدك بالإدخال لهالمحل. الإضافة بتتمّ من لوحة التحكّم.»

### ٢٫٥ الطبقةُ الثانية — تأكيدٌ بنيويٌّ عند الكتابة

Lia تكتب `module_key="barber"` في `:2759` و`:3800`. يُضاف **تأكيدٌ** (assert/raise) عند كلّ
موضعِ كتابةٍ بأنّ vertical التينانت في `_LIA_VERTICALS` — لا ليحمي من مسارٍ قائم (البوّابةُ
تغطّيه)، بل ليمنع مساراً **مستقبليّاً** من الالتفاف عليها.

> النمطُ نفسُه الذي يوثّقه `create_reservation` لنفسه: *«provisioning prevents the state and the
> runtime detects it anyway»*.

## §٣ — التغيير الثاني: فهرسُ سباقِ المورد

### ٣٫١ الـmigration

`prisma/migrations/add_reservation_resource_slot_unique_index.sql` — **جديد**، يعكس ملفَّ الحلاق
حرفيّاً في الشكل والحدود:

```sql
CREATE UNIQUE INDEX IF NOT EXISTS reservations_active_resource_slot_uidx
ON reservations (client_id, resource_id, reserved_at)
WHERE status IN ('pending', 'confirmed', 'arrived') AND resource_id IS NOT NULL;
```

**ويحمل رأسَ التعليق نفسَه معدَّلاً:** غيرُ قابلٍ للتعبير في `@@unique` (لا دعمَ للفهارس الجزئيّة
في Prisma DSL) ⇒ SQL خام · **ولا يغلق تداخلاً بأوقاتِ بدءٍ مختلفة** (09:00-09:30 مقابل
09:15-09:45) — الحدُّ نفسُه المُعلَن في فهرس الحلاق، ويُعلَن هنا لا يُفترَض أنّه مفهوم.

**والملفُّ القائم للحلاق يذكر هذه المتابعةَ بنفسه** — فهذه ليست فكرةً جديدة، بل إغلاقُ بندٍ
مكتوبٍ منذ ٢٠٢٦-٠٨-٢٤.

### ٣٫٢ إصلاحُ P1-F4 — في المرحلة نفسِها، لا بعدها

```python
# reservation_service.py — بعد repo.create
except UniqueViolationError:
    if resource:
        raise ValueError("This resource is already booked for that time. Please choose a different time.")
    raise ValueError("This barber is already booked for that time. Please choose a different time.")
```

**الجملتان منسوختان حرفاً بحرفٍ من الفحصِ المسبَق فوقهما** — لا نصَّ جديد يُخترَع، وهو ما يوثّقه
الكودُ نفسُه كقاعدة: *«translated into the exact same customer-facing message the pre-check above
already gives»*. ⇒ **لا حاجةَ لإقرارِ نصٍّ هنا.**

**فالسؤال:** هل يحمل أيٌّ من الخمسة `reservations` أو `lia` **فعّالة**؟

```
إن كان الجواب لا   ⇒  السياجُ صفرُ تغييرٍ سلوكيٍّ على أيّ تينانتٍ حيّ.  ✅ ننفّذ كما هو.
إن كان الجواب نعم  ⇒  السياجُ يسحب وصولاً قائماً من تينانتٍ حيّ،
                      وهذا قرارُك أنت لا قرارُ عقدٍ تقنيّ.
```

**الاستعلامُ المطلوب — `SELECT` واحد، بالقارئ المختوم نفسِه:**

```sql
SELECT c.slug, c.vertical, cs.service_key, cs.is_active
FROM clients c JOIN client_services cs ON cs.client_id = c.id
WHERE cs.service_key IN ('lia','reservations') AND cs.is_active = true
ORDER BY c.slug;
```

## 🔒 تصحيحُ مفرداتٍ مُقَرّ (سلمان، ٢٠٢٦-٠٩-٢٥)

> **الـDDL كان Production mutation، ولو لم يكن data write.**

بما أنّ P1-B كان **يتطلّب** إنشاء الفهرس أصلاً، وطُلب دليلُ `pg_indexes`، فهو **داخل نطاق P1
بعد إذن التنفيذ**. ما يُثبَّت هنا هو الوصفُ لا الحكم:

```
❌  لا تُوصَف P1 مستقبلاً بأنّها «صفر production mutations»
✅  الوصفُ الصحيح: «صفر production DATA writes»  —  ٦٦/٦٦ صفّاً بلا حركة،
    ومعها production mutation واحدة من نوع DDL: فهرسٌ واحد، مُعلَنٌ ومقيسٌ وقابلٌ للتراجع
    بجملة DROP واحدة.
```

وهذه ليست تفصيلاً لغويّاً: تقريرٌ يقول «صفر mutations» عن مرحلةٍ غيّرت schema الإنتاج يصير
بعد سنةٍ ادّعاءً كاذباً في وثيقةٍ يُوثَق بها.
