# Track A (Calendar) — Phase A2.2: Barber-aware working-hours grid — Evidence (2026-08-21)

Fixes Finding 2 from the barber-production-readiness study
(`.claudedocs/work/barber-production-readiness-study/2026-08-21/summary.md`, Phase A1): the
Dashboard Calendar's Today view rendered a grid using the tenant-wide `Client.config.working_hours`
regardless of which barber's column was showing, offering slots the backend would reject for a
barber whose own hours are narrower (or otherwise different). Scope, per Salman's explicit
instruction: UI-only, no Settings/working-hours data changed, no backend validation touched unless
proven necessary — it wasn't.

## Source-of-truth investigation (done before any code change, as required)

Read `app/services/reservation_service.py` directly (not assumed) to confirm the real backend
resolution order for every write path that validates a reservation time
(`_check_working_hours()`, called from availability-slot generation, admin create, and reschedule):

1. `resource.workingHours` — only applies to Resource-backed module_keys (e.g. clinic). Never
   populated for `module_key='barber'`, confirmed by grep — no code path sets a `Resource` row for
   Barber reservations.
2. `barber.workingHours` — used whenever the reservation has a `barber_id` and that barber has a
   non-empty `workingHours` JSON set.
3. `client.config.working_hours` — fallback, only when neither of the above applies.

So for every real Barber-module tenant (mr-h, rk), the backend's actual authoritative source is
**the specific barber's own `working_hours`, falling back to the tenant-wide config only if that
barber has none set** — confirmed exactly, not inferred, from `reservation_service.py` lines
204-220 (create/reschedule path) and 322-338 (availability-slot generation).

Cross-checked the real data (read-only): mr-h's only barber "Ali" has `{09:00,18:00}` while the
tenant config says `{09:00,20:00}` — a real, live mismatch. rk's "جعفر" (Jaafar) has `{09:00,18:00}`
while the tenant config says `{09:00,21:00}`; rk's other barber "حسين" (Hussein) has
`{09:00,21:00}`, matching the tenant config exactly — a real case of one barber differing and one
not, at the same tenant, at the same time.

Traced how the Dashboard's own two calendar surfaces get their real barber context:

- **`ReservationsTodayView.jsx`** — confirmed via its own code and a direct comment
  ("barber at a time, switched via the pill control above, never multiple columns") that exactly
  ONE barber's reservations render at a time, selected via `visibleBarberId`
  (owned by `ReservationsTab.jsx`, passed down). This is unambiguous — there is always exactly one
  real "current barber" for this view's grid.
- **`ReservationsWeekCalendar.jsx`** — confirmed via its own `byDay` grouping that this view's
  columns are **days**, not barbers — every barber's reservations for a given day are pooled into
  one column. There is no single barber a grid boundary could correctly narrow to here without a
  real per-barber-lane redesign (out of scope: "no refactor").
- `GET /barbers/` (already fetched once per Dashboard session via the existing `useBarbers()` hook,
  reservationInteractions.jsx:61) already returns each barber's real `working_hours`
  (`app/api/v1/admin/barbers.py:79`, `_fmt()`'s shared serializer) — no new API call needed.

## Change — smallest safe fix, no refactor

Three files, additive/rewiring only:

- **`ReservationsTab.jsx`** — `parseHourLoose()` (already existed, used for the tenant-wide
  fallback) exported so it can be reused rather than duplicated.
- **`ReservationsTodayView.jsx`** — moved the existing `visibleBarber` lookup to the top of the
  component (was previously computed after all the hour-dependent hooks that needed it). Replaced
  the direct `const [startHour, endHour] = hourRange` with: use `visibleBarber.working_hours` when
  it has both `open_time`/`close_time` set and parses to a valid range, else fall back to the
  incoming `hourRange` prop (the tenant-wide default `ReservationsTab.jsx` already computes) —
  mirroring the backend's exact priority. Every downstream consumer of `startHour`/`endHour`
  (`quarters`, `hourMarks`, `nowIndex`, `handleEmptySlotClick`, `handleDragEnd`, `StaffColumn`
  rendering) is unchanged — only the *source* of the two numbers changed, not the mechanism.
- **`ReservationsWeekCalendar.jsx`** — no logic change; added a comment recording the deliberate
  decision to leave it on the tenant-wide range (see Registered Finding below).
- No backend file touched. No `Client.config.working_hours` or `Barber.workingHours` DB row
  touched by this change (temporary test reservations created for verification were cancelled
  afterward, see below — the working-hours *data* itself was never written to).

## Registered Finding — not fixed, out of scope

`ReservationsWeekCalendar.jsx`'s Week view still uses the tenant-wide `hourRange` for every day
column, regardless of which barbers have reservations that day. This is architecturally correct as
a *scope decision* (the view pools multiple barbers per column, so there is no single barber's
hours to narrow to without a real per-barber-lane redesign — out of "no refactor"), but it does mean
Week view can still visually offer a slot a specific barber's own hours wouldn't accept; the
backend correctly rejects it regardless (unaffected by this fix, always was, always will be until
Week itself is redesigned). A future Week-view redesign is the real fix for that surface — named
here, not solved.
