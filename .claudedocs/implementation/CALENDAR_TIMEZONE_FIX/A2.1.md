# Track A (Calendar) — Phase A2.1: Unify List-view time display — Evidence (2026-08-21)

Fixes Finding 5 from the barber-production-readiness study
(`.claudedocs/work/barber-production-readiness-study/2026-08-21/summary.md`, Phase A1): the same
real reservation displayed three different clock times across the Dashboard (Calendar 11:00, List
02:00 PM, Reschedule field 11:00). Scope, per Salman's explicit instruction: display-only fix, no
backend change, no working-hours logic touched, smallest correct architectural change.

## Documented convention this fix relies on (recorded before implementation, as required)

`reserved_at` is **not** a real UTC instant — it is the tenant's wall-clock appointment time written
directly into a UTC-typed database column, with no real timezone conversion anywhere in this
feature. This is the project's own existing, deliberate convention, documented in two places
already in the codebase before this fix touched anything:

- `app/services/reservation_service.py` — `_check_working_hours()`'s own comment: "All times
  treated as UTC directly."
- `frontend/src/pages/generic-admin/components/reservationInteractions.jsx:23-28` — `fmtTimeUTC()`'s
  own comment: "All UTC-field accessors, deliberately -- `reserved_at` values represent the
  tenant's wall-clock time directly with no real timezone conversion anywhere in this feature."

The Calendar (Week/Today) views and every reschedule/edit popover already read this correctly via
`fmtTimeUTC()` (`getUTCHours()`/`getUTCMinutes()` — raw digit read, no locale conversion). The one
place that disagreed was `ReservationsTab.jsx`'s own local `fmtTime()`, which used
`new Date(iso).toLocaleTimeString('ar-SA', ...)` with no timezone argument — letting the *browser's*
local zone (Beirut, UTC+3) convert the `Z`-suffixed ISO string, shifting the displayed time by 3
hours. The fix aligns the outlier to the already-established convention; it does not introduce a
new one.

## Side Finding (registered, not fixed — out of this step's scope)

`fmtDate()` (day formatting, same file) uses the same `toLocaleDateString` pattern without a
timezone argument. A reservation stored close to a UTC midnight boundary (e.g. `23:30`) would be
vulnerable to the identical class of bug shifting it to the wrong calendar day in the browser's
local zone. No real reservation in either tenant's data currently falls near that boundary, so this
was not observed or evidenced this pass — flagged for a future, separately-scoped check rather than
fixed speculatively here.
