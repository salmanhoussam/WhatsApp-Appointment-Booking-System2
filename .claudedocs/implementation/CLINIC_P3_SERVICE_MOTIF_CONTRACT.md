## §٠ — النطاق

### الفصلُ الذي يفرضه العقد

```
Service            ما يحجزه المريض  —  قائمٌ اليوم، لا يُلمَس
    name_ar / name_en · price · durationMin

Booking Contract   شروطُ إتاحته  —  يُضاف
    instructions      نصٌّ يُعرَض للمريض عند الحجز
    bookable_by       من يحقّ له أن يحجزه
```

**ولا كيانَ Motif ثانٍ.** السبب من الكود لا من الذوق: `Reservation.serviceId` هو مسارُ الكتابة
القائم، وكيانٌ ثانٍ يعني FK ثانياً قابلاً للإفراغ على `Reservation` — أي **طريقتين لتسمية الشيء
نفسه**، وهو ما يمنعه `rules/backend/architecture.md` §9.

**وسابقةٌ من الكود تسند التوسيع:** `CatalogService` يحمل أصلاً ثلاثةَ أعمدةِ إقامة
(`propertyId` · `pricingUnit` · `isIncluded`) موصوفةً في الـschema حرفيّاً بأنّها *«inert for an
appointment-style service»*، وكلُّ صفٍّ قائمٍ صحيحٌ بـNULL بلا backfill. التوسيعُ ليس سابقةً جديدة.

### ما **لا** تفعله P3

| | |
|---|---|
| **`patient_category`** | **خارجٌ بقرارِ Q1 المعدَّل.** لا يدخل إلّا بدليلٍ واحدٍ بعينه: عيادةٌ حقيقيّةٌ تقول إنّها ترفض **مرضى جدداً** لخدمةٍ بعينها، **مع** بيان كيف تعرّف «الجديد» |
| «استشارة أولى» و«متابعة» | **خدمتان منفصلتان في v1** لهما اسمان ومدّتان وسعران. هذا يغطّي الحاجة التشغيليّة بالكامل؛ المؤجَّلُ هو **الرفض** لا **التسمية** |
| نوافذُ الحجز (أدنى مهلة · أقصى أفق) | **C2.4 — تنتمي إلى التوفّر (C4)، لا إلى الخدمة.** وأين تسكن قيمتُها UNKNOWN (U3) |
| التوفّر · `ResourceService` · الواجهة · تدفّقاتُ الحجز | P4 / P5 / P6 / P7 |
| أيُّ لمسٍ لـPatient أو Customer أو Barber أو Lia | — |

### 🔒 لا قناةَ واتساب في P3 — مُقَرٌّ ٢٠٢٦-٠٩-٢٥

> **«P3 يعرّف Service/Motif contract داخل الدومين، مش عم يبني قناة WhatsApp نفسها.»**

#### تمييزٌ يُثبَّت لئلّا يُخلَط مرّةً أخرى

```
Template                    رسالةٌ استباقيّةٌ من النظام إلى التاجر، خارج المحادثة
                            (new_reservation_alert). تحتاج إقرارَ Meta.

Interactive session flow    أزرارٌ وقوائمُ داخلَ محادثةٍ قائمة.
                            ليست قالباً، ولا تحتاج واحداً.
```

**فلا يُضاف قالبٌ لمجرّد أنّنا نريد أزراراً داخل تدفّق الحجز.** الاثنان موضوعان مختلفان.

#### والتدفّقُ نفسُه مكانُه P6، والسببُ تسلسليّ

```
Service/Motif → Patient → Doctor/Resource → Date → Slot → Patient details → Confirmation
```

كلُّ خطوةٍ منها تقف على عقدٍ لم يُغلَق بعد: **الهويّة** من P2 ✅ · **الخدمة/الشروط** من P3 ✅ ·
**توفّرُ المورد** من P4 ⏸️ · **سلوكُ الموقع** من P5 ⏸️.

> **ولو بُنيت الأزرارُ الآن، لَأُعيدت كتابتُها مع كلّ قرارٍ في P4 وP5.** وهذا هو سببُ الترتيب،
> لا تفضيلٌ إجرائيّ.

**الترتيبُ المُقَرّ:** P3 العقد · P4 التوفّر (الطبيبُ يعرض أوقاتاً فعلاً) · P5 الموقع (يُثبَّت
العقدُ بلا تعقيد واتساب) · P6 واتساب فوق أربعةِ عقودٍ ثابتة.

#### ما أُثبت في P3 المنفَّذة — قياساً لا ادّعاءً

```
ملفّاتُ واتساب التي لمستها P3        : صفر
أسطرٌ تذكر زرّاً أو قائمةً أو قالباً   : صفر   (send_interactive · button · list_reply · template · wamid)
```

#### وحقيقةٌ واحدةٌ محفوظةٌ لـP6 — مقيسةٌ عندنا، لا ادّعاءٌ عن سياسة Meta

`reservation_service.py:732` و`:818` يسجّلان قياسَنا نحن: **قائمةُ واتساب التفاعليّة تحمل ١٠
صفوفاً إجمالاً عبر كلّ الأقسام**، وقد قِيست على التينانتات الثلاثة الحقيقيّة. هذه ملاحظةٌ لتصميم
P6، **ولا يُدَّعى فيها شيءٌ عن سياسةِ القوالب أو نافذةِ الـ٢٤ ساعة** — ولا مصدرَ رسميٌّ متاحٌ
الآن، فلا يُكتب ما لا يُسنَد.

## §١ — الشكلُ المقترَح

### عمودان على `CatalogService`

| العمود | النوع | الافتراضيّ | خاملٌ عند الحلاق |
|---|---|---|---|
| `instructions` | `String?` | `NULL` | نعم — `NULL` هو المعنى الصحيح، لا حشو |
| `bookableBy` | `String` | **`"patients"`** | نعم — الافتراضيُّ يعيد السلوك **حرفيّاً** |

`bookableBy` نصٌّ بقيمٍ موثَّقة (`"patients"` · `"staff_only"`)، **لا enum في قاعدة البيانات** —
عرفُ هذا الـschema نفسِه على `Reservation.source` و`Resource.type` و`Client.vertical`.

**والقيمةُ الثالثةُ عند Doctolib لا تُنقَل:** «par adressage» (بإحالةِ زميل) تفترض **مفهومَ
إحالةٍ لا نملكه إطلاقاً**؛ إضافتُها تنتج فرعاً لا أحد يستطيع بلوغَه.

### الأثرُ المقيس

`CatalogService` يحمل **٣٨ صفّاً (٣٧ فعّالة)** على الإنتاج (P0.5). كلُّها تصير
`instructions = NULL` و`bookable_by = 'patients'` ⇒ **صفرُ تغييرٍ سلوكيّ، وصفرُ backfill.**

## §٢ — أين يُنفَّذ `bookable_by` — وهو القرارُ الحقيقيُّ في P3

### الموضع

في **`reservation_service.create_reservation`** وحدَه — القدرةُ الواحدةُ ومسارُ الكتابة الواحد
(§9). لا في المسار العامّ، ولا مكرَّراً في اثنين.

### كيف يعرف **مَن** يسأل

بـ`source`، وهو موجودٌ ومضبوطٌ في كلّ مُنادٍ حقيقيّ اليوم:

```
"website"  · "whatsapp"   ⇒  مريضٌ/زبون   ⇒  يخضع لـbookable_by
"admin"    · "lia"        ⇒  موظّف/مالك   ⇒  لا يخضع
None                      ⇒  يُعامَل معاملةَ الموظّف  ← قرارٌ صريح، انظر أدناه
```

**`source = None` تُعامَل كموظّف عن قصد، ويُقال السبب:** المنادي الوحيدُ الذي قد يتركها فارغةً
هو سكربتٌ أو تكاملٌ داخليّ — والمسارات الأربعة الحقيقيّة كلُّها تمرّرها
(`public/reservations.py` → `"website"` · `whatsapp_reservation_flow.py:893` → `"whatsapp"` ·
`admin/reservations.py:334` → `"admin"` · Lia → `"lia"`). **قائمةُ سماحٍ للخضوع**
(`source in {"website","whatsapp"}`)، لا قائمةُ منع — فقناةٌ جديدةٌ تُضاف غداً **لا تخضع
تلقائيّاً** حتّى تُذكَر، وهو الاتّجاه الآمن هنا: الخطأُ يميل إلى «موظّفٌ يستطيع» لا إلى «مريضٌ
يُمنَع بلا قرار».

### 🔴 وهذا تغييرُ سلوكٍ على خدمةٍ مشتركة — يُقال صراحةً

`create_reservation` تخدم الحلاقةَ أيضاً. الافتراضيُّ `"patients"` يجعل الأثرَ **صفراً على
الـ٣٨ صفّاً القائمة**، لكنّ **العقد نفسَه اتّسع**: صار للخدمة رأيٌ في من يحجزها. يُسجَّل
كـTRANSITION مثل `allow_past` و`status` قبله، لا كتفصيل.

## §٥ — الهجرة والتراجع

```
ALTER TABLE catalog_services ADD COLUMN instructions  TEXT;
ALTER TABLE catalog_services ADD COLUMN bookable_by   TEXT NOT NULL DEFAULT 'patients';
```

| | |
|---|---|
| صفوفٌ تتأثّر | **صفر منطقيّاً** — ٣٨ صفّاً تأخذ `NULL` و`'patients'`، وهما معناهما الصحيح |
| backfill | لا شيء يُكتب بغير الافتراضيّ |
| التراجع | `DROP COLUMN` ×٢ · و`git revert`. **صفرُ فقدانِ بيانات** |
| القواعد | ❌ `prisma db push` · ✅ `migrate diff` ⇒ مراجعةٌ بالعين ⇒ SQL صريح · migration واحدة |
