### E. Proposed storage/URL architecture

**Existing abstractions found in this codebase, inspected before proposing anything new:**

1. **`frontend/public/assets/alzabt/`** — a plain Vite static-asset folder, **already the exact
   precedent for this exact page**: it currently holds `dashboard.png` and `booking-page.png`, the
   two real-tenant screenshots the Contract explicitly forbids (left on disk, untouched, per the
   2026-08-26 Contract's own instruction not to delete them without separate approval). This is a
   plain static-file mechanism — no database row, no upload flow, just a git-tracked file served by
   Vite at a stable path (`/assets/alzabt/<filename>`), browser-cached like any static asset.
2. **`GalleryImage` (Prisma model) + `app/services/storage_service.py`** — the project's real
   tenant-media abstraction: Supabase Storage bucket `properties`, path convention
   `{clientId-scoped slug}/...` (per `.claude/rules/storage-tenant.md`), admin-authenticated upload
   flow, DB row per asset (`imageType`, `url`, `altText`, `sort_order`, etc.). **This is
   tenant-scoped by design** (`GalleryImage.clientId` is required, FK to `Client`) — confirmed no
   `Client` row exists for "Alzabt the marketing product" itself (the platform homepage isn't a
   tenant; `alzabt-demo` is a separate, real, isolated tenant used only for the live demo booking
   flow, unrelated to this marketing page). Forcing platform-marketing assets through this
   tenant-scoped pipeline would mean inventing a fake tenant just to hang images off of — exactly
   the kind of new-system-invention the brief asked to avoid.

**Recommendation: reuse abstraction #1, do not touch #2.**

- Any future real static asset for this page belongs in **`frontend/public/assets/alzabt/`**,
  git-tracked, served at a stable path (`/assets/alzabt/<descriptive-name>.<ext>`), exactly the
  mechanism already in place — just populated with new, Alzabt-native, Contract-compliant content
  instead of the two forbidden files currently sitting there.
- **No database table is proposed** for these assets. They are not tenant data, not currently
  editable through any admin/dashboard UI, and the page today needs zero of them (0 `<img>` tags,
  by design). Adding a DB-backed manifest for assets that don't exist yet and aren't user-editable
  would be exactly the kind of premature abstraction `rules/team-roles.md`'s Abstraction Rule
  warns against — "extract a shared abstraction only after at least two independently implemented
  production use cases demonstrate the same stable behavior," and there is currently **zero** real
  use case, not two.
- `ProductShowcaseHome.jsx` would consume any future real asset the same way `AlzabtLandingPage.jsx`
  already does today (`src="/assets/alzabt/<file>"`) — a stable, absolute, static path, never a
  database query, never a binary embedded in page source.
- **If** a real future need appears for marketing assets to be swappable without a frontend deploy
  (e.g., Salman wants to update a hero image himself without asking for a code change) — that is a
  genuinely different requirement (a lightweight marketing-CMS, not tenant media) and should be its
  own explicitly-approved decision, not something this pass builds preemptively.

**Proposed manifest structure** (documentation-only artifact for this Asset Map, not a DB table —
see above for why no table is proposed; this is the tracking shape to use in this Markdown file and
any future PR description, so every asset's provenance stays traceable):

| Field | Meaning |
|---|---|
| `asset_id` | short slug, e.g. `hero-dashboard-01` |
| `section` | one of the 11 section names in §2 |
| `role` | e.g. `hero-laptop-screen`, `whatsapp-chat-tile` |
| `source_file` | which of the 9 `new-matirial/alzabt/` files (if any) inspired it, or `none — built from Contract copy only` |
| `final_asset_path_or_url` | `/assets/alzabt/<file>` once a real file exists, or `n/a — CSS/SVG component` for everything currently live |
| `alt_text` | Arabic alt text, required the moment any real `<img>` is introduced (none exist today) |
| `status` | `live-css`, `reference-only`, `rejected`, `needs-recreation` |

Applied to the current real state, every one of the 11 sections' rows would read
`status: live-css`, `final_asset_path_or_url: n/a — CSS/SVG component` — there is nothing to fill
in as a pending asset row today.
