## 🔴 FINDING الثاني — وهو الأهمّ: `allow_past=False` **تضييقٌ لا حفاظ**

أمرُك جمع شرطَين، وهما متوافقان لأحدِ المُعامِلَين ومتوتّران للآخر:

| | السلوكُ الحاليُّ **للخدمة** (مقيس) | الافتراضُ المطلوب | الحكم |
|---|---|---|---|
| `notify_merchant` | يُشعِر **دائماً وبلا شرط** | `True` | ✅ **حفاظٌ تامّ** — والقياسُ يؤكّده (`1 call`) |
| `allow_past` | **يقبل الماضي** (لا حارسَ داخلها) | `False` | 🔴 **تضييق** — الخدمةُ ستبدأ ترفض ما تقبله اليوم |

**ولماذا هو آمنٌ عمليّاً رغم ذلك:** المستدعون الثلاثةُ **كلُّهم يرفضون الماضيَ قبل النداء**
(الإداريُّ والعامُّ بمقارنةٍ صريحة، والواتسابيُّ **بنيويّاً** لأنّه لا يعرض خانةً ماضيةً أصلاً).
⇒ **فلا يتغيّر سلوكُ أيِّ مستدعٍ قائم**، ويتغيّر سلوكُ **الخدمةِ نفسِها**.

```
⇒ الصياغةُ الدقيقة:  «الافتراضاتُ تحفظ سلوكَ المستدعين الثلاثة»
   وليست:            «الافتراضاتُ تحفظ سلوكَ الخدمة»
```

وهذا فرقٌ يجب أن تُقرّه أنت لا أن أُمرّره: **تضييقُ عقدٍ عامٍّ قرارٌ**، حتى حين لا يشعر به أحد.
🟢 **وأراه متوافقاً مع نيّتك** (R-4: *«allow_past=False يكون الحاجز الصريح في service»*) — لكنّي
أسمّيه تضييقاً لا حفاظاً.

## الدليلُ المُثبَّت (خطُّ الأساس)

### ١ · التوقيعُ اليوم

```python
create_reservation(client_id, module_key, customer_name, customer_phone, reserved_at,
                   duration_min, notes, metadata, customer_email=None, source=None)
```

```
عشرةُ مُعامِلات · واثنان فقط لهما افتراضٌ وكلاهما None
allow_past       ❌ غيرُ موجود
notify_merchant  ❌ غيرُ موجود
```

### ٢ · المستدعون — **ثلاثةٌ بالضبط**، محسوبةً كنداءاتٍ لا كنصّ

```
app/services/whatsapp_reservation_flow.py:884
app/api/v1/admin/reservations.py:324
app/api/v1/public/reservations.py:83
```

🔬 **والعدُّ الأوّلُ عندي قال ستّة**، لأنّ الـregex طابَق `async def create_reservation(` في
المسارِ الإداريِّ وفي الخدمةِ نفسِها. **والتعريفُ ليس مستدعياً.** صُحِّح بالتحليلِ الشجريّ.

والمفاتيحُ المُمرَّرة، مُثبَّتةً حرفيّاً:

```
الإداريُّ والعامُّ   ١٠ مفاتيح  (فيها customer_email)
الواتسابيُّ          ٩ مفاتيح   (بلا customer_email)
ولا واحدٌ منهم يمرّر أيّاً من المُعامِلَين الجديدَين اليوم
```

### ٣ · الحُرّاس — مُحلَّلةً لا مقروءة

```
الإداريّ    ✅ يقارن reserved_at بـnow() فعلاً
العامّ      ✅ مثلُه
الواتسابيّ  🔴 **لا مقارنةَ عنده إطلاقاً** — حارسُه **بنيويّ**: الخاناتُ من get_next_open_days
الخدمة     🔴 جسمُ create_reservation لا يذكر now() أبداً  ⇒ **وهذا هو أساسُ الشريحةِ كلِّها**
```

⇒ **وأثرُ هذا على T3-b:** الواتسابيُّ لن يحتاج تمريرَ `allow_past=False` ليُحفَظ سلوكُه؛ الافتراضُ
يكفيه. لكنّه **يفقد حمايتَه البنيويّةَ لحظةَ أن يُعرَض عليه مصدرُ تاريخٍ آخر** — يُسجَّل ولا يُفتَح.

### ٤ · السلوكُ الحقيقيُّ اليوم (بالدالّةِ الحقيقيّة)

```
ماضٍ      ✅ يُقبَل · ويُشعِر التاجر (1 call) · status=pending
مستقبلٌ    ✅ يُقبَل · ويُشعِر التاجر (1 call) · status=pending
⇒ لا فرقَ في المعاملةِ اليومَ بين ماضٍ ومستقبل — وهذا بالضبط ما تُدخِله T3-b
```

## المواصفةُ المقترَحةُ لـT3-b — للمراجعةِ، ولم تُكتَب

```python
async def create_reservation(
    client_id, module_key, customer_name, customer_phone, reserved_at,
    duration_min, notes, metadata, customer_email=None, source=None,
    *,                                   # الجديدان keyword-only: لا مستدعيَ موضعيٍّ يُكسَر
    allow_past: bool = False,            # 🔴 تضييقٌ مُقَرّ (R-4)
    notify_merchant: bool = True,        # ✅ حفاظٌ مقيس
) -> dict:
```

وموضعُ الفحصَين، بلا غموض:

```
allow_past       في مرحلةِ **Validate**، قبل حلِّ المورد — فالرفضُ يسبق كلَّ قراءةٍ للقاعدة
                 `if not allow_past and reserved_at < datetime.now().replace(tzinfo=utc):`
                 **بنفسِ صيغةِ الـroutes حرفيّاً** — وإلّا اختلف حارسانِ يفترضُ الناسُ تطابقَهما

notify_merchant  حول نداءِ Post Actions وحدَه:
                 `if notify_merchant: await _notify_merchant_new_reservation(reservation)`
                 ولا يُمَسّ _notify_reservation_event (فهو للزبونِ وعلى تغيّرِ الحالة، لا هنا)
```

**ولا يُمَسّ أيُّ route في T3-b:** الحُرّاسُ الثلاثةُ يبقون كما هم. تكرارُهم مع الحارسِ الجديدِ
مقصود: الـroute يردّ **400** برسالةٍ للمستخدم، والخدمةُ ترفع **ValueError** كدفاعٍ ثانٍ — وهو نفسُ
النمطِ الذي أقرّه سلمان في `a3-PR` («التقديمُ يمنع الحالة، والتشغيلُ يكشفها أيضاً»).
