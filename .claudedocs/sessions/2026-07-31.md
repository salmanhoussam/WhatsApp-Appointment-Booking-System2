## 🔧 Architectural Decisions Ratified

1. **`services.py`'s real domain, confirmed by code, not assumed**: `service_repo` has zero
   callers besides `admin/services.py`; `create_service` auto-assigns `propertyId`. Confirmed
   Clinic/Barber's `Service` rows never go through this route (seeded directly). Write ownership:
   `MANAGER_UNITS`. Read: `+MANAGER_RESERVATIONS` (Salman's point that a reservations manager may
   need visibility, applied as read-only rather than write, since the file's real scope is
   property/unit add-ons, not a Clinic-services admin surface — which doesn't exist yet).
2. **`dashboard.py` stays `MANAGER_RESERVATIONS`-only, `MANAGER_UNITS` excluded** — confirmed by
   reading the actual response bodies: both endpoints bundle revenue figures and customer PII with
   occupancy data in one non-separable payload. Per Salman's own Least Privilege principle: an
   occupancy-only need gets a new narrow endpoint later, not a widened mixed one now.
3. **`upload.py` stays conservative (`SUPER_ADMIN`/`TENANT_ADMIN` only)** — no dedicated
   catalog/content role exists; the endpoint spans unit/catalog/page contexts with no single
   natural owner among current roles.
4. **`restaurant.py`/`store.py` folded into Authorization Hardening, not treated as a new
   initiative** — same gap class, found while finishing this one, fixed in the same pass.
5. **No Reservation Strategy work this session** — architecture for that capability is closed per
   2026-07-31's earlier decision; today's Barber work was execution + comparison + a bounded
   extraction decision, not new design.
