## Part 2 — Beit Al Fakhar Store: Full Flow, Checkout Bug, Product Page, Showroom Checkout, Store Experience Review

Triggered by Salman's explicit push-back that "the API works" is not the same as "the feature
works," and his instruction to run a real Phase 0 Runtime Validation of the entire store flow
before any redesign work began — directly invoking the Investigation Protocol's two new
principles (added in this same Part): **Runtime Before Assumption** (backend success ≠ feature
success; verification traces `Data → Transformation → State update → Render → Visible UI`) and
**Independent Causes Are Allowed** (a single symptom can have more than one real, unrelated cause).

### Phase 0 — Runtime Validation (commit `e5e8baa`)

A real headless-Chrome + Chrome DevTools Protocol walkthrough of the entire store flow (no
Playwright/Puppeteer installed — a real `google-chrome` binary was driven directly over its raw
CDP websocket). Found a real checkout bug: `POST /store/orders` failed with a `500`.

### Phase 1 — Root Cause and Fix (commit `78f9635`)

Empirical bisection (6 cases) disproved the first theory (scalar `clientId` mixed with a nested
`items: {create: [...]}` relation write) and found the real cause: Prisma's Python client rejects
an explicit `None` for the `Json?` field `shippingAddress` — unrelated to the `items` relation at
all. Fixed in `app/repositories/store_repo.py` by omitting the key entirely when absent, wrapping
it in `Json(...)` when present, matching the pattern already used elsewhere in the codebase. The
wrong first theory was corrected **publicly**, in an appended section of the Phase 0 report, not
silently edited — praised explicitly by Salman for handling it this way.

### Phase 2 — Premium Product Experience (commit `a3043e7`)

Built per Salman's 6 pre-JSX requirements (study the tenant's identity as a gallery, not a
webshop; study the full journey; produce a wireframe before implementing; the image is the hero,
never the price/button; future-proof the content model; reuse cart logic, never reinvent it) plus
9 refinements to the wireframe (never hide the price — "السعر يُحدد حسب الطلب" instead; a short
Story line above the description; Add to Cart visually secondary; "قد يعجبك أيضاً" instead of
"Related Products"; a gallery-style breadcrumb; never crop the hero image by default; the design
must work with empty `metadata`; three handmade/hand-painted/one-of-a-kind badges; a graceful
"image not available" state). Validated via real CDP walkthrough, catching and fixing two of my
own mistakes before shipping: a Rules-of-Hooks violation, and a first draft that hardcoded
tenant-specific story text inside the *shared* `_fmt_product()` endpoint (moved to the
tenant-specific frontend file instead, since that endpoint also serves footlab).

### Phase 3 — Showroom Checkout Experience (commit `1070e88`)

Renamed by Salman from "Premium Checkout" — "the page is no longer just a checkout, it's the last
room inside Beit Al Fakhar's gallery" — with 9 requirements (60/40 showroom/form split, not 50/50;
the form panel opens with a real heading and sentence, not abrupt fields; a warmer order-summary
heading; the WhatsApp button in the tenant's own accent color, never stock green, with a real
Spinner → Create Order → THEN open WhatsApp sequence; a toast instead of a separate success
screen; no repeated long product info in the summary panel; the same "السعر يُحدد حسب الطلب"
phrasing reused verbatim for consistency). An apparent 20-second "hang" found during validation was
investigated with real server-log timing correlation rather than assumed fixed or broken — it
turned out to be ~25–40 seconds of genuine Supabase pooler latency across two sequential requests,
not a code bug; `window.open` was confirmed firing correctly with the exact right WhatsApp number
and message once given enough time to observe it.

### Store Experience Review (commit `e75615e`)

A real, clean-cart, user-eyes (not programmer-eyes) CDP walkthrough of Home → Collection → Product
→ Add to Cart → Showroom Checkout, per Salman's explicit request as the gate before beit-al-fakhar
could be considered for reference-template status. Along the way, caught and fixed my own
test-harness bug (9 stale background Chrome tabs left open across the day's testing, all sharing
the same origin's `localStorage` and overwriting each other's cart state).

**Results and architectural decisions**: the built architecture holds up — all of Phase 2 and
Phase 3's requirements are visibly correct in the running app, confirmed via real screenshots, not
assumed from source. Two real, named gaps were found, and both turned out to be **content**, not
**architecture**: the hero video's real footage doesn't show the craft itself (an alley/doorway
shot, not a ceramic piece), and every product title is a generic sequential number ("طبق فخار
مرسوم يدوياً رقم 1–8"), which undercuts the page's own "no two pieces are identical" story copy.
Neither required touching `ProductPage.jsx`, `CheckoutPage.jsx`, or any of their supporting
components. This distinction — a real Store working correctly, but needing a human, not a
developer, to keep it looking finished — is the exact thread that led into Part 3.

## Part 3 — Dashboard → Tenant OS: the Architecture Plan's Full Evolution

Salman's framing at the start of this Part: the two content gaps just found in Part 2 would
recur, tenant after tenant, forever, unless clients could genuinely self-manage their own content
— and that this shift ("building the product every client uses to run their own store," not "a
Store") was one of the most sensitive turns in the whole project. What follows is six real,
separate revisions of one evolving document, `.claudedocs/architecture/TENANT_OS_PLAN.md`
(originally `TENANT_SELF_SERVICE_DASHBOARD_PLAN.md`) — design-only throughout: no code, no UI, no
new API, no schema, at every single revision.

**Draft 1** (commit `387178f`) — real investigation first (a dedicated research pass read
`GenericAdminDashboard.jsx`, `SmarAdminDashboard.jsx`, `CanvasPageEditor.jsx`,
`scripts/data/page_templates/*.json`, and the real Prisma fields), then a first plan: a Content vs
Structure boundary, a per-module Content Ownership Matrix, Live Preview, "No API Thinking," Theme
boundaries, a Service Contracts recommendation, and a reserved placeholder for future AI
integration.

**Draft 2** (commit `591214a`) — Salman corrected the two-way Content-vs-Structure split into
three explicit layers: **Platform** (developer-only, never touched), **Template** (developer-owned
by default, narrow curated exceptions), **Content** (tenant-owned, fully). Added the **Dashboard
First Principle** — every future feature must answer "how will the client edit this a month from
now?" — and reframed the deliverable as a **Content OS** (Notion/Shopify/Framer-style direct
manipulation, not a form-based admin panel), plus recorded the Client Journey Audit as the
recommended next gate, explicitly deferred.

**Draft 3** (commit `dac9a3a`) — Salman held the sequencing: no Client Journey Audit yet, since
without defined capability boundaries it would only produce a list of what's missing. Added seven
**Capability Contracts** (Catalog, Category, Media, Theme, Content, Orders, Customers, each with a
verified real-vs-Gap sub-capability list) and the **Capability Matrix** (Client/AI columns,
Developer omitted as trivially unrestricted) as the stated "golden reference" for future
AI-assistant permission scoping. Surfaced two new real findings while writing the Customers
Capability: its route file is never mounted, and its endpoints take an unguarded `client_id` query
parameter.

**Draft 4** (commit `0a8bdce`) — renamed the document from "Dashboard" to **Tenant OS**: the
Dashboard is one interface among several (Dashboard, AI, Mobile, API) onto a set of
interface-agnostic Capabilities, never the product itself. Added an eighth Capability, **Site
Configuration** (broader than Theme — brand, WhatsApp, email, currency real today; domain,
timezone, tax, languages, delivery, analytics, integrations named as real Gaps, cross-referenced
against `service-system.md`'s already-Planned serviceKeys). Added the **Single Source of Truth
Matrix**, ranked above the Capability Matrix per Salman's explicit instruction that it's the most
important table in the plan — building it honestly surfaced two serious real findings: `store.py`
and `restaurant.py` both perform full `CatalogItem`/`CatalogCategory` CRUD by calling
`admin_catalog_repo` directly, bypassing `catalog_service.py` entirely (a live violation on the
same tables `catalog.py` correctly routes through a Service for), and a systemic pattern of admin
routes skipping the Services layer to call Repositories directly from Routes.

**Draft 5** (commit `b083060`) — Salman corrected the anatomy again: Capability is not the top of
the tree, it's one of three siblings — **Capability / Interface / Governance**. Named a
**Governance** layer that hadn't existed before (Permissions, Draft/Publish, Audit, Versioning,
Activity) as cross-cutting concerns built once and inherited by every Capability, never
re-implemented per domain — with a real finding that `SecurityAuditLog` already has the right
shape for Audit but is used today only for security/system events, not tenant content activity.
Added **Design Principle 5**, the project's proposed constitution line: *"One Capability. One
Contract. One Service. One Source of Truth. Many Interfaces."* Reclassified every Architecture
Integrity Finding into exactly one of three named types — **Broken** (a Service exists, the Route
bypasses it), **Missing** (no Service exists at all), **Duplicate** (multiple independent write
paths to the same data) — which required re-verifying several write paths individually: Settings
and Units are Broken (real services exist, unused); Gallery, Team, and Store/Restaurant Orders are
Missing (no service exists at all, confirmed against the full `app/services/` listing); Products/
Categories and a frontend `PageBuilderTab`/`CanvasPageEditor` pair are Duplicate.

**Draft 6** (commit `d9dce12`) — added **Capability Lifecycle** (Idea → Contract → Implementation
→ Interface → Governance → AI Access → Review), applied honestly to Catalog — this project's
single most built-out Capability — showing it's only roughly a third of the way through. Added
**Capability Maturity** (Reserved/Experimental/Developing/Stable/Mature) applied to every real
Capability, so "Customers exists" became "Customers is Experimental." Added **Capability
Acceptance Criteria** — a 9-item checklist (Dashboard/AI/API/Validation/Audit/Activity/
Permissions/Draft-Publish/Documentation) scored honestly for Catalog: **4.5/9, ≈50%**, computed
transparently rather than adopting an illustrative percentage. Elevated Design Principle 5 to a
platform-wide rule.

**Draft 7** (commit `021a7c9`) — added **Capability Proposal**, a five-question Product Governance
gate (what problem, for whom; new Capability or extension; does more than one Interface need it;
what is the Source of Truth; how does the *client* measure success) every future Capability must
pass before a Contract is written — deliberately not a fourth branch of the anatomy, the admission
gate that precedes it. Applied retroactively to Catalog as a sanity check; it passed cleanly.
Added the **Capability Health Dashboard** — Catalog's score turned into a progress bar plus a
per-stage readout, with every other real Capability given an explicitly-approximate bar rather
than invented precision. Recorded Salman's framing of this project's three **backbone documents**
(Service Execution Constitution, Backend Architecture Rules, this document).

## Part 4 — Architecture Governance Outcomes

- **The constitution line moved to Backend Architecture Rules** — `.claude/rules/backend/
  architecture.md` gained a new §9, "One Capability, One Service, Many Interfaces," elevating the
  principle to apply platform-wide (Booking, Restaurant, Store, AI, any future Plugin), not just
  the Tenant OS's own scope — deliberately placed there rather than in
  `service-execution-constitution.md`, which already owns a different, disambiguated meaning of
  "Service" (autonomous agents like `tenant-seeder`); adding it there would have re-introduced
  exactly the term collision this plan spent several revisions avoiding.
- **Architecture Integrity Findings formally documented** — 7 findings, each classified as Broken,
  Missing, or Duplicate, none fixed (all named and evidenced, left for a future Implementation
  Contract).
- **Three backbone documents identified** — `service-execution-constitution.md` (how
  Services/Agents operate), `backend/architecture.md` (how the system is technically written),
  and `TENANT_OS_PLAN.md` (how an idea becomes a Capability usable across every Interface).
- **Phase 2.5 and Phase 4 added to the Rollout Phases** — Phase 2.5, formal adoption of the
  document as Reference Architecture, sits between "the contract is written" and "implementation
  begins"; Phase 4, the Client Journey Audit, was moved to *after* a first real batch of
  Capabilities is built against the reference, not immediately after review.
