## 🔬 Investigation Rounds — `experiments/rk-barber-story-lab/`

This is the real substance of the day. Salman's own framing: "the lab succeeded in validating the
rendering engine, but it didn't validate the user experience we're trying to build" — three
distinct, increasingly precise rounds followed that same discipline (investigate → build real
prototype → verify with instrumented evidence → report, never assert without evidence):

- **Round 1** (original casual footage): compared 4 rendering techniques (canvas 77/230 frames,
  native continuous seek, hybrid native play/pause) with real measured payload sizes, operation
  counts, and seek-latency data. Conclusion: none were the real problem — the source footage
  (undeliberate phone pan, real motion blur confirmed by direct frame inspection) was the ceiling.
- **Round 2** (new CapCut-edited footage, `new-matirial/barbershop_genuine.mp4`): same 4 techniques
  re-tested on calmer footage, this time also on a real mobile viewport (390×844 @2x) per Salman's
  own note that the footage is mobile-framed. Zero console errors across every combination; real
  screenshots confirmed a genuinely premium-looking result. Also fixed a real oversight: Cairo was
  referenced in CSS but never loaded — added a real Google Fonts link.
- **Round 3** (same footage, real investigation before any more technique variants): Salman's
  correction that "engine validated ≠ UX validated" led to two concrete, evidence-based
  investigations:
  1. **Frame density measured, not guessed** — real mean-abs-pixel-difference motion analysis
     against a 15fps reference set (`evidence/measure_motion.py` + real output committed). Round
     2's 6fps guess showed ~2.5x more motion per visible step than true continuous playback; 12fps
     brought that to ~1.24x — the new, evidence-backed density (240 frames, real 4.4MB payload).
  2. **Timeline-driven pacing implemented and verified** — researched the real, named technique
     (GSAP's `scrub: true` vs `scrub: <seconds>` distinction), implemented the latter for real (a
     persistent `requestAnimationFrame` loop exponentially easing displayed progress toward a
     scroll-set target, τ≈0.5s) as a new `canvasTimeline` technique. Verified with real
     instrumentation that displayed progress keeps moving toward the target for close to a second
     with zero further scroll input — objective proof of real decoupling from scroll velocity, not
     a relabeled direct scrub. Real cost found: this mode draws continuously (a genuine
     performance/battery tradeoff), not free.

Real bugs found and fixed *during* this investigation work, not shipped unnoticed:
- Redundant canvas redraws during scroll holds (no same-index skip guard) — found via a real
  instrumented headless-Chrome test, fixed, benefits beit-al-fakhar's Hero too.
- A React hooks-order violation introduced by the same edit.
- A sticky-pin/chapter-timing mismatch (booking chapter's hold sat past the point where
  `position: sticky` naturally releases) — rescaled chapter timing to the real pinned zone.
- A self-triggering `timeupdate` feedback loop in the lab's hybrid technique (pauseCalls hit
  50,000+ before the fix).
- Two of my own test-script bugs (checkpoint scroll-position math mismatch; a double
  query-string bug in CDP tab-creation URLs) — caught via re-verification, not shipped unnoticed.

## 🔧 Technical Decisions Made

- **Reverted `story_experience` for RK Barber's Video 1, kept the code.** Real user feedback (two
  rounds of it) established the footage was the real ceiling, not the rendering technique — this
  is a legitimate, evidence-backed investigation outcome, not a failure to hide. `story_experience`
  SectionType, component, and the shared frame-sequence engine all stay in the codebase — real,
  validated code, just not applicable to *this* footage.
- **Design Laboratory Protocol adopted as standing practice** (`.claude/agent/frontend-architect.md
  §10.5`): repeated in-Tenant-OS tuning that doesn't resolve a real complaint is the signal to stop
  tuning and build a standalone, architecture-free lab instead.
- **Never hardcode a single validated number as a platform standard.** 230 frames (round 1) and
  120 frames (round 2's initial guess) were both real, footage-specific findings, not universal
  constants — logged in the Evolution Log as a "density is a pipeline property, not a magic
  number" finding, explicitly not promoted to a formal profile system on 2 data points.
- **Direct scrub vs. timeline-driven pacing are architecturally distinct, and now both real,
  working, comparable options** in the lab — which one (and what τ) is right for production stays
  an explicit, deferred human judgment call, not asserted here.
- **Catalog Capability duplication logged as a 2nd real instance** of the "two parallel
  implementations, one broken" pattern first seen with Media (previous session) — two independent
  cases is this project's own Abstraction Rule threshold for treating something as a confirmed
  pattern worth a future targeted audit.
