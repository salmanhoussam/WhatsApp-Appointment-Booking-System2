## Part 4 — TOS-005: CMS Generic Engine (the real architectural work)

### The real finding that shaped the whole ADR

While grounding the CMS design in real code (not assumption), found that **a generic editing
engine already existed** — `TOS-002` (Decided, an earlier ADR) had built `EditableRegion.jsx` +
`discovery.js` + a real Schema (`tenant-os/schemas/content.js`), wired into `HeroSection.jsx`/
`StorySection.jsx` for real Inline click-to-edit on `hero.title`/`story.heading`. It called its own
dedicated backend routes (`/content/hero-title`, `/content/story-heading`) — separate from the
`/content/sections/{type}/fields` route Phase 2.6 built for the Dashboard's Section Settings form.
**Both routes wrote to the exact same JSON location** (`config.content.sections[type].data[field]`,
confirmed by reading `sectionFieldHelpers.js`) — the data model was never duplicated, only the
route was, by two pieces of work built at different times without knowing about each other.

This connected directly to a real, not-yet-ratified evolution log entry
(`.claudedocs/evolution/capability-operations-model.md`, 2026-07-29) that already named the
correct fix — "one Operation, one Contract, many Interfaces" — which Salman had called "one of the
most important ideas that will enter the Capability Architecture ADR later, once it matures more."
This session's finding was that second real proof point.

### TOS-005 — Decided, approved with 4 binding conditions

`.claudedocs/adr/TOS-005-cms-generic-engine.md` + `.claudedocs/implementation/TOS-005/CONTRACT.md`
(commit `aff8335`). Decision: unify `hero.title`/`story.heading` onto the generic route (retiring
the two dedicated ones); one canonical declarative Section Schema; a generic repeatable-group
route family; `EditableRegion`/`discovery.js` untouched (real, working, intentionally dormant
infrastructure, not retired or extended). New section *types* from the Dashboard explicitly out of
scope for v1.

Salman's 4 conditions before commit, each mapped into the documents:
1. Phase A must be a pure migration — zero visible behavior change.
2. One structural (not conventional) single source of truth for the schema — no hand-kept
   frontend mirror, ever.
3. The repeatable-group editor must be genuinely generic (`RepeatableGroupEditor`, never
   per-section editors).
4. Server-side validation, independent of the Dashboard, mandatory.

### Phase A — Interface Unification (commit `ceac0bf`)

Retired `/content/hero-title`/`/content/story-heading`; both fields now write through
`PATCH /content/sections/{type}/fields`. `content.js`'s two schema entries gained a `buildPatchBody`
hook so the generic `saveFieldValue` in `GenericAdminDashboard.jsx` needed zero capability-specific
branching. **All 9 items of the real Acceptance Test verified with a real browser** (Playwright MCP,
driven directly in-session): Inline edit → real network capture of the new route → real
`GET /public/mr-h/config` read confirming the DB value changed → real public homepage load
confirming the visible text → same for `story.heading` → Dashboard's own Section Settings form
reconfirmed still working on the same fields → grep + `404` confirmed no caller of the old routes
remains anywhere → RK reconfirmed unaffected (0 console errors).

### Phase B — Canonical Section Schema (commit `f01d383`)

New `app/schemas/section_schemas.py` — the single real source of truth, covering all **14** real
section types `SECTION_MAP` renders (a real scope finding made while executing: RK's live config
already uses `story_experience`/`video_story`/`testimonials`, none of which were in the original
9-section Homepage Contract — those 5 plus `categories_grid`/`offers` got a label only, deliberately
preserving their exact current no-edit-button behavior rather than silently expanding scope).
New `GET /content/sections/schema` route; `update_section_fields` now validates every request
server-side before writing. `SettingsTab.jsx`'s hardcoded `SECTION_FIELDS`/`SECTION_LABELS` objects
deleted entirely — the Dashboard fetches the same schema file's content instead.

Verified: 3 raw `curl` calls proving validation independent of the Dashboard (undeclared field →
422, wrong type → 422 with a real message, valid → 200); real browser pass on both Mister H (9
sections, zero regression) and RK (10 sections including the 5 label-only ones, zero regression, no
phantom edit buttons).

### Phase C — Repeatable-Group Backend Engine (commit `5a29c22`)

One generic route family (`GET/POST .../repeatable/{field}`, `PATCH/DELETE .../{field}/{index}`,
`PATCH .../{field}/reorder`) for every repeatable field on every section — never a section-specific
route. `content_sections_repo.py` gained the matching read-merge-write functions.

Verified against **all 3 real repeatable fields** (`why_choose_us.items`, `location.tags`,
`story.stats`) with real `curl` calls: add/edit/delete/reorder each confirmed via real
`GET /public/mr-h/config` reads; both object-shaped and bare-scalar item validation confirmed
rejecting malformed input; the `{field}` gate confirmed rejecting a real scalar field and an unknown
field. All test data cleaned up, tenant state restored exactly. One transient Supabase pooler `500`
hit mid-test — confirmed via the server log as the same already-documented recurring infra
flakiness this project has hit all session, not a regression (the very next identical request
succeeded).

### Phase D — Repeatable-Group Dashboard UI + Service-layer hardening (commit `c7eed23`)

Salman's real, additional requirement when authorizing this phase: **changes must only ever happen
through the Dashboard, never a script reaching around it.**

**Real gap found while addressing it**: validation only lived in the Route layer
(`content.py`), not the Service layer (`content_service.py`) — a script calling the Service
directly would have bypassed it entirely. Fixed: `content_service.py`'s own functions now validate
internally too. **Honest, documented limit**: a script writing via raw Prisma, bypassing
`content_service.py` entirely, can't be prevented by code — that's Python import discipline, not a
technical guard. Found **3 real historical scripts that already do exactly this**
(`scripts/fix_cta_mrh.py`, `scripts/add_why_choose_us_mrh.py`, `scripts/set_mrh_social_contact.py`,
all dated 2026-08-18, one-off, already executed, predating this Contract) — not rewritten
retroactively, but the going-forward convention is now explicit in `section_schemas.py`'s own
docstring: any future script touching section content must call `content_service.py`, never raw
Prisma.

**UI**: new `FieldInput` (one shared kind→input-type renderer, used by both scalar fields and
repeatable sub-fields) and `RepeatableGroupEditor` (`{sectionType, field, fieldSchema}` → generic
add/edit/delete/reorder) in `SettingsTab.jsx`. Local per-row draft state with an explicit per-row
"حفظ" (avoids a per-keystroke autosave race where two overlapping PATCHes against the same index
could interleave).

**Verified through the real Dashboard UI, not curl**: real clicks, real typing, a real `<select>`
interaction — added a real item to `why_choose_us.items`, edited it via the row's own auto-appearing
Save button, deleted it, reordered two items and reordered back — every step confirmed via a real
`GET /public/mr-h/config` read. 0 console errors throughout. RK reconfirmed unaffected. Mister H's
real content restored to its exact pre-test state at the end.

## Part 5 — Tenant OS Section Editor: Implementation Plan (planning only, no code)

After TOS-005 A→D closed, Salman asked directly for the Mister H dashboard to be usable
(`/bo-hussein run the server let me test mr-h dashboard` — servers started, real creds handed
over). His real, live testing of the Settings/Section Settings UI produced the next real request:
a full **CMS Section Editor Implementation Plan** — explicitly planning-only, no code, no commit,
no DB change — for turning the flat Section Settings accordion into a real two-pane Section
Editor (list + live preview + per-section editor), grounded entirely in real code, never assumed.

**Real investigation, not guessing, produced the single most important finding**: "Services" (the
plan's own mandatory worked example) is not one thing. `FeaturedItemsSection.jsx`'s
`heading_ar`/`limit` are real Content Capability data, already schema-driven. But the *items*
themselves (name/price/image/order/add/delete) are **not** `content.sections[]` data at all — they
are real `CatalogService` rows, already fully CRUD-editable via `StaffTab.jsx`'s already-mature
"الخدمات" sub-view. Building a second items-editor inside the new Section Editor would have been
exactly the dual-write-path anti-pattern TOS-005 itself exists to prevent — resolved as: the
Section Editor **orchestrates** (links/embeds `StaffTab.jsx`), never rebuilds, for anything owned
by another Capability (Services, Staff).

Other real, code-grounded findings: CTA's 3 variants share the exact same 5 fields (verified, not
assumed); Footer is **not** a Section today (no `enabled`/`order`, not in `SECTION_MAP`, content
lives directly on `Client` fields, not `content.sections[]`); `page_type`/`catalog_layout`/`font`
(the "old" General Settings controls) are confirmed **dead code** for any Section-System tenant —
traced end-to-end, zero real consumer anywhere in the renderer tree, while `primary_color` is
real and load-bearing everywhere.

Salman then reframed the whole effort explicitly: **not a Mister H CMS — the next real increment
of the platform-wide Tenant OS Editing Engine**, schema-driven (a Section declares its own
editable shape, the Dashboard reads it and generates the editor — never a
`HeroEditor.jsx`/`StoryEditor.jsx`/... per section), with Mister H as the acceptance tenant, RK as
the mandatory second-tenant proof, and a real, binding rule: **zero `if slug === ...` anywhere in
the new code.** Added to the plan under his direction: two new schema `kind`s (`media` — declared
in schema but reusing the existing dedicated upload Renderers, reconciled explicitly with `TOS-002`
§4.5's Processing Pipeline principle; `group` — a single nested object, real but not yet used
anywhere, e.g. a possible future `Hero.cta = {label, url}`, confirmed Hero has no real `cta_link`
field today). Footer's own open question resolved: **join `SECTION_MAP` + get a real
`enabled`/`order` row, but its content stays capability-owned (`Client` fields), never migrated
into `content.sections[footer].data`** — a third real proof of the same "content-owned-by-another-
capability" pattern as Services/Staff, plus a named, real, not-yet-built win it unlocks (Footer's
currently-hardcoded `QUICK_LINKS` could become derived from the real enabled-sections list).

Final plan replaced with Salman's own 6-phase structure (Section Shell → Schema-Driven Field
Editor → Repeatable Groups [already done, TOS-005 D] → Media Editor → Capability Integration →
Remove Legacy Settings), each phase mapped to real files/routes, GREEN/YELLOW/RED verdict per
phase.
Document: `.claudedocs/architecture/ALZABT_CMS_SECTION_EDITOR_IMPLEMENTATION_PLAN.md` (still
uncommitted, planning artifact — commit status is Salman's own call, not assumed).

## Part 7 — Dashboard "old UI" flash — investigation + fix (commit `61a3be2`)

Salman reported a real, repeatable symptom via a real screenshot: on first load or a weak
connection, `/mr-h/dashboard/settings` briefly showed a visibly different, "older-looking"
Dashboard (a short nav — `نظرة عامة/الطلبات/الكتالوج/الإعدادات` — and generic default branding)
before settling into the real one. Investigation-only first (no code/commit), per his explicit
instruction, following `investigation-protocol.md`'s full discipline.

**Real root cause, fully traced, no guessing**: there is no second/legacy Dashboard component
involved at all (confirmed by tracing `App.jsx`'s real route table on both `localhost` and
`demo.salmansaas.com` — `SmarAdminDashboard` never matches this URL pattern in either
environment). It is `GenericAdminDashboard.jsx`'s own real, current code, caught mid-render: two
independent, unsynchronized async sources — a local `/settings` fetch (gates `loading` → the
spinner) and `useTenantConfig()`'s own separate React Query (drives `NAV` via
`active_services`/`hasReservations`) — with nothing gating the shell's render on *both*. Confirmed
exact code match to the screenshot: `buildNav(false)` returns precisely the 4 short-nav items;
`settings`'s own `.catch()` fallback is the exact literal values shown (`'لوحة التحكم'`,
`'#6366f1'`). Confirmed structurally platform-wide (zero tenant-specific branching in this code
path), not `mr-h`-specific. A real, separate, dev-only contributing factor also found and named:
Vite dev mode's unbundled module transfer can itself produce an even longer, fully-blank
pre-spinner window under a throttled connection.
Evidence: `.claudedocs/work/dashboard-old-ui-flash-investigation/2026-08-19/summary.md`.

Salman then explicitly chose to fix this **before** Phase 2 ("لأنها تضرب بالضبط الشيء الذي نحن عم
نبنيه الآن"), with strict constraints (this file only, no refactor, no fallback-data change, real
tests including simulated failure of both sources, independent commit). Fix: gate the spinner on
`loading || configLoading` (was `loading` alone); on a real, permanent failure of either source,
render a new `DashboardErrorState` (message + real retry button) instead of either an infinite
spinner or the wrong shell. **Verified with real evidence, both tenants**: the actual race
(tenant-config real-delayed 3s via `page.route()`, confirmed via real request-hit logs) sampled
every 400ms for the full window — never once showed the short nav, then jumped straight to the
correct shell on resolution; a real simulated `500` on `/admin/settings` and, separately, on
tenant-config (with `useTenantConfig`'s own unchanged `retry: 2` firing for real) each
independently produced the new error state, not a stuck spinner.
Evidence: `.claudedocs/work/dashboard-old-ui-flash-investigation/2026-08-19/fix-evidence.md`.
