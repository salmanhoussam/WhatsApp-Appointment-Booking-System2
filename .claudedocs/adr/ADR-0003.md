# ADR-0003 — Architecture Documentation System (Documentation Policy v2)

**Status:** Decided (2026-07-22). Adopts the design; implementation is a separate, later
Implementation Contract (file-by-file migration), not part of this ADR.

**SSOT note:** This ADR does not restate the full design. `/home/musicmaster/.claude/plans/`
holds the working design record from this decision's planning session (Plan agent design +
Salman's corrections + 4 confirmed decisions). Once the Implementation Contract executes, this
ADR's own content becomes the permanent record — the plan file is scratch, this document is not.

**Scope note:** This is a **platform-wide** ADR, not a Tenant-OS-scoped one — it governs how *all*
future architecture documentation is organized (Tenant OS, Tenant Lifecycle, Super Admin
Dashboard, any future domain), the same scope as ADR-0001 and ADR-0002. It lives in this sequence
(`ADR-0001` → `ADR-0002` → `ADR-0003`), not in a Tenant-OS-specific `TOS-XXX` sequence, per the
same platform-vs-domain distinction this ADR itself establishes for future ADRs (§4).

---

## 1. Context / Problem Statement

`.claudedocs/architecture/TENANT_OS_PLAN.md` grew to 1,432 lines / 26 sections, playing 8 roles at
once (Vision, Architecture, Capability Contracts, Sprint history, Findings, Decisions, Review log,
Roadmap) in a single file. No one — including an AI agent picking up one Capability's Sprint work
— could hold its mental model in memory or read only the relevant part. This is not unique to that
one file: a reconnaissance pass found the existing `documentation-policy.md` (49 lines) only
accounts for 7 of ~19 real folders actively in use under `.claudedocs/` (~150 files, ~26,000
lines) — `work/`, `plans/`, `roadmap/`, `audits/`, `archive/`, and several loose root files exist
and are used but were never reconciled with the policy.

## 2. Decision Drivers

- **Every architectural idea should have exactly one home** — the same Single Source of Truth
  principle already governing the codebase (`rules/backend/architecture.md` §9), applied to
  documentation itself.
- **Small context loads for AI agents and humans alike** — a Sprint on one Capability should need
  a handful of small files, not one 1,400-line document covering 25 unrelated concerns.
- **Growability for ~5 years**, not a one-time tidy-up — the same folder must still make sense
  after Catalog, Orders, Site Configuration, and future domains (Booking OS, AI OS) are added.
- **Reuse proven prior art, don't reinvent** — `.claudedocs/audits/claudedocs_audit.md`
  (2026-04-24) already executed one real self-reorganization of this exact folder; this decision
  continues that lineage rather than starting from zero.

## 3. Options Considered

**Option A — Split `TENANT_OS_PLAN.md` into smaller files, leave everything else as-is.**
Rejected. Treats the symptom (one file's size), not the cause (no standing system governing how
any future large architecture doc gets organized — the same growth would recur for the next
domain).

**Option B — A six-folder system with a `governance/` folder for cross-cutting matrices** (first
design pass, via a Plan agent). Presented, then **rejected** by Salman: it still produced
medium-large documents (a `TENANT_OS_VISION.md` holding all "why" prose in one place) and mixed
Principles (forever-true) with Decisions (one-time, irreversible) in ways that don't match how
those two actually differ in permanence and purpose.

**Option C — Radical minimalism: tiny entry point, Principles and ADRs fully separated,
Capabilities flat, Reviews and Roadmap fully separate, one navigation Index (chosen).** Every
document capped at ~100–200 lines. No cross-cutting matrix files — each Capability carries its own
status inline; a single `INDEX.md` is the one rollup. This is the design in §4 below.

## 4. Decision

Adopt Option C. Six layers, each answering one question, each with its own rate of change:

| Layer | Answers | Rate of change | Folder |
|---|---|---|---|
| Entry Point | What is this, at a glance, with links out | Rare | `TENANT_OS.md`, `README.md`, `INDEX.md` |
| Principles | What is permanently true, regardless of Capability | Rare — years | `principles/` |
| Decisions (ADR) | What irreversible/cross-cutting call did we make, and why | Occasional, append-only | `adr/` |
| Capability Contracts | What is true, right now, about ONE Capability | Every Sprint, in place | `capabilities/` |
| Reviews | Independent, point-in-time evidence something worked/didn't | At defined gates, immutable | `reviews/` |
| Roadmap | What's next, in what order | Constant, disposable | `roadmap/` |

**Every fact has exactly one home file.** No separate `governance/` folder or cross-cutting matrix
files (no `SSOT_MATRIX.md`/`FINDINGS_REGISTRY.md`/`HEALTH_DASHBOARD.md`). Each Capability file
carries its own inline status (Maturity, Open Findings, SSOT owner); `INDEX.md` is the one
rollup/navigation table (Decision | Location | Status), extended to also list Capabilities.

**Platform vs. Domain-scoped ADRs are kept in separate sequences.** `ADR-000X` (this sequence,
`.claudedocs/adr/`) is for platform-wide, cross-domain decisions — exactly ADR-0001, ADR-0002, and
this ADR itself. Domain-specific ADRs (e.g. Tenant OS's own architectural decisions — why the
Editing Engine exists, the Capability Contract model) get their own prefixed sequence
(`TOS-XXX`, in `architecture/adr/`) so the platform sequence's numbering stays meaningful as more
domains (Booking OS, AI OS, etc.) accumulate their own decision histories over years, rather than
one shared sequence where "ADR-0047" tells a reader nothing about scope.

**Principles vs. `.claude/rules/`.** `.claude/rules/*.md` remains the canonical, always-loaded home
for platform-wide enforceable rules (Single Source of Truth — `backend/architecture.md` §9,
Admin/Public Contract — §10, the Abstraction Rule — `team-roles.md`). `architecture/principles/`
holds only Tenant-OS-specific principles that have no other home, numbered `P-XXX`. Which specific
principles qualify, and their exact filenames, is Implementation Contract work, not decided here.
`INDEX.md` lists both groups explicitly under separate headings — "Platform Principles → see
`.claude/rules/...`" and "Tenant OS Principles → `principles/P-XXX-...md`" — so the
one-idea-one-place rule is visible at the navigation layer, not just implied.

**Capability Contract as parent; Admin/Public are projections of it, not independent contracts.**
Confirmed by Salman while reviewing this exact design (using this language himself, unprompted) —
promotes a concept previously deferred in project memory pending a 2nd/3rd real Capability. Every
`capabilities/<name>.md` documents Admin behavior and Public behavior as two projections of one
Contract.

## 5. Single Source of Truth

This ADR for the adoption decision and the six-layer model. The Implementation Contract (separate,
future document) for the exact file-by-file migration mapping. `.claude/rules/documentation-policy.md`
is updated to reference this ADR and replace its "Fixed folder structure" section with the tree
this ADR establishes — that rule file remains the operational instruction agents read; this ADR is
the decision record for why.

## 6. Scope / Non-Goals for This ADR

**In scope:** the six-layer model, the platform-vs-domain ADR sequence split, the
principles-vs-rules boundary, the elimination of cross-cutting matrix files, promoting the
Capability/projection framing.

**Out of scope (deferred to the Implementation Contract):** the exact `git mv` destination for
every one of the ~150 existing files; naming/dating conventions for `reviews/*.md` and
`roadmap/sprint-N.md`; whether `roadmap/*.yaml` is retired in favor of markdown or both coexist;
triage of `plans/`'s 19 files and the loose root files; exact placement of
`BEIT_AL_FAKHAR_STORE_EXPERIENCE_REVIEW.md`; the full section-by-section mapping of
`TENANT_OS_PLAN.md`'s remaining sections. None of these change the decision in §4 — they are
execution detail.

## 7. Consequences

- `TENANT_OS_PLAN.md` is retired as a single file — its content is preserved exactly, redistributed
  across `TENANT_OS.md`, `principles/`, `architecture/adr/TOS-XXX`, and `capabilities/*.md` during
  the Implementation Contract. No architectural fact changes; only where it lives.
- `documentation-policy.md`'s "Fixed folder structure" section is superseded by this ADR's §4 tree
  and must be updated to match (Implementation Contract work).
- Two confirmed real cross-reference risks must be fixed during migration: `CLAUDE.md:62` restates
  the old 7-folder list inline; `bo-hussein.md:223` cites `TENANT_OS_PLAN.md §19` by section
  number — both break once the split happens.
- Future domains (Booking OS, AI OS, etc.) inherit this same six-layer model rather than each
  re-deriving their own — the explicit intent behind designing this once, generally, rather than
  as a one-off fix for Tenant OS specifically.
- No document in the new structure should exceed ~200–300 lines; `TENANT_OS.md` itself under 200 —
  an explicit, checkable target for the Implementation Contract's verification step.
