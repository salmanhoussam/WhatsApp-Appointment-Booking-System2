# ADR-0002 — Tenant Lifecycle & Subscription Domain Architecture

**Status:** First implementation slice complete and Post-Implementation Reviewed (2026-07-18) — see `.claudedocs/reviews/ADR-0002_POST_IMPLEMENTATION_REVIEW.md`. §7's slice (Tenant Status / Account Lifecycle State split) is implemented, verified, and the live migration has run. Remaining slices (Subscription/Plan, Payment/Invoice, Usage) are future, separately-scoped work per §6.

**SSOT note:** This ADR does not restate the domain design. `.claudedocs/architecture/TENANT_LIFECYCLE_PLAN.md` is the single source of truth for entity definitions (Tenant/Subscription/Plan/Payment/Invoice/Usage), the state machines, and the Business Principles (Phase 0). This document records the decision to adopt that design and scopes the first concrete implementation slice.

---

## 1. Context / Problem Statement

`Client.status` today mixes two unrelated concepts: an administrative concept (is the account technically usable — `suspended`) and a lifecycle concept (`trial`/`demo`). Three separate onboarding paths (`registration_service.py`, `demo_service.py`, `onboarding.py`) create trial periods with inconsistent, hardcoded durations (14 days vs. 7 days). No `Subscription`, `Plan`, `Payment`, or `Invoice` entity exists — `Client.tier` is a free-text field, not an assignable plan. No automation checks `trial_ends_at`; the only status transition mechanism today is a manual Super Admin `PATCH`. Full detail: `TENANT_LIFECYCLE_PLAN.md`.

## 2. Decision Drivers

- **No Status Mixing** (`TENANT_LIFECYCLE_PLAN.md` Phase 0, principle 5) — the root problem this ADR exists to fix.
- **Configuration over Hardcoding** (Phase 0, principle 3) — the 14-day/7-day trial inconsistency is a direct symptom of not having this.
- **ADR-0001's enforcement must not regress.** Tenant status enforcement (`app/core/tenant.py`, suspended/expired hard-block) is implemented, archived, and verified — any change here must preserve or deliberately and explicitly extend that behavior, never accidentally weaken it.
- **Incremental implementation discipline.** ADR-0001 succeeded specifically because it was implemented one small, independently-revertible step at a time with real evidence per step, not as one large change. This ADR adopts the same discipline.

## 3. Options Considered

**Option A — Keep `Client.status` as a single field, add more allowed values to it.**
Rejected. This perpetuates exactly the status-mixing problem being fixed — every future addition (payment status, onboarding status) would keep landing in the same overloaded field.

**Option B — Build the full domain model at once** (Subscription, Plan, Payment, Invoice, Usage all in one implementation pass).
Rejected. Too large a single change, high risk of the kind of silent regression ADR-0001's Phase 3/4 caught early precisely because those steps were small. Several of these entities (Payment, Invoice) also depend on an unmade business decision — which payment provider — so building them now would be speculative.

**Option C — Incremental adoption, starting with the smallest safe slice (chosen).**
Adopt the `TENANT_LIFECYCLE_PLAN.md` model as the target architecture, but implement it slice by slice, each slice getting its own Implementation Contract. The first slice: separate **Tenant Status** from **Account Lifecycle State** on the existing `Client` model — no new entities yet, just correcting the existing status-mixing bug. Subscription/Plan/Payment/Invoice/Usage entities come in later, separately-approved slices.

## 4. Decision

Adopt the domain model defined in `TENANT_LIFECYCLE_PLAN.md` as SalmanSaaS's tenant lifecycle architecture going forward. Implementation proceeds incrementally (Option C); this ADR does not itself decide implementation mechanics — those belong to each slice's own Implementation Contract.

## 5. Single Source of Truth

`TENANT_LIFECYCLE_PLAN.md` for entity/state-machine/principle definitions. This ADR for the adoption decision and slice scoping. `app/core/tenant.py` (ADR-0001) remains the sole enforcement point for Tenant Status and is not modified by this ADR itself — only by whichever future Implementation Contract slice touches it, and only after §9 below is answered.

## 6. Scope / Non-Goals for This ADR

**In scope (across multiple future Implementation Contracts, not this document):** separating Tenant Status from Account Lifecycle State (first slice, §7); later, Subscription/Plan entities; later still, Payment/Invoice (Phase 5, deferred pending a payment-provider decision); Usage tracking (deferred).

**Out of scope:** choosing a payment gateway; any actual UI (covered separately and already deferred, per `SUPER_ADMIN_DASHBOARD_PLAN.md`); pricing/VAT strategy.

## 7. First Implementation Slice (scoped here, built in a separate future Implementation Contract — not this document)

Separate **Tenant Status** (`active`/`suspended`, ADR-0001-enforced, unchanged) from **Account Lifecycle State** (`trial`/`paid`/`grace_period`/`expired`/`cancelled`/`archived`, a new field). This is the smallest change that removes the actual status-mixing bug without touching anything else.

## 8. Compatibility Change This ADR Now Authorizes

ADR-0001's enforcement today blocks directly on `Client.status == "expired"` or `"suspended"`, identically for both. Per §9.1 below, this ADR **authorizes a real extension to ADR-0001's enforcement**: `suspended` stays a Hard Block; `Lifecycle: expired` becomes a distinct **Soft Block** — a different, narrower enforcement behavior, not merely a renamed value. This is a deliberate widening of what `app/core/tenant.py` needs to do, not a like-for-like field split. The exact endpoint allowlist for Soft Block is scoped in §9.1's implementation note below, not assumed.

## 9. Decisions Made (resolved 2026-07-18)

### 9.1 — Access impact: `expired` vs `suspended`

**Decision:** Not equivalent. `suspended` = Hard Block (administrative/security/ToS action — no login, no access to any interface, unchanged from ADR-0001 today). `expired` = **Soft Block** — core features blocked, but the tenant admin retains access to a small allowlist: a billing/renewal surface and an account-settings/data-export surface.

**Reasoning (user):** administrative suspension and financial/trial expiry are different in kind and should not carry the same UX — soft-blocking expired accounts materially improves retention/win-back versus a full lockout.

**Implementation note (flagged now, not deferred silently):** `TENANT_LIFECYCLE_PLAN.md` explicitly defers Payment/Invoice/Billing entities to Phase 5 — **there is no Billing/renewal page in the codebase today.** The Implementation Contract for the first slice must therefore scope the Soft Block allowlist to what actually exists now (realistically: the tenant's own Settings page, and whatever manual/WhatsApp-based renewal contact path already exists via `ai_settings_agent.py` or direct support) — it cannot allowlist a "renew online" flow that hasn't been built. A full "true" Soft Block experience (self-service renewal) is contingent on a future Billing slice; the first slice implements the access-control mechanism (an allowlist-aware check distinct from Hard Block) with today's honestly-limited allowlist, not a placeholder promise of a page that doesn't exist.

### 9.2 — Unified trial duration & configurability

**Decision:** 14 days becomes the single default (matching `registration_service.py`; `demo_service.py`'s 7-day default is retired in favor of the same 14-day default, unless a future decision says demo tenants should behave differently — see §9.3). Per-tenant configurability is required, not optional — implemented via the **existing** `Client.trial_ends_at` field (`schema.prisma:44`, already present), which both onboarding paths already populate at creation time. No new "duration" config is needed at the platform level; what changes is that both onboarding paths compute `trial_ends_at` the same way (`created_at + 14 days`) by default, while remaining a per-row date a Super Admin can extend later (a manual-extension *endpoint* is not built in this slice — flagged as a natural, separately-scoped follow-up, not assumed here).

**Reasoning (user):** 14 days is the standard time-to-value window for SaaS onboarding without requiring pre-configuration; 7 days creates premature urgency and only suits trivially simple products. Storing a per-tenant date (already the schema's existing pattern) rather than a hardcoded duration is what makes future sales/support-driven extensions possible without a schema change.

### 9.3 — Migration mapping for existing tenants

**Decision:**
- `status="trial"` → new Tenant Status = `active`, new Lifecycle = `trial`, existing `trial_ends_at` value is kept as-is (both onboarding paths already set it correctly at creation — no recompute needed). **Exception:** if a tenant's existing `trial_ends_at` is already in the past at migration time, grant a one-time 3–7 day grace extension from the migration date (exact number decided in the Implementation Contract) and notify the tenant, rather than immediately flipping them to `expired`/Soft-Block on migration day.
- `status="demo"` → exempted from expiry entirely. Represented either as a distinct Lifecycle value (e.g. `evergreen`) or `trial_ends_at = null` (exact mechanism — a new enum value vs. a null-means-exempt convention — decided in the Implementation Contract, not here) so demo/internal-showcase tenants keep working indefinitely without being caught by the new expiry logic.

**Reasoning (user):** trial tenants shouldn't be suddenly cut off by a migration event with no warning; demo tenants are internal-showcase environments, not real subscriptions, so expiry logic shouldn't apply to them at all.

## 10. Consequences

- Adds one new field (Account Lifecycle State — exact name/type decided in the Implementation Contract) + a transitional migration per §9.3.
- `suspended` enforcement is unaffected — verified unchanged behavior is a required check in the upcoming Implementation Contract.
- `app/core/tenant.py`'s enforcement gains a genuinely new capability (Soft Block / allowlist-aware check for `expired`), not just a second field to read — this is more implementation surface than a simple split, and the Implementation Contract must treat it as such (its own test matrix, not reused wholesale from ADR-0001's).
- The Soft Block allowlist is honestly scoped to what exists today (§9.1) — it is not blocked on Billing/Payment being built, but it also doesn't pretend a renewal page exists yet.
- No new entities (Subscription/Plan/Payment/Invoice) are introduced by this ADR — those remain future, separately-scoped work per `TENANT_LIFECYCLE_PLAN.md`.

## 11. Second Slice — Subscription & Plan Domain (Design, 2026-07-19)

**Status:** Implemented (4 phases) and Post-Implementation Reviewed (2026-07-19) — see `.claudedocs/reviews/ADR-0002_CONTRACT02_POST_IMPLEMENTATION_REVIEW.md`. `Plan`/`Subscription` exist, `PATCH /clients/{id}/lifecycle` is provably routed through the single write path, `app/core/tenant.py` confirmed byte-unchanged throughout. Two small follow-ups named, not blocking: (1) `SuperRepository.update_client_lifecycle_state()`'s residual dual-write capability is dead but not deleted, (2) `registration_service.py`/`demo_service.py` don't yet auto-create a `Subscription` for new tenants.

### 11.0a Subscription Ownership — decided now (not left open)

Unlike the questions in §11.0b, this one is resolved now, because it determines the foreign-key shape of `Subscription` itself — getting it wrong means a real migration later, not just a documentation update.

**Decision:** `Subscription` belongs to `Client` (Tenant) only — `Subscription.clientId → Client.id`, full stop, for this slice.

**Reasoning:** matches today's confirmed reality exactly — there is no `Organization` or `Account` concept anywhere in the codebase; `Client` is already the atomic tenant unit everything else (bookings, catalog, users, `ClientService`) hangs off of. Introducing an ownership layer above `Client` now would be designing for a business structure that doesn't exist yet.

**Explicitly flagged, not hidden:** if SalmanSaaS ever needs an `Organization` (one company, multiple `Client` tenants) or an `Account` (one billing entity, multiple `Client`s) layer, **`Subscription`'s foreign key is exactly where that change would land** — this is the specific, known future migration point, called out now so it isn't a surprise later.

### 11.0b Business Model — Open Questions (explicitly deferred, not assumed either way)

Beyond ownership (settled in §11.0a), SalmanSaaS's full business model is **not yet decided**, and this slice's design does not decide the rest of it — it works only under today's confirmed reality and states plainly where it would need revision if that reality changes:

| Question | State in the codebase today | How this design handles it |
|---|---|---|
| Multiple subscriptions per `Client`? | No — `Client` is one tenant, one business, one `tier` string | Design assumes **at most one active `Subscription` per `Client`** — a business rule, not a hard DB constraint. A future need for multiple would be a separate design fork, not handled here. |
| Add-ons? | `ClientService`/`PlatformService` already exist (feature activation) but have no relationship to a "plan" concept | **Not touched by this slice.** Whether add-ons should relate to `Plan` is left an open question, not answered. |
| Usage-based billing? | Doesn't exist | Deferred — matches `TENANT_LIFECYCLE_PLAN.md`'s existing Usage Tracking deferral. |
| Enterprise plans (custom pricing/contracts)? | Doesn't exist | Out of scope — `Plan` here assumes a fixed catalog price only. |
| Reseller model? | Doesn't exist anywhere in the codebase | Out of scope entirely, not referenced by this design. |
| Organization/Workspace (one business owning multiple `Client` tenants)? | Doesn't exist — `Client` is the atomic unit today | Design assumes this continues to hold — see §11.0a for the specific migration point if this ever changes. |
| **Does `Plan` describe the product, or the price?** | `Client.tier` today conflates both (a tier name that also implies its price) | **Left open, not solved here.** A classic ERP pitfall: if price lives directly on `Plan` and the price later changes, existing subscribers either get silently repriced or the historical price is lost. The "correct" long-term answer is likely a separate `PricingVersion`/`PriceBook` entity that `Plan` references, with `Subscription` pinned to the price version active when it started — **not designed here**. §11.1's `monthly_price` field is explicitly a provisional placeholder for this minimal slice, not a final answer to this question. |

None of the §11.0b rows are being predicted or designed around — if any of them become real product decisions later, `Plan`/`Subscription` as designed here may need revision. That is accepted and expected, not a flaw in this design. (Matches the project's existing Abstraction Rule in `rules/team-roles.md`: abstract from proven needs, not anticipated ones.)

### 11.1 Proposed entities (minimal only)

- **`Plan`** (new table) — replaces `Client.tier`'s free-text value. Proposed fields: `id, key (unique), name_ar, name_en, monthly_price, currency`. `monthly_price` is a **provisional** field, not a resolution of the Product-vs-Price question in §11.0b — if that question resolves toward a separate pricing entity, this field moves, doesn't stay. **No** usage-limits/features JSON in this slice — that belongs to the future Usage Tracking slice, not here.
- **`Subscription`** (new table) — links a `Client` to a `Plan` over time, per the ownership decided in §11.0a. Proposed fields: `id, clientId, planId, startedAt, endedAt (nullable), status`. Has its own `status`, distinct from every other status field in the system.

### 11.2 ⚠️ The real architectural fork — `Subscription.status` vs. the already-built `Client.lifecycle_state`

This is the genuine difference between this slice and the first one — not just "add a field," but "decide who owns the truth":

- **Option A (recommended):** `Subscription` becomes the new source of truth for subscription lifecycle, but `Client.lifecycle_state` **stays exactly as built** — a cached mirror that `subscription_service` updates whenever the `Subscription` changes. **Advantages:** zero change to `app/core/tenant.py` — every Hard/Soft Block mechanism verified in the first slice keeps reading the same field, only who writes it changes; the migration to this model can happen gradually, tenant by tenant, rather than as one atomic cutover; and the mirror itself can be removed later without re-touching `tenant.py` again, if a future decision decides it's no longer needed. **Trade-off:** a deliberate, documented duplication (unlike the old, undocumented `isActive`/`status` drift ADR-0001 inherited).
- **Option B (not recommended):** remove `Client.lifecycle_state`, read `Subscription.status` everywhere directly — reopens and modifies code already verified in the first slice for no clearly necessary reason, against the "smallest safe step" discipline that has worked so far.

**Recommendation: Option A.**

### 11.3 Automation scope for this slice

Same pattern as the first slice (manual before automatic): assigning/changing a `Client`'s `Plan` is a manual Super Admin action only — **no** self-service plan-change UI, **no** payment integration (Billing/Payment stays out of scope, per `TENANT_LIFECYCLE_PLAN.md` Phase 5, pending a payment-provider decision).

### 11.4 Decisions Requiring Human Approval

1. **Confirm §11.0a** — `Subscription.clientId → Client` only, with Organization/Account explicitly named as the known future migration point if that layer is ever introduced.
2. **Confirm the §11.0b business-model question list is now complete** — covers multi-subscription, add-ons, usage billing, enterprise contracts, reseller, organization/workspace, and product-vs-price — or is there another open business question that should also stay explicitly unresolved?
3. Build `Plan`/`Subscription` now with minimal fields (§11.1), or wait until the payment-provider decision to avoid a possible second redesign?
4. Confirm Option A (§11.2) explicitly — `Subscription` as the new source of truth, `Client.lifecycle_state` as an updated cached mirror — or prefer a different approach?
5. Does `Plan.key` replace `Client.tier` immediately (in a future implementation slice), or do they coexist temporarily pending a manual migration similar to `scripts/migrate_lifecycle_state.py`?
