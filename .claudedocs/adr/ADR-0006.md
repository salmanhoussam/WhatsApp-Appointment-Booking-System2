# ADR-0006 — Unified Bilingual (AR/EN) i18n Architecture

**Status:** Decided (2026-09-01), Salman's explicit approval ("Go ahead. Start phase one.") after
reviewing the full audit. Decision only — this ADR ratifies Option 3 from the audit; the actual
Context/dictionary/tenant-content layer is built under a separate Implementation Contract,
starting with the isolated Phase 1 slice (new code, touches no live page yet).

**Scope note:** Platform-wide, not Tenant-OS-scoped (`ADR-000X`, not `TOS-XXX`) — applies to every
tenant vertical and every generic-dashboard tenant's public/admin pages, not to Tenant OS's
internal architecture specifically.

---

## 1. Context / Problem Statement

Full evidence: `.claude/docs/implementation/BILINGUAL_I18N_ARCHITECTURE_AUDIT/evidence.md`
(2026-09-01, live-verified via real browser sessions on `/rk`, `/rk/store`, `/smar/listings`).
Supersedes the narrower `.claudedocs/implementation/BILINGUAL_AUDIT/evidence.md` (2026-08-30) in
completeness, confirms the same core conclusion.

SalmanSaaS has **15 distinct language-related mechanisms**, none of which gives the real tenant
product (every generic-dashboard tenant's public pages, cart, catalog, reservation flow, admin
dashboard) a working bilingual toggle. Two working, complete AR/EN systems exist
(`pages/marketing/context/LanguageContext.jsx`, `pages/showcase/context/LanguageContext.jsx`) but
are scoped to non-product apps (the marketing landing page, the old demo-builder tool) — neither
reaches a real tenant page. A newly-added header toggle (`TenantHeader.jsx`, added earlier this
same session) is real and visibly works, but is proven cosmetic by live evidence: clicking it
never changes `document.documentElement.lang/dir` and never changes page-body content, only the
header's own nav labels. `document.documentElement`'s `lang`/`dir` never change at runtime on any
live page — the only code that could write them is dead.

## 2. Decision Drivers

- Concrete, live-verified evidence, not a predicted problem — Salman's own real-browser testing
  of RK found the toggle broken before this audit began; the audit then confirmed and completely
  inventoried the gap.
- Real product-readiness pressure: RK is a live pilot tenant; a visibly non-functional language
  button is a real, user-facing defect on a page actively being tested.
- The audit's own comparison found no existing system passes as an off-the-shelf adoption — two
  real, non-overlapping gaps exist (static UI strings vs. tenant-specific content), each already
  solved correctly in one place (`pages/marketing`'s dictionary shape; `UnitCard.jsx`'s
  fallback-pair pattern) — the decision is to combine those two proven pieces, not invent new ones
  or adopt a whole system on the strength of it merely existing.

## 3. Decision

Build **one unified i18n layer** for the real tenant product:

- **One real Context** (single source of truth for the active language), mounted at the app root,
  reusing the mounting pattern and `document.documentElement.dir`/`.lang`-writing technique already
  proven correct in the now-dead `context/LanguageContext.jsx` (the only code in the audit that
  ever did this right).
- **One shared static-string dictionary**, reusing the flat key→string shape already proven in
  `pages/marketing/translations.js` — for UI vocabulary ("Book Now", "Shop", nav labels, etc.),
  consumed by shared design-system components (`TenantHeader.jsx`, `TenantModuleNav.jsx`).
- **One tenant-content resolution pattern**, generalizing `UnitCard.jsx`'s already-correct
  `name_ar`/`name_en` fallback-pair logic past its single current caller — for per-tenant authored
  data (a unit/service/product's own name, a homepage section's own heading/body).
- **One `localStorage` persistence convention** for the real product, replacing the informal
  `appLang`/`showcaseLang` split going forward for tenant pages specifically (those two existing
  keys are NOT touched — see Non-Goals).

Rejected: adopting `pages/marketing`'s context whole (fails on tenant-specific content — it has no
concept of per-tenant data at all); adopting `UnitCard.jsx`'s pattern whole (fails on persistence
and shared UI vocabulary — it has no dictionary or state of its own). Both rejected on named,
specific requirement gaps (audit's Phase 3 comparison table), not on subjective preference.

## 4. Consequences

- Real, cross-cutting migration work follows this ADR — not small. The audit's own risk section
  names the largest blast-radius item: ~20 files hardcoding `direction: 'rtl'` independently, each
  a real chance to regress a currently-working RTL layout if migrated carelessly.
- `GenericAdminDashboard.jsx` gains a genuinely new capability (it has zero i18n today, not a
  broken one) — larger new-build effort than "migrate existing broken code."
- Whether tenant-authored `content.sections` data needs parallel `_en` fields is a real,
  separate backend/schema question this ADR does NOT decide — flagged explicitly in the audit as
  out of scope, to be raised as its own decision once the frontend layer is real.
- Category E (6 dead files: `BookingFlow.jsx`'s stale TODO, `pages/smar/spatial/i18n.js`,
  `SpatialHomePage.jsx`'s fake context, `pages/catalog/CatalogPage.jsx`, the `ChaletCard.jsx`
  family, `LanguageSwitcher.jsx`) becomes safe to delete outright — already unreachable, confirmed
  by the audit's own import-graph search.

## 5. Scope / Non-Goals

- `pages/marketing/context/LanguageContext.jsx` and `pages/showcase/context/LanguageContext.jsx`
  (and their own `appLang`/`showcaseLang` `localStorage` keys) are explicitly NOT touched — they
  already work correctly for their own, separate audiences (the marketing site, the old
  demo-builder tool). This ADR governs the real tenant product only.
- No backend/DB/schema change is decided here (see Consequences — the tenant-content `_en` field
  question is deliberately deferred, not silently assumed either way).
- No auth, tenant-resolution, or deployment change.
- Phase 1 (the first real implementation slice, see Implementation Contract) is explicitly
  isolated new code — it does not modify any existing page's rendered behavior. Migrating real
  pages onto it is later, separately-verified work per the audit's own Migration Plan section.
