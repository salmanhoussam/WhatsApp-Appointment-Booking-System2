# ADR-0004 — Information Ownership Model

**Status:** Decided (2026-07-29). Classification decision only — no code, no new tables, no
migrations. Implementation of any consequence named below (e.g. Payments) is separate, future,
and separately decided.

**Scope note:** Platform-wide, not Tenant-OS-scoped — this sequence (`ADR-000X`), not `TOS-XXX`,
since the classification applies to every tenant type (Booking, Catalog, future Restaurant/Clinic,
future Payments), not to Tenant OS's own internal architecture specifically.

---

## 1. Context / Problem Statement

This platform was built from two mental models at once, neither ever named: **Platform/SaaS**
(Tenant, Booking, Catalog, Orders, Payments, Dashboard — relational, tables and joins) and
**Website Builder** (Hero, Story Experience, Theme, animation — JSON page-definition, deliberately
not tables). Both are correct for what they hold. Nothing has ever stated the boundary between
them, so a concept can drift from one to the other unnoticed — confirmed real, not hypothetical:
this session's Schema Architecture Review found `Unit.content_blocks`/`amenities`/`rules_policies`/
`description_ar/en` (editorial, page-structure content) sitting inside `Unit`, a relational
Business Data table owned by Booking, entirely outside `Client.config.content.sections[]`, the
only place Content's real Ownership is documented (`SCHEMA_ARCHITECTURE_REVIEW.md`, Appendix D2).

Separately, **Payments** has no real Capability home today — cash-only by an explicit prior
decision (`.claudedocs/decisions/2026-07-20-cash-only-billing.md`) — but real provider integrations
(Stripe, Tap, HyperPay, Apple Pay, Google Pay, Payment Links, WhatsApp Payment in some markets) are
a named, approaching need with nowhere principled to go once they arrive.

## 2. Decision Drivers

- The real `Unit.content_blocks` case — concrete evidence this boundary is needed, not a predicted
  future problem.
- Payments' current lack of a designed home.
- Ratified directly now, not gated behind a second independent case (this project's usual
  Abstraction Rule threshold) — the cost of *not* deciding compounds every time a new tenant type
  (Restaurant, Clinic) adds fields with nowhere principled to go, and the evidence
  (`Unit.content_blocks`) is already concrete enough to justify deciding now.

## 3. Decision

**The governing question is ownership, not storage.** Persistence (Database table, JSON blob,
dedicated service) is a *consequence* of deciding who owns a concept — never the first question
asked.

```
Concept
    ↓
Who owns this? (Ownership)
    ↓
Which Capability follows from that ownership?
    ↓
Persistence (a downstream implementation decision, not this one)
```

**Ownership resolves to exactly one of four answers:**

| Owner | Layer | Deciding question | Real examples |
|---|---|---|---|
| The Business | **Business Data** | Does the business transact, search, or relate this to other rows? | Products/`CatalogItem`, Categories, Reservations, Orders, Customers, Payment *transactions* |
| The Experience | **Experience Definition** | Is this page/experience structure, read and rendered as a whole unit? | Section ordering, Hero layout, Story Experience (frames/chapters), animation, CTA copy |
| The Platform | **Platform Configuration** | Is this a setting of the tenant/platform itself, not a business transaction and not page content? | Tenant identity, Domain, Brand, Locales, Feature Flags, Theme, Currency, Languages |
| An External Provider | **Integration** | Does this talk to an external system, with its own auth, webhooks, and lifecycle? | **Payments** (Providers, Methods, Transactions, Webhooks) — named here as the first real case, not designed |

**Primary Color is the clearest illustration of why ownership must come first**: it is not
Business Data (nothing transacts on it), not Experience Definition (it isn't page/section
structure), and not an Integration. It is Platform Configuration — a setting of the tenant itself.
Persistence for Platform Configuration may reasonably be JSON *or* a Database column (Site
Configuration already uses both, per `SCHEMA_ARCHITECTURE_REVIEW.md`'s Site Configuration section)
— **that choice is implementation, decided after ownership, never instead of it.**

Only once ownership is answered does a second, separate, implementation-level question follow:
does this specific concept need search/joins/relations (→ Database), or is it read as a whole
blob (→ JSON), or does it need its own service boundary (→ dedicated Capability code)? This
second question has no bearing on which of the four owners above is correct — it only decides how
that owner's decision gets implemented.

## 4. Consequences

**This ADR intentionally classifies concepts by ownership, not by storage technology. Database
tables, JSON schemas, or dedicated services are implementation consequences of the ownership
decision, not the decision itself.**

- Retroactively **names** (does not fix) `Unit.content_blocks` as a real violation of this
  principle — Business Data (`Unit`) currently holds Experience Definition-owned content. A future
  candidate for migration into Content's real model; not touched by this ADR.
- Payments becomes a named, real Integration-Capability gap. **Decision Required from Salman**:
  when its own Investigation/Contract starts — not scheduled by this ADR, and not implied to jump
  the existing Restaurant → Store → Clinic template sequencing already established
  (`.claudedocs/architecture/TEMPLATE_ROADMAP_VISION.md`).
- Future Capabilities (Restaurant menus, Clinic booking, Notifications, Analytics, and other
  concepts not yet built) answer "who owns this" once, here, instead of re-deriving it per field —
  each new concept slots into one of the four rows above rather than reopening the question.

## 5. Scope / Non-Goals

- No code changes. No new tables. No Payments design or implementation.
- No migration of `Unit.content_blocks` — named as a consequence, not executed here.
- Does not revisit or change any existing Capability's already-documented Ownership (Content,
  Media, Site Configuration, Catalog) — this ADR states the general classification principle those
  existing decisions already followed informally; it does not re-litigate them.
