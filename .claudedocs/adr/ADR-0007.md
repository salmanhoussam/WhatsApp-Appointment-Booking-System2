## Context

Since 2026-08-29 the platform has carried an open, repeatedly-logged, never-root-caused risk:
"DB latency ~1.5–2 s per query." On 2026-09-05 it was root-caused with reproducible measurements
(`.claudedocs/work/frontend-performance-audit/2026-09-05/`, three evidence files).

The cause is physical, not algorithmic:

```
Users (Middle East) → Cloudflare → Railway AMSTERDAM 🇳🇱 → Supabase SYDNEY 🇦🇺   ~16,600 km
```

Measured facts:

- A trivial `SELECT 1` costs **~1.65 s** through the app; the same query via psycopg2 on a reused
  connection costs **0.338 s** — which is exactly the TCP round-trip time to Sydney.
- A request that touches no database at all completes in **0.15 s**, so neither Railway, FastAPI,
  nor the network to the app is implicated.
- Production (Railway, Amsterdam) and a developer machine in Lebanon pay **the same** DB cost
  (1.58–1.84 s vs 1.62–1.93 s), proving the latency belongs to the database's location rather than
  to the client, the CDN, or the host.
- Endpoint latency follows `≈ 0.15 s + (round trips × per-query cost)`, verified against
  `barbers` (2.9 s), `/rk/config` (7–8.4 s), and a 404 (0.15 s).
- Real user impact: the RK homepage finishes loading at **20 s**; the reservation journey takes
  **8.75 s**, of which **99.6 % is API latency and 0.4 % is JavaScript**.

Every mitigation short of relocation has been measured and rejected:

| Option | Result |
|---|---|
| Remove `pgbouncer=true` (port 6543) | 4× faster but **broken** — 17–19 of 30 concurrent reads fail with `prepared statement "s6" does not exist` (PostgreSQL 26000). The flag is load-bearing. |
| Session mode (port 5432) | ~3.9×, but needs ~20 connections against a **Free-tier Pool Size of 15**. Not viable. |
| Raise Pool Size / `connection_limit` | Does not affect latency at all; and no capacity problem exists today (13–15 of 57 connections, 0/30 errors). |
| Frontend optimization | Already done where it was real (commit `8b44c14`). The bundle reaches DOM-interactive in 75 ms; it is not the problem. |

## Decision

**Create a new Supabase project in `eu-central-1` (Frankfurt) and migrate the platform's database
and storage to it.**

- Frankfurt because the application runs in Amsterdam: ~360 km, RTT **~10–15 ms**, with dense
  direct peering between AMS-IX and DE-CIX. `eu-west-2` (London) and `eu-west-3` (Paris) are
  acceptable equivalents; Frankfurt is chosen as the largest and most mature EU region.
- **`pgbouncer=true` and transaction-mode pooling are retained.** At ~15 ms RTT their ~4-round-trip
  overhead costs ~60 ms instead of ~1.3 s, so the platform keeps prepared-statement safety and
  connection multiplexing instead of trading them away for speed.
- The existing Sydney project remains live and untouched until the migration is verified and an
  observation period has passed.

### Scope: what moves, and the agreed three-phase split

**Phase A (this ADR) migrates ALL 37 client rows unchanged** — every tenant, REAL and DEMO and
EXPERIMENTAL alike. Nothing is filtered, nothing is transformed. Cleanup is Phase B; schema redesign
is Phase C, each with its own decision.

```
PHASE A  Sydney → EU: identical schema, identical data, identical storage, references rewritten,
         verified  →  EU becomes primary
PHASE B  cleanup of demo/experimental tenants
PHASE C  schema redesign (separate ADR)
```

This ordering is the point, not an accident: migrating unchanged is what preserves **clean
attribution** — *same application, same schema, same data, only topology changed* — so any latency
improvement is unambiguously attributable to the region move. Doing a schema redesign inside the
migration would destroy that experiment, invalidate the row-count parity gate, and remove the
ability to roll back.

**Tenant inventory is settled and must not be re-derived by guesswork:** see
`TENANT_INVENTORY.md` in this ADR's implementation folder — **9 REAL** (an earlier "7" was wrong; it
predated Salman's decision to keep `olivello` and `roz`), 14 DEMO, 9 EXPERIMENTAL, and **5 that
remain an explicit open decision** (`cafe`, `tastybites`, `sneakers-lb`, `sneakers-beirut`, `assi` —
all with zero items, orders and reservations). 9 + 14 + 9 + 5 = 37, fully reconciled. The
NEEDS-DECISION five affect **Phase B only**; Phase A migrates them regardless, so they do not block
ratification.

**Not decided here, deliberately excluded from this ADR** (each needs its own decision):
- Any schema redesign — including the `catalog_items` / `catalog_services` duplication and the
  overlapping tenant-type columns on `clients`. See "Consequences" below.
- Removal of test/demo tenants (Phase B).
- Any Supabase↔GitHub integration.

## Rationale

The distance is paid **per round trip**, and every customer-facing flow makes several. This makes
relocation the only lever that reduces the *repeated* penalty rather than a single instance of it —
which is why it is an architectural fix and the alternatives above are tuning.

Projected: per-query cost **1.65 s → ~0.08 s**. This is an estimate derived from measured RTT, **not
a guarantee that any given endpoint becomes 20× faster**; Phase 7 of the Implementation Contract
exists to verify it against reality, and Phase 1 aborts the migration outright if a `SELECT 1` from
Amsterdam to Frankfurt does not land in the ~10–20 ms range.

## Consequences

**Positive**
- The dominant cost in every customer journey is removed.
- The safe pooling configuration is preserved rather than sacrificed.
- Connection-budget pressure disappears as a concern at current scale.
- A brief window exists where two projects run simultaneously — the closest this platform has had to
  a staging environment, which is a documented standing gap.

**Negative / risks**
- Supabase project regions cannot be changed in place, so this requires a new project and a data
  migration on a system with live paying tenants.
- A new project ref invalidates every absolute Supabase URL. Measured: `frontend/src` 35
  occurrences, `scripts/` 11, `prisma/` 1, and in the database `clients.config` 3 rows and
  `gallery_images.url` 6 rows. `app/` is clean (0 — fully env-driven).
- Storage (~200 MB) does not move with `pg_dump` and requires a separate bucket copy. Missing this
  breaks all media on all tenant sites.
- Any write landing on the new project after cutover is lost if we roll back, so cutover needs a
  low-traffic window and an explicitly bounded rollback period.

**Mitigating fact:** the database is only **32 MB**, so dump/restore is a matter of minutes.

**Row-Level Security — a decision about this deployment, NOT a standing principle about Supabase.**
Salman's framing, adopted deliberately so this does not harden into doctrine:

> RLS is intentionally disabled because the current production data path does not use Supabase's
> client/Data API and the backend connects as the database owner; enabling it would not protect the
> current access path without `FORCE ROW LEVEL SECURITY`, and could introduce silent schema drift
> through the existing event-trigger mechanism.

This applies to the "enable automatic RLS on new tables" event trigger offered at project creation:
leave it **off**.

Supporting evidence gathered 2026-09-06: the app connects as `postgres` (verified via
`current_user`), which owns the tables; `supabase-js` is **not** a frontend dependency; no anon key
ships in the frontend bundle; a Data API request against `clients` returns **401**; and tenant
isolation is enforced in application code, where every query filters `client_id`.

**Mandatory re-review trigger** — this decision is revisited, and RLS becomes mandatory rather than
optional, if **any** of the following is ever introduced:

```
supabase-js in a client  OR  the Supabase Data API exposed  OR  direct-to-Supabase mobile/client access
                                        ↓
                            RLS review becomes MANDATORY
```

**Follow-on work this ADR deliberately does not authorise:** the survey performed while preparing
this decision found a real schema problem — the same bookable services stored in *two* parallel
models (`catalog_items.metadata.requires_booking` and the `catalog_services` table: 6/6 rows for
`mr-h`, 6/7 for `rk`), plus roughly eight overlapping columns on `clients` describing tenant type
(`service_type`, `vertical`, `page_type`, `template_key`, `selected_services`, `features`,
`unit_types`, `tier`) alongside the `client_services` table. `vertical` is additionally NULL for
every real non-barber tenant. This is a genuine "one capability, two write paths" violation under
`rules/backend/architecture.md` §9 and deserves its own investigation and ADR. **It must not be
folded into this migration**, because the Contract's rollback and its row-count acceptance gate both
depend on the schema being identical on each side.

## Verification

Governed by `.claudedocs/implementation/SUPABASE_EU_MIGRATION/CONTRACT.md` — nine phases, each with
its own acceptance gate. The ADR is satisfied when Phase 7 shows measured per-query cost materially
below the 1.65 s baseline, a real WhatsApp reservation completes end-to-end against the new database, all
tenant pages render with media intact, and error rate does not increase.
